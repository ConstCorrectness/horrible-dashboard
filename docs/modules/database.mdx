# Module: database

A **plug-and-play database inspector** — a `psql`-like console pane where the user (or
the agent) writes SQL and runs it against any connected database. It ships with a
pluggable driver layer so you can connect to several providers, and exposes the
dashboard's own local vector store as the built-in **`app`** connection.

**Status: implemented** — frontend in `packages/core/src/modules/database/`, backend in
`backend/modules/database/`.

## What it does

- **Connections** — a named-connection store. The built-in `app` connection (the node's
  own SQLite database, `.data/app.db` — library sources, browser history, code symbols,
  tasks) is always present and read-only; you add your own connections for external
  databases. Connections persist in `.data/connections.json`.

  :::note `app` is the app database, not the vector store
  The vector store is **LanceDB**, a *directory* under `.data/lancedb` — there is no
  SQLite file for the SQL console to open, so the `app` connection points at `app.db`
  instead. The two used to be the same file (the vector store was SQLite before the
  LanceDB migration), which is why `vectorstore.get_db_path()` and
  `app_db.get_app_db_path()` are now deliberately separate functions. Browse LanceDB
  collections via the vector-store panel, not the SQL console.
  :::
- **SQL console** — write SQL, run it with **Run** or **Ctrl/Cmd+Enter**, and get a
  results grid with column headers, a status line (`N rows · M ms`, truncation flag),
  and inline error output. Recent queries are kept in a history dropdown. A **Read-only**
  toggle restricts a run to a single `SELECT`/`WITH`/`EXPLAIN` statement.
- **Schema-aware autocomplete** — the editor is CodeMirror with `@codemirror/lang-sql`
  (`SqlEditor.tsx`): keyword completion in the connection's dialect (postgres, mysql,
  sqlite; duckdb uses the PostgreSQL dialect as its nearest match) plus table and column
  completion fed live from the same `/database/connections/{id}/schema` introspection the
  sidebar shows — schema-qualified names (`public.users`) included, with the dominant
  schema as the unqualified default. The mapping lives in the pure helper
  `sqlSchema.ts:schemaToSqlConfig`.
- **Schema sidebar** — an introspected tree of tables → columns (with types and PK
  markers). Click a table to drop a `SELECT * FROM <table> LIMIT 100` into the editor.
- **No synthetic data** — the pane only ever shows real rows returned from a real
  connection.

## Providers & drivers

Each provider is a thin synchronous driver (`backend/modules/database/drivers/`) behind a
uniform `test` / `run_query` / `introspect` contract. Routes run drivers via
`asyncio.to_thread` so the (blocking) client libraries never stall the event loop. Client
libraries are imported lazily, so a missing optional dependency yields a clear error
rather than breaking boot.

| Provider | Driver | Dependency | Notes |
| --- | --- | --- | --- |
| `sqlite` | `sqlite_driver` | stdlib | Backs the built-in `app` connection (`.data/app.db`) and any `.sqlite`/`.db` file. |
| `postgres` | `postgres_driver` | `psycopg[binary]` | Connect to any Postgres; **pgvector** `vector` columns and `bytea` blobs are summarized in the grid. |
| `duckdb` | `duckdb_driver` | `duckdb` | Local analytical/columnar querying (file or in-memory). |
| `mysql` | `mysql_driver` | `pymysql` | MySQL / MariaDB. |

Result cells are coerced to JSON-safe values: binary blobs and long numeric arrays
(embeddings, pgvector) are summarized (e.g. `<1536 bytes>`, `[384 numbers]`), and
dates/decimals are stringified.

## The node's two local stores

The dashboard keeps its own data in **two** places, and they are not the same thing:

| Store | Path | Shape | Reached by |
| --- | --- | --- | --- |
| **App database** | `.data/app.db` | SQLite file — `library_sources`, `browser_history`, `browser_bookmarks`, `code_symbols`, `async_tasks` | the built-in `app` connection; `app_db.get_app_db_path()` |
| **Vector store** | `.data/lancedb` | LanceDB *directory*, one table per collection | `vectorstore.py`; the vector-store panel |

The **app database** is ordinary SQL you can query in the console
(`SELECT id, library, status FROM library_sources`), because it is a real SQLite file.

The **vector store** is not. LanceDB is a directory of its own format, so it has no
SQLite file to attach and is reached through `vectorstore.py`
(`upsert_document` / `search_documents` / `list_documents`) rather than the console.
Sibling tables (`<collection>__clip`, the CLIP vectors) are hidden from the global
sweeps so they don't show up as fake collections — see [library](library.mdx).

:::warning These were one file once
Before the LanceDB migration the vector store *was* SQLite, and a single `get_db_path()`
returned it. Code that still assumes that — passing the LanceDB path to
`sqlite3.connect()` — fails with the opaque `unable to open database file`. That is why
`vectorstore.get_db_path()` (the LanceDB dir) and `app_db.get_app_db_path()` (the SQLite
file) are separate, deliberately un-mergeable functions.
:::

Embeddings are generated by a tiered pipeline (active agent provider → dedicated
embedding model probe → deterministic local hash fallback so it works offline) in
`embeddings.py`. The vector store also backs **agent-commons** matchmaking — see
[network](network.mdx).

:::tip Bulk writes: use the batch APIs
`get_embeddings(texts)` and `upsert_documents(collection, rows)` are the paths any
index build should take. Their single-document siblings are fine for one-off writes but
pathological in a loop, because **both costs are per-call, not per-row**:

- `merge_insert` is a whole-table operation — ~1.5s on a 5k-row table whether you hand
  it 1 row or 256.
- `get_embedding` resolves the model (`GET /api/tags`) and builds a fresh HTTP client
  on every call.

Looping the single-document versions over ~40k symbols took **hours**, with the
embedder itself accounting for well under a minute of it. `get_embeddings` resolves the
model once (cached, 60s TTL), reuses one client, and sends a batched `/api/embed` —
falling back to bounded-concurrency single requests when the provider has no batch
endpoint. See [symdex](symdex.mdx#build-cost).
:::

## Contributions to the Layout Shell

- **Widget**: `database.console` — the connection bar + schema sidebar + SQL console.
- **Command**: `database.open` (`Database: Open Console`) — opens the console in the
  workspace center.
- **Settings**: `database.defaultConnection` (default `app`) and `database.rowLimit`
  (default `1000`), read live via `useSetting()` — see [settings](settings.mdx).

## Backend REST API

Mounted under `/api/database`.

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/connections` | List connections (built-in + saved, secrets redacted) and available providers. |
| `POST` | `/connections` | Create a connection. |
| `PUT` | `/connections/{id}` | Update a connection (built-in is read-only; omitted secrets are preserved). |
| `DELETE` | `/connections/{id}` | Delete a saved connection. |
| `POST` | `/connections/test` | Probe an unsaved connection (form still holds the password). |
| `POST` | `/connections/{id}/test` | Probe a stored connection (server-side credentials). |
| `GET` | `/connections/{id}/schema` | Introspected tables/columns. |
| `POST` | `/query` | Run SQL against a connection. `read_only` rejects non-`SELECT`. Returns columns, rows, rowcount, `elapsed_ms`, `truncated`. |
| `GET` | `/status` | App vector store stats + active embedding provider/model. |
| `POST` | `/pull` | Stream an Ollama `all-minilm` embedding-model download (NDJSON). |
| `GET` | `/collections` | App vector store collection names. |
| `GET` | `/documents` | List app vector store documents (paginated, filterable). |
| `POST` | `/documents` | Embed and upsert a document into the app vector store. |
| `DELETE` | `/documents/{id}` | Delete a document by id. |
| `POST` | `/search` | Semantic similarity search in an app vector store collection. |

## Agent Tools

The widget registers these tools with the agent orchestrator:

| Tool Name | Description | Parameters | Side Effect |
| --- | --- | --- | --- |
| `database.listConnections` | List connections the agent can query. | none | No |
| `database.describe` | Schema (tables/columns) for a connection, so the agent writes correct SQL. | `connection_id` (str, opt) | No |
| `database.query` | Run a **read-only** `SELECT` against a connection. | `sql` (str), `connection_id` (str, opt) | No |
| `database.execute` | Run a writing statement (INSERT/UPDATE/DELETE/DDL); permission-gated. | `sql` (str), `connection_id` (str, opt) | Yes |
| `database.semanticSearch` | Vector search a collection in the app vector store. | `collection` (str), `text` (str), `limit` (int, opt) | No |

## Agent Context

The console exposes the active connection and its schema via `useAgentContext()` so the
agent can target the right database:

```typescript
{
  activeConnection: "app",
  provider: "sqlite",
  tables: [{ name: "documents", columns: ["id", "collection", "text", "embedding"] }]
}
```

## Security

SQL execution is unsandboxed (consistent with the v1 trusted plugin posture). The agent's
`database.query` tool is read-only; writes go through `database.execute`, which is
side-effect gated. Connection credentials are stored as plaintext in the gitignored
`.data/connections.json`; encryption is a tracked follow-up.

## Browser vs Desktop

Identical in both layouts — the frontend talks to the local FastAPI server, which owns
the driver connections and the SQLite vector store.
