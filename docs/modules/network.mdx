# Module: network

:::note This module contributes no panes
Its surfaces are sections of the **[People](people.mdx)** pane
(`people.home`). Everything below still describes the services, settings and
components; only the "where do I click" answer changed. Old names keep resolving —
`show("Peers")`, `show("social.friends")` and the rest land on the right section.
:::

Distributed multi-user collaboration: connect this node to other users' nodes,
share panes live, and let your agent talk to theirs. The frontend is a **Peers**
widget plus settings; the heavy lifting is the backend peer fabric documented in
[Distributed peer fabric](../architecture/distributed.mdx).

**Status: implemented (groundwork).** Frontend in
`packages/core/src/modules/network/`, backend in `backend/modules/network/`.

## Contributions to the layout shell

**No panes, and no widgets.** This module contributes services and settings only.

It used to own five widgets — Peers, Peer Chat, Peer Monitor, Lobby and Agent
Relay, grouped as a "Peer Fabric" panel group. Only one of them was something a
person wanted to *look at*, and it is now the **Messages** section of the
[People](people.mdx) pane. The other four were infrastructure readouts that became
destinations because a pane was the only way to show anything — "Peers" in
particular answered *which machines are connected* when the question people
actually have is *which of my friends is around*, which People answers by person.

Nothing was lost. The transports, trust store and rendezvous are still here as
services (`ws.ts`, `lobby.ts`, `peerchat.ts`, `collab.ts`), the knobs are on the
settings page, and the traffic is in [observability](observability.mdx). What went
away is the idea that each of them deserved somewhere to live.

- **Commands:** none of its own; People's commands reach every surface.
- **Settings:** [below](#settings), split basic / advanced.

## Network-aware panes (the collab contract)

A pane declares it participates in the peer fabric through the **`collab`** field
on its `PanelDecl`/`WidgetDecl` (the `CollabDecl` shape in
[`@horribledashboard/sdk`](../architecture/plugin-sdk.mdx)):

```ts
collab?: {
  room: 'shared' | 'instance'; // one well-known room, or one room per pane instance
  key?: string;                // key suffix; defaults to the view id
  autoShare?: boolean;         // start shared on open (default false — opt-in)
}
```

This makes networking a **declared, first-class property of a pane** rather than
something each pane hand-wires. Panes consume it through the **`useCollab(paneKey)`**
host hook (exported from the network module), which owns joining/leaving the room,
tracking the authoritative revision, rebasing on a rejected (stale) op, and
surfacing a live presence count — returning `{ text, setText, shared, setShared,
members }`. The [scratch](scratch.mdx) panel is the reference consumer.

The agent-to-agent tools `list_peers` and `agent.ask_peer` are **backend-static**
(resolved in the orchestrator against the `PeerHub`), so unlike other modules they
need **no frontend `agentTools` handler** — there's nothing for a browser to execute.
They're documented in [Agent chat](agent-chat.mdx).

## Backend surface

### REST — `/api/network`

| Method & path | Purpose |
|---|---|
| `GET /identity` | This node's `NodeIdentity` (node_id, public_key, node_name, capabilities). |
| `GET /peers` | `{ self, peers[] }` snapshot. |
| `POST /invite` | Mint a single-use invite `{ invite, token, expires }`. |
| `POST /pair` | Redeem an invite (decode → dial → handshake with the token). |
| `POST /connect` | Dial an address directly `{ address, transport }`. |
| `DELETE /peers/{node_id}` | Disconnect a peer. |
| `POST /ask-peer` | Ask a peer's agent `{ peer_id, prompt }` → `{ ok, answer?, error? }` (REST entry to `agent.ask_peer`; the remote turn is gated read-only). |

### WebSocket endpoints

- **`/peer-ws`** — inbound peer connections (the signed `PeerEnvelope` protocol
  between nodes; **not** the browser channel protocol). Distinct from `/ws`.
- **`/ws` `network` channel** — live presence + control for the browser:

  | Direction | event | data |
  |---|---|---|
  | client→server | `list_peers` | `{}` |
  | client→server | `list_metrics` | `{}` (request an immediate Peer Monitor snapshot) |
  | client→server | `connect` | `{ address?, nodeId?, transport }` |
  | client→server | `disconnect` | `{ nodeId }` |
  | client→server | `pair_redeem` | `{ invite }` |
  | server→client | `peers` | `{ self, peers[] }` |
  | server→client | `peer_update` | `{ peer }` |
  | server→client | `peer_metrics` | `{ metrics[] }` (periodic + on request — see [Peer Monitor](#peer-monitor)) |
  | server→client | `pair_result` | `{ ok, peer?, error? }` |
  | server→client | `error` | `{ message }` |

- **`/ws` `collab` channel** — shared-pane sync (see below).
- **`/ws` `peerchat` channel** — direct 1:1 peer messaging (see [Peer Chat](#peer-chat)).
- **`/ws` `lobby` channel** — discovery + rooms for the browser:

  | Direction | event | data |
  |---|---|---|
  | client→server | `state` | `{}` (request a snapshot) |
  | client→server | `connect` | `{ url? }` (connect to a lobby server) |
  | client→server | `list_rooms` / `create_room` / `join_room` / `leave_room` | `{ … }` |
  | server→client | `state` | `{ connected, url, rooms[], directory[], self }` |
  | server→client | `rooms` | `{ rooms[] }` |
  | server→client | `directory` | `{ directory[] }` |
  | server→client | `room_created` / `joined` / `peer_joining` / `error` | `{ … }` |

The **lobby server** itself is a standalone app (`lobby_server.py`) exposing
`/lobby-ws` (directory + rooms + signaling) and the bundled `/relay-ws` for the
fallback path; run it separately:
`uv run uvicorn backend.modules.network.lobby_server:app --port 9000`. A node opts in
via `network.lobbyUrl`. See
[the lobby system](../architecture/network-protocol.mdx#the-lobby-system).

## Collaborative shared panes

A `CollabRoom` (`collab.py`), keyed by an opaque `paneKey`, holds authoritative
`text` + a monotonic `rev`. Members sync with a **rev check** — last-writer-wins,
but no *lost* updates: an op with a stale `baseRev` is rejected and the writer
rebases onto the authoritative state. Inbound peer ops are adopted as authoritative
by `rev` and rebroadcast to local members (not re-forwarded, so no loops). This is
groundwork, not a CRDT — a clean seam for one later.

### A share is addressed to a person

You share a pane **with Andrew**, and the fabric picks whichever of his machines is
online. Asking someone which of their own computers to send a pane to is a question
with no good answer, and it is the same reason the roster is keyed by person.

Each room tracks the **nodes it is actually shared with** (`room.peers`). A node
lands there two ways: you shared the pane with its owner, or an op for that pane
arrived from it — which only happens if they shared with you, and is how the far
side learns to route edits back.

:::danger The leak this replaced
`_forward_to_peers` used to iterate `peer_hub.peers` — *every* node with a live
session — and send the pane's full text to each. Anyone you were connected to
received the contents of every shared pane, whether or not they had any part in
it. "Sharing" was a global broadcast wearing the word "room".

Inbound ops are now also gated on `session.info.trusted`. Knowing a pane key is not
permission: ops are last-writer-wins, so an untrusted peer that guessed or overheard
a key could both read the pane (we would start forwarding to them) and rewrite it.
:::

| Direction | event | data |
|---|---|---|
| client→server | `join` | `{ paneKey }` |
| client→server | `leave` | `{ paneKey }` |
| client→server | `op` | `{ paneKey, baseRev, text }` |
| client→server | `share` | `{ paneKey, personId }` |
| client→server | `unshare` | `{ paneKey, personId }` |
| server→client | `state` | `{ paneKey, rev, text, members }` |
| server→client | `op` | `{ paneKey, rev, text, from }` |
| server→client | `presence` | `{ paneKey, members }` (occupancy changed) |
| server→client | `shared` | `{ paneKey, people: [{ personId, name }] }` |
| server→client | `rejected` | `{ paneKey, rev, text }` |
| server→client | `error` | `{ paneKey, message }` (e.g. nobody of theirs is online) |

`shared` resolves nodes back to **people** on the backend, because the node holds
the device→person map and a pane listing node ids would be exactly the
machine-shaped UI the roster exists to replace.

The reference consumer is the **scratch** panel's "Share with…" picker, which
declares a `collab` room and drives the
[`useCollab`](#network-aware-panes-the-collab-contract) hook
(`modules/scratch/index.tsx` + `modules/network/useCollab.ts`). See
[Scratch](scratch.mdx).

## Peer Monitor

A backend **`PeerMonitor`** (`monitor.py`, started by the app lifespan) heartbeats
every connected peer on an interval: it pings each (the hub's `ping`/`pong`
round-trip) to measure RTT and samples the per-session byte/message counters the
hub maintains. Each tick is broadcast as a `peer_metrics` event on the `network`
channel; a freshly opened monitor requests an immediate snapshot with
`list_metrics`. The `network.monitor` widget renders the table. The monitor is
read-only — it never mutates peer state beyond stamping each session's `rtt_ms`.

Each `PeerMetrics` row: `{ node_id, node_name, transport, status, rtt_ms,
bytes_in, bytes_out, msgs_in, msgs_out, last_seen }`.

## Peer Chat

The transport half of direct messaging: `ChatManager` (`chat.py`) relays a message
over the signed peer wire (a `peer_chat` envelope) and mirrors it to this node's
own tabs. Where `collab` syncs an **editable document**, `peerchat` is an
**append-only message log**.

Conversations are keyed by **person** and persisted in `social_messages`, not held
in memory per node — see [Messages](social.mdx#messages) for the channel contract,
the unread counts, and why an inbound message nobody is reading raises a
[notification](notifications.mdx).

## Agent-to-agent relay

The `network.relay` widget (Agent Relay) is the UI over agent-to-agent: pick an
agent-capable peer, ask a question, and read the answer. It calls `POST
/api/network/ask-peer`, a thin wrapper over the same `agent_bridge.ask_peer` the
`agent.ask_peer` tool uses, so the remote turn runs gated and read-only-by-default
on the peer's node (which must have `network.allowRemoteAgent` enabled). See
[Agent chat](agent-chat.mdx#agent-to-agent-talking-to-a-peers-agent).

## Remote control (`remote_command`)

A trusted peer can drive this node: open a pane, play media, raise a notification,
ask for an agent-generated briefing, or cancel a turn it started. Handled by
`remote_control.py`, which drops any command from an untrusted peer; the reverse
direction is the `mobile.*` agent tools in `mobile_tools.py`. The [Android
companion app](mobile-android.mdx) is the primary consumer of both — it pairs by
QR and appears on the fabric as an ordinary peer carrying the `mobile` capability.
That page holds the full command table.

A remote agent turn (`agent_request`) is run on a **detached task** tracked in
`agent_bridge._active_remote_turns`, so a follow-up `agent_cancel` can stop it.
Handlers are awaited inline by the session pump, so a handler that awaited a long
turn would wedge the receive loop for its duration — see
[Cancelling a remote agent turn](mobile-android.mdx#cancelling-a-remote-agent-turn).

Screen watching (`view_request` / `view_frame`) is **scaffolded but not
functional** — the desktop never emits a frame. See
[Remote view](mobile-android.mdx#remote-view-screen-watching).

## Settings

Split **basic** and **advanced** on the settings page. The line between them: a
basic setting is one a working install might legitimately change (what am I called,
do I accept connections, who may pair). Advanced is NAT-traversal plumbing — TURN
credentials, STUN hosts, relay and signalling URLs — which is either irrelevant or
copied verbatim from whoever runs your infrastructure. Fourteen knobs at equal
weight taught people to skim past the six that matter.

### Basic

| Key | Type | Default | Meaning |
|---|---|---|---|
| `network.nodeName` | string | hostname | Display name advertised to peers. |
| `network.enableDirect` | boolean | `true` | Accept/dial direct WebSocket peers. **Restart.** |
| `network.enableLanDiscovery` | boolean | `false` | Advertise/discover via mDNS. **Restart.** |
| `network.trustMode` | enum | `manual` | `manual` (an invite you generated) or `open-lan`. |
| `network.lobbyUrl` | string | `""` | Lobby server `ws://…/lobby-ws` for discovery + rooms (blank = off). |
| `network.allowRemoteAgent` | boolean | `false` | Let a trusted peer's agent ask yours. |

### Advanced

| Key | Type | Default | Meaning |
|---|---|---|---|
| `network.advertisedAddress` | string | `""` (auto) | URL peers dial to reach this node, encoded into invites. Blank auto-detects this machine's LAN IPv4 — `localhost` would make every invite undialable from another device. Set it for a public hostname or a forwarded port. |
| `network.relayUrl` | string | `""` | Rendezvous broker URL (blank = off). **Restart.** |
| `network.iceEnabled` | boolean | `false` | Gather a STUN server-reflexive candidate (public IP) alongside host/LAN candidates. |
| `network.stunServer` | string | `stun.l.google.com:19302` | `host:port` for STUN public-IP discovery (when ICE is on); also the STUN ICE server for the WebRTC transport. |
| `network.enableWebRtc` | boolean | `false` | Connect over a WebRTC data channel, SDP signaled via the lobby. Needs `uv sync --extra webrtc`; the relay stays the fallback. **Restart.** |
| `network.turnUrl` | string | `""` | Optional TURN relay for WebRTC (`turn:host:3478`) for NATs STUN can't punch (blank = STUN only). |
| `network.turnUsername` | string | `""` | TURN username credential (if required). |
| `network.turnCredential` | string | `""` | TURN password/credential (if required). |
| `network.remoteAgentMode` | enum | `plan` | Permission mode for a remote turn (`plan` = read-only, then `acceptEdits`, `autonomous`). |

**Restart** marks the four settings `build_transports()` reads once at startup. A
transport owns a bound socket or a multicast thread, so swapping one under live
sessions is a different job from reading a flag; before they said so, they looked
like live switches that silently did nothing.

### Two settings that were removed

- **`network.directoryUrl`** had **zero readers repo-wide**. Finding people by name
  is the [Atlas presence directory](social.mdx#the-presence-directory-mongodb-atlas)
  and the game server's username directory, neither of which is configured here.
- **`trustMode: 'directory'`** was never implemented, so `trust.evaluate` rejected
  every peer — selecting it made the node silently unpairable. `trust_mode()` now
  reads a stored `directory` as `manual`, so an existing config recovers rather
  than staying broken.

`remoteAgentMode: 'ask'` went the same way: ASK prompts a human, and the human it
would prompt is not the one who started the turn. It was mapped to `default`, so
choosing "ask" silently granted a *higher* permission level than its name promises.
An unrecognized mode now falls back to `plan` — read-only — so a stored `ask` fails
closed.

### Pairing is mutual

`handshake_dial` persists a `known_peers` record for the peer it dialled, the same
way `trust.evaluate` does for one it accepted. It used to mark trust in memory
only, so after A redeemed B's invite **only B remembered** — and the next time A
was the one dialled, B's node had never heard of it and rejected the handshake.
Both ends have verified an identity cryptographically during the handshake; both
should write it down.

Server-side state under `$HORRIBLE_DATA_DIR`: `network-identity.key`,
`network-peers.json`, `network-invites.json`.

## Browser vs desktop

| | Browser | Desktop (Tauri) |
|---|---|---|
| Peers widget, REST, `/ws` channels | ✅ | ✅ |
| Direct / relay transports | ✅ (backend) | ✅ (backend) |
| LAN discovery (mDNS) | depends on the host network allowing multicast | same |

Everything runs in the backend, so both layouts behave identically; LAN discovery is
the only capability that depends on the host network (and degrades gracefully when
multicast is unavailable).
