# Module: training

**Notebook-driven neural-network training** inside the dashboard: pick an environment
(a Kaggle competition, a Hugging Face dataset, a Gymnasium env — or any plugin-provided
source), get a **project** with its own uv-managed venv and a scaffolded `.ipynb`
notebook, then build and train models with live visual feedback (metrics charts, model
architecture graph, manim explainers, gym rollout frames). The agent drives the whole
flow: *"i want to work on kaggle's pokemon tcg competition"* resolves the competition,
creates the project, downloads the data, and opens the right panes.

**Status: implemented** — frontend in `packages/core/src/modules/training/`, backend in
`backend/modules/training/`. Projects + per-project venvs + the environment provider
layer, the native notebook pane on the Jupyter kernel protocol, the live metrics
pipeline + chart pane, the architecture graph pane, the manim + gym-rollout runners,
Kaggle-kernels/Colab push, the peer-fabric training ads, and the agent tool integration
that drives the whole flow from a natural-language ask.

## Projects on disk

Each project is one directory under `training.projectsRoot` (default
`~/horrible/training`); the directory **is** the record:

```
<projectsRoot>/<slug>/
  main.ipynb        # scaffolded notebook (nbformat v4, Kaggle-compatible)
  project.json      # ProjectModel dump (id, name, refs, python, flags)
  data/             # provider-fetched datasets
  media/            # manim renders, saved frames
  .venv/            # uv-managed project venv
```

Torch-sized dependencies live in the **project venv**, never the backend env. The venv
is created with `uv venv --python <training.defaultPython>` and bootstrapped with
`ipykernel` (kernel side of the Jupyter protocol) plus the local **`horrible-train`**
helper package, then the provider's scaffold requirements (`pandas`,
`gymnasium[box2d]`, …). All subprocess work (uv, kernels, renderers) uses blocking
`Popen` pumped on daemon threads — the Windows-safe pattern shared with the LSP/terminal
modules — with output lines streamed to the UI.

A directory whose `project.json` is missing or unreadable (e.g. a partial dir left by an
aborted bootstrap — just a `.venv`) is treated as **not a project**: it's skipped by
listing/lookup, creating the same env **adopts** the slug (writes `project.json`, reuses
the existing `.venv`) instead of stranding it behind a `-2` suffix, and `delete` removes
such partial dirs (which `get_project` can't resolve). If a persisted notebook pane
references a project that no longer exists, the kernel-open error carries an
`unknown_project` code and the pane shows a "no longer exists" state with a **Close**
button that drops the dead pane from the saved layout — so it self-heals on the next load.

### Projects another module owns

`ProjectModel.owner` names the module that keeps a project as **working storage**.
The only one today is [evals](evals.mdx#that-project-is-working-storage-and-says-so),
which builds one per suite to run Hugging Face benchmarks in. Those are created
straight through `create_project` rather than through the create *route*, so — and
this is the part that bit — they have **no scaffolded `main.ipynb`**, and their venv
carries only the benchmark's requirements: no `ipykernel`, no `horrible_train`.

They are listed and **marked, not hidden** (the bundled-suite rule): a project
missing from the pane is a directory eating disk you can neither see nor delete. What
they do not get is authoring actions — open notebook, recipe, and both pushes are
disabled with the reason in their tooltip, because every one of them could only fail.
Delete stays enabled.

Two failures this closed, both of the silent kind:

- **A missing notebook read as a path.** The open reached a bare `FileNotFoundError`,
  whose `str()` is *only* the path, and the pane renders that verbatim — so the whole
  explanation was a lone `C:\…\main.ipynb`. It is now a `MissingNotebookError`
  carrying a sentence, and it deliberately does **not** use the `unknown_project`
  code: the project is fine, so a pane that self-heals by closing itself would be
  throwing away the wrong thing.
- **The kernel badge contradicted the error.** `kernel` starts at `starting` and only
  `opened` or a `kernel_status` event ever moved it, so a failed open left "● starting"
  sitting next to the message explaining why it hadn't. An error arriving before
  `opened` now marks the kernel `dead` — and *only* then, since the same event also
  carries recoverable errors on a live session (a rejected `cells` op), where calling
  the kernel dead would be its own lie.

That "unreadable means not a project" rule has a sharp edge: background workers rewrite
`project.json` (`_mark(project, venv_ready=True)`) while requests read it, and a
`write_text` truncates before it writes. A read landing in that window saw an empty file
and the route answered **404 for a project that exists** — a bug that only appeared under
load and looked like anything but itself. Both sides now go through
`backend/atomic_write.py`: writes replace atomically, and reads distinguish "no such
record" from "someone is replacing it right now", which on Windows is a transient
`PermissionError` rather than a missing file. Pinned by a concurrent read/write test in
`test_training_projects.py`.

Background work started by a route (`fetch`, venv bootstrap, dep install) runs on
**tracked** daemon threads: `routes._spawn` registers each one and `routes.join_workers`
waits for them. Nothing in the product blocks on it — it exists so tests can wait on the
work itself rather than on a wall clock, which is what a fixed-deadline poll silently
degrades into on a loaded machine.

## Environment providers

A provider is a thin synchronous adapter behind one uniform contract
(`backend/modules/training/providers/base.py`), mirroring the database module's driver
layer: `search`, `resolve`, `fetch` (into `data/`, with progress), and `scaffold`
(starter notebook cells + venv requirements). Client libraries import lazily inside
methods; short calls run via `asyncio.to_thread`, fetches on daemon threads.

| Provider | Kinds | Fetch | Scaffold |
| --- | --- | --- | --- |
| `kaggle` | competition, dataset | download + unzip into `data/` (creds: `training.kaggle.*` settings → `~/.kaggle/kaggle.json`) | pandas data-loading starter |
| `huggingface` | dataset | lazy — the notebook calls `datasets.load_dataset(id)`; snapshot into `data/` on request | `load_dataset` starter |
| `gymnasium` | env | nothing to fetch (bundled static catalog; no gym import in the backend env) | RL rollout loop streaming frames + episode rewards |

**Plugins add providers**: a backend plugin calls `host.add_training_provider(provider)`
(see [backend plugin SDK](../architecture/backend-plugin-sdk.mdx)); `get_provider()`
falls back to the plugin registry, so a new environment type is one file or one plugin
call.

## The `horrible-train` helper

`backend/modules/training/helper/` is a zero-dependency pip package installed into every
project venv. Training code (notebook cells or scripts) calls:

```python
import horrible_train as ht
ht.run("baseline")            # name the run (auto-created on first log)
ht.log(step=i, loss=0.42)     # → live metrics chart pane
ht.frame(env.render())        # → live rollout pane
ht.watch(model, example=x)    # → architecture graph pane (torch.fx, tree fallback)
```

Each call prints one `@@HORRIBLE@@{json}` **sentinel line** to stdout; the backend
strips these from visible output and fans them out as `training` channel events — the
same line-protocol trick the visualizer uses for Pygame frames, so it works identically
under a kernel, a script runner, or manim.

## The recipe surface

A fine-tune is a couple of dozen numbers, and until this landed the only place to
put them was a notebook cell written from memory. `recipes.py` makes them a
**schema**: a curated catalog of fields, each with a type, a default and a
one-line description, rendered as a form by `training.recipe` (non-singleton,
params `{projectId}`) and **materialized into `main.ipynb`**.

**There is no new execution path.** `materialize()` returns notebook cells. They
run on the same kernel in the same venv, their `ht.log()` output is
indistinguishable from hand-written code's, and the same notebook is what the
Kaggle and Colab push already send. The recipe itself lives in `recipe.json` so
the *form* round-trips; the cells are yours the moment they land and are never
read back. A regenerate **replaces** the previous block (found by a
`horrible_recipe` cell-metadata flag, with the header line as a fallback) rather
than appending — two `SFTConfig` definitions in one notebook is a bug where the
second silently wins, discovered after a wasted run.

### Validated against what is actually installed

The expensive failure this exists to prevent: `trl` renamed
`SFTConfig.max_seq_length` to `max_length`, so a recipe emitting the wrong one
dies with a `TypeError` several minutes in, after the dataset has downloaded. So
fields carry `aliases`, and `introspect()` asks the **project venv** — one
subprocess, cached on the venv's mtime — which names its installed classes
actually accept, via `dataclasses.fields()` on the real `SFTConfig`/`LoraConfig`.

Four states, and the last two are not the same thing:

| Status | Meaning | Emitted? |
| --- | --- | --- |
| `ok` | the installed class accepts this name | yes |
| `renamed` | it accepts an alias instead | yes, under the alias, with a comment |
| `unsupported` | we asked, and it accepts neither | **no** — dropped, and named as dropped in the header |
| `unvalidated` | we never got to ask (no venv, no trl) | yes, with a banner saying it wasn't checked |

Two fields make the rule concrete. `max_length`/`max_seq_length` **are** aliases —
same meaning, different spellings across versions. `warmup_ratio` and
`warmup_steps` are deliberately **not**, even though transformers 5 dropped the
first and kept the second: they carry different units, so aliasing them would
send `0.03` — three percent of training — into a field meaning "three hundredths
of a step", which is no warmup at all and raises nothing anywhere. Whichever one
the installed version accepts is the one that renders.

**The form admits it is not the whole API.** `TrainingArguments` has 112 fields
on transformers 5.15; this catalog has 24. `Introspection.extra` counts the
difference and the header says "24 of 118 knobs — edit the generated cell for the
rest", because a form that looks complete is a form you trust to be complete.

Parameter docs come from the node's own **versioned doc index** (the `trl` and
`peft` crawler seeds): `GET /training/recipe/docs` returns a link per config class
carrying the indexed version and the `installedMismatch` annotation, so the link
is to docs for a version you can compare against rather than to whatever is
current. An empty index yields no links rather than a guessed URL.

### `report_to` is first-class, and local metrics stay authoritative

The tracker picker (`none` / `tensorboard` / `wandb` / `mlflow` / `trackio`) sets
`SFTConfig.report_to`. It is genuinely **additive**: every generated recipe
installs `ht.callback()` — a `TrainerCallback` in the helper package that mirrors
each logged scalar into the metrics pane — so the chart works offline, works with
`report_to=["none"]`, and keeps working when a tracker's key expires mid-run.
"None" means no third party, never no metrics.

Credentials live in the **`trackers` connector** (Fernet-encrypted, W&B key and
MLflow tracking URI, both secret because a tracking URI routinely embeds one),
never in settings — `GET /api/settings` hands the whole bag to the browser. This
is the one connector whose `id` names no agent-tool group, because "log this run
to W&B" is a property of a recipe you wrote, not something the agent should do on
your behalf.

They reach training code through the **environment at spawn**: `SessionConfig.env`
(new, on `notebook_core`) is merged over the backend's own by the kernel manager,
and the script runner does the same. That is what keeps the key out of the
notebook, out of `project.json`, and out of every HTTP response. `env_for()` is
scoped to the trackers the recipe selected, so connecting the tile does not by
itself start shipping every run somewhere.

### Closing the loop: checkpoint → GGUF

`convert.py` turns a finished checkpoint into a GGUF in the **llama.cpp module's
managed model directory** — the one its catalog scans, its disk budget counts and
its delete route may touch — so a model you trained is one this node serves. See
[llamacpp](./llamacpp.mdx).

- **The converter is not in the release binaries.** `convert_hf_to_gguf.py` lives
  in the llama.cpp repo, so it is fetched on demand **at the tag of the installed
  build** (a converter from a different release can write a file the server reads
  slightly wrong), cached under the data dir with its sha256 recorded as
  `verified: false` — GitHub publishes no digest for a raw file.
- **A LoRA checkpoint is not a model.** Told apart by `adapter_config.json` and
  sent to `convert_lora_to_gguf.py` with the base model read from that file; the
  result is labelled an adapter, since `llama-server` loads it with `--lora`
  beside a base model rather than serving it alone.
- **It runs in the project venv**, which is where torch lives. Missing converter
  deps (`gguf`, `sentencepiece`, `protobuf`) are installed through `envs.install`
  — `uv pip install --python <venv>`, because a uv-created venv has **no pip in
  it at all** and `python -m pip` fails on every project this module makes.
- Output types are the ones the converter itself writes (`f16`/`bf16`/`f32`/
  `q8_0`). `q4_k_m` is a separate `llama-quantize` step and is deliberately not
  offered, because offering it and silently producing f16 would be worse.

### The conversion records where the file came from

`lineage.py` writes one row per produced GGUF into `app.db`, keyed by its path.

Before it, a file called `my-project-checkpoint-1200-f16.gguf` in the llama.cpp
catalog told you a project id and nothing else — not the base model it was fine-tuned
from, not the recipe that produced it. "Score my fine-tune against its base" needs
that first one, and it was something you had to remember by hand.

**The GGUF path is the join key**, which is what keeps this a provenance row rather
than a workflow engine: `RunTarget.model_path` already names a file and
`_output_path` already writes a deterministic name, so everything downstream keys off
the path already. **One writer** — `convert.py`, at the one moment every field is
known. Several readers: `GET /api/evals/targets` labels a target *"fine-tune of
&lt;base&gt;"* and carries `baseModel`, and `llamacpp.list_models` reports the same.

Two details that decide whether it works:

- **The base model falls back to the recipe.** `run_conversion`'s `base_model`
  argument is only *required* for a LoRA (an adapter is meaningless without one), so
  for a full fine-tune it is empty and the recipe is the only place the base is
  recorded. Reading the argument alone would leave every full fine-tune with no base
  — that is, with the feature not working in the common case.
- **The recipe is snapshotted, not referenced.** `recipe.json` keeps changing as you
  tune the next run, and a row saying "trained with lr=2e-4" has to keep meaning that
  after you try 1e-4.

Writing the row can never fail a conversion: `lineage.record` swallows, because the
GGUF is on disk and servable whether or not the bookkeeping lands.

## The notebook pane & kernel sessions

`training.notebook` is a **native cell UI** (CodeMirror cells, non-singleton, opened
with params `{projectId, notebook}`) speaking the Jupyter kernel protocol — no iframed
JupyterLab. The kernel engine itself is **domain-neutral and shared**: it lives in
`backend/notebook_core/` (`KernelSession`, nbformat IO, the manager's ws event handling)
and is also consumed by the generic [notebook module](./notebook.mdx). `training/kernels.py`
subclasses it with the training specifics — sessions keyed `{projectId}:{path}`, spawned
from the project venv, with the stdout sentinel scan. The backend side runs one
`TrainingKernelSession` per open notebook:

- The kernel spawns from the **project venv's python** (`-m ipykernel_launcher`) via
  `jupyter_client`'s sync API on daemon threads (event-loop-agnostic: works under
  uvicorn `--reload` on Windows). No kernelspec files — an in-memory spec pins the venv.
- Sessions are **process-global**: closing the pane (or the tab) leaves training
  running; reopening reattaches and replays the current notebook state.
- The in-memory nbformat doc is authoritative — UI/agent edits mutate it, iopub
  outputs append to it, and it's flushed atomically to the `.ipynb` (debounced 2 s +
  after each completed cell), so the on-disk notebook stays Kaggle-compatible truth.
- Executions run serially through a queue; stream output passes through the sentinel
  splitter, so `horrible_train` telemetry never appears as cell text.
- **Interrupt** rides the platform interrupt (Win32 event / SIGINT). Windows caveat:
  it lands *between* statements — training loops stop in milliseconds, but a single
  long blocking C call (one `time.sleep(600)`) defers it until that call returns;
  **Restart** is the hard stop.

Cells also get a **language server** — completion, hover and diagnostics, with names
resolving across cells (see
[Notebook cells get the same language server](editor.mdx#notebook-cells-get-the-same-language-server)).
This is the one place it matters most: the server resolves its interpreter by walking
up from the file to the nearest `.venv`, which for a training notebook is **the project
venv** — so a recipe completes against the `transformers`/`trl`/`peft` it will actually
run on, not against the dashboard's own environment. That is also why the pane resolves
`Project.root` from `GET /api/training/projects/{id}` and joins it to the relative
notebook path before attaching: a relative path would point the server somewhere else
entirely, and it would resolve *something* rather than fail.

Kernel slice of the `training` ws channel: client sends `open`, `run_cell`, `run_all`,
`cells` (ops: insert/edit/delete/move), `interrupt`, `restart`, `shutdown`, `watch_run`;
server sends `opened`, `kernel_status`, `execution_state`, `output` (raw nbformat output
dicts), `cells_changed`, `run_backfill`, and `error`.

## Visualizations

All four visual panes feed off the same `training` channel; the notebook (or a script
run) drives them through the `horrible_train` helper's sentinel events:

- **Metrics** (`training.metrics`, uPlot) — one streaming chart per metric of the
  selected run. `metrics.py` keeps a per-run ring buffer (`training.metrics.bufferPoints`,
  default 5000) so a chart opened mid-run backfills via `watch_run`, and coalesces the
  wire to ≤20 events/s per run while keeping every point server-side.

  **And they persist now.** They used to live *only* in that ring buffer, so they died
  with the backend process: you could fine-tune for six hours, restart the app, and have
  nothing but a checkpoint. Meanwhile [localtrack](localtrack.mdx) — the module whose
  entire job is keeping exactly this — had one producer (the evals sweep) and four
  default charts (`train/loss`, `eval/loss`, `eval/accuracy`, `train/learning_rate`)
  that **nothing had ever written**. Those are Hugging Face `Trainer` key names and
  `ht.callback()` emits precisely them, so connecting the two fills the default
  workspace on the first run.

  Three decisions about where that hook goes:

  - **In `metrics.record_event`, not in `horrible_train`.** The helper's contract is
    zero dependencies and a stdout sentinel protocol; giving it an HTTP client breaks
    the Kaggle and Colab push, which run it on someone else's machine.
  - **Not through `report_to`.** That is a Hugging Face field with known integration
    names — an unknown one is a runtime error, not a no-op. `ht.callback()` is already
    additive and installed regardless of `report_to`, which is exactly why it is the
    right carrier. `localtrack` is deliberately *not* added to `recipes.TRACKERS`.
  - **Every point, not the coalesced wire.** The wire drops intermediates at 20/s
    because a chart cannot draw faster; a store has no such excuse, and a loss curve
    missing 90% of its points is not the curve.

  The localtrack project is the **training project's id**, so each project keeps its own
  run history — deliberately unlike the evals sweep, which files everything under one
  hardcoded `evals` project. The mirroring itself is
  `localtrack.mirror.RunMirror`, shared with that sweep so the swallow-everything
  posture cannot drift between two copies.

  One honest limit: the helper emits no "finished" event and kernel lifecycle lives in
  shared `notebook_core`, so a run is marked finished when a **new run supersedes it**
  for the same project, or at backend shutdown. A run whose process merely died stays
  `running` until the next one starts — visible in the pane, and better than guessing
  from a timeout.
The four panes below are declared **`embedded`**: they are companion strips of the
notebook they ride on, reached with their region keys or the `Training: Open …`
commands (which reveal the strip rather than opening a pane). `training.metrics` is
deliberately **not** — it is seeded as the Training workspace's own center pane, so it
is a destination in a way the others are not. See [Embedded views and sections](../architecture/windowing.mdx#embedded-views-and-sections).

- **Architecture** (`training.modelgraph`, dagre SVG) — the layer graph from
  `horrible_train.watch(model)`: `torch.fx` topology (with tensor shapes when an
  `example=` input is given), or the `named_modules` tree when the model isn't
  traceable. With `weights=True`, per-layer gradient norms color-map the nodes live
  during training (`model_stats` events).
- **Rollout** (`training.rollout`) — the latest `frame` event as an `<img>`,
  rAF-throttled with an fps readout; gym envs stream via `horrible_train.frame(env.render())`.
- **Manim** (`training.manim`) — plays the mp4 a render produces (`manim_status`
  progress lines + `manim_done {url}`), served by the media route.

## Runners

Two subprocess runners live outside the kernel (both Popen-on-thread, sentinel-parsed,
process-global so they survive pane/tab closes):

- **Script runner** (`runners/script_runner.py`) — `python -u <script>` in the project
  venv; `ht.log()`/`ht.frame()` in the script are indistinguishable from notebook cells.
  Driven by `POST/GET/DELETE /projects/{id}/runs`.
- **Manim runner** (`runners/manim_runner.py`) — `python -m manim render` against a
  scene file under `media/scenes/`; auto-installs manim into the venv on first use;
  locates the newest mp4 and serves it via the traversal-guarded media route.

## Cloud push

A `PushTarget` driver layer (`push/`, same shape as the provider layer) sends a
project's `main.ipynb` to cloud compute:

- **Kaggle kernels** (`push/kaggle_push.py`) — generates `kernel-metadata.json`
  (competition/dataset sources drawn from the project's Kaggle refs, `enable_gpu`),
  then `kernels_push`; `status` polls `kernels_status`. Competition *submissions* stay
  manual (`kaggle competitions submit …` in the terminal pane).
- **Google Colab** (`push/colab_push.py` + `google_auth.py`) — Colab has no API, so the
  notebook uploads to Drive with the Colab mimetype; the file id is remembered
  (`.push-colab.json`) so re-pushes update in place. OAuth uses the user's own client
  (settings `training.google.clientId/clientSecret`), manual-code flow, refresh token in
  `.data/training_google_token.json` — **never** returned to the client.

## Peer fabric (advertise + manual handoff)

Training compute is shared across the distributed [network](network.mdx) fabric without
any remote-execution engine in v1: a node **advertises** that it's offering GPU or
seeking help, matches surface in the UI, and the actual handoff is a normal collab/agent
chat.

- `fabric.py` registers a `training_ad` handler on the `PeerHub` at network startup.
  Received ads are validated into `TrainingAdModel`, **pinned to the sending session's
  node id** (a peer can't advertise on another node's behalf), stored, and fanned to
  every browser on the `training` channel (`training_ad` event). A `status: "none"` ad
  retracts.
- `specs.py` snapshots hardware for the ad — platform/CPU/RAM from the stdlib, GPU via
  `nvidia-smi` (no torch in the backend env); a node with no NVIDIA GPU simply
  advertises none.
- Advertise mode is settings-driven (`training.fabric.advertise`: off | offering |
  seeking, plus `training.fabric.note`). Changing it re-broadcasts to peers; a new peer
  connecting (`peer_update`) triggers a re-send so late joiners see the ad.
- The `training.peers` pane shows ads with **match highlighting** (their offering ×
  my seeking, and vice versa) and an "Open chat" button that opens the network module's
  peer-chat pane — module boundary respected via `registry.openPanel('network.chat')`.

## Agent integration (the flagship)

Typing *"i want to work on kaggle's pokemon tcg competition"* into the ask bar drives
the whole flow. Two tool groups make this work, both **progressively disclosed** (loaded
on demand or by keyword) so they don't bloat the model's tool budget:

- **`training` — backend tools** (`agent_tools.py`, registered into the backend-sdk
  registry via `register_agent_tools()`, called from `app.py`). Server-resolved, so they
  run with no tab attached: `training.search_environments`, `resolve_environment`,
  `list_projects`, `project_status` (read-only); `create_project`, `fetch_data`,
  `install_deps`, `start_run`, `stop_run`, `push`, `render_manim` (side-effecting, gated
  by the agent permission engine with a `specifierTemplate` like `{provider}:{ref}`).

  Plus the two that close the loop: `training.list_checkpoints` (read-only — checkpoint
  names are not guessable, so this is the call before the next one) and
  `training.convert`, which turns a checkpoint into a GGUF in llama.cpp's managed
  directory. `convert` drains the conversion's NDJSON stream and reports only the
  outcome: the route streams it so a pane can show a progress log, but an agent has
  nowhere to put hundreds of progress lines and would pay for every one in context. It
  takes minutes and is deliberately *not* backgroundable the way `start_run` is —
  there is no id to poll afterwards, the answer **is** the output path.
- **`training` — frontend tools** (`agentTools` on the `training.notebook` panel). Full
  cell CRUD + execute against the pane's session store: `training.list_cells`,
  `read_cell`, `kernel_status` (read-only); `insert_cell`, `edit_cell`, `delete_cell`,
  `run_cell` (waits ≤120s, returns outputs/traceback), `run_all`, `interrupt`, `restart`.

  These were `notebook.*` until they collided with the [reactive notebook](notebook.mdx),
  which declares the same seven verbs against a different store with a different session
  argument (`path`, not `projectId`). The frontend resolves a tool call by name with
  `find` and this module registers first, so *these* won and the reactive notebook's were
  unreachable — silently, decided by registration order in `main.tsx`. They are grouped
  by name prefix, so moving them to `training.*` both ends the collision and files them
  with the rest of this module. A `duplicateToolNames` check in the manifest now logs any
  recurrence, and stored permission rules naming the old tools are migrated on load
  (`permission_store.rename_in_rule`) — a `notebook.run_cell` grant was a grant over
  *this* notebook, and must follow the tool rather than the name.

The orchestrator changes are generic (`backend/modules/agent/orchestrator.py`): `AgentTool`
gained an optional `group` field (`backend/sdk/types.py`) — `None` keeps a plugin tool in
the always-loaded core (unchanged), a set group moves it into the progressive-disclosure
pool. `_GROUP_KEYWORDS` preloads `training` on "kaggle/train/dataset/gym/…" and `notebook`
on "notebook/cell/kernel/…". Now that the cell verbs are `training.*`, this flow needs
only the one group — but a prompt naming both notebooks preloads both, and with the cell
tools counted in `training` that is over `TOOL_BUDGET`; see the note below.
`open_pane` now accepts optional `params`, so the agent opens the notebook pane bound to a
project (`open_pane("training.notebook", {params: {projectId, notebook}})`).

**Flow**: keyword-preload `training` → `search_environments` → `create_project` (approval
gate, specifier `provider:ref`) → `fetch_data` → `open_pane(training.notebook, params)` →
`split_area` for the metrics pane → `training.insert_cell`/`run_cell` to build the
starter. Verified end to end against a live Ollama model: the ask reaches
`training.create_project`, the gate fires with the right specifier, and on approval the
project + scaffolded notebook land on disk.

### Open: the two groups no longer fit together

This flow used to span `training` (12) + `notebook` (10 cell verbs) on top of an 11-tool
core. With the cell verbs moved, the flow is one group of 22 and needs `notebook` not at
all — strictly better. But a group's own name is an implicit preload keyword, so the
phrase "training notebook" still preloads **both**: 11 + 22 + 9 = 42 against a
`TOOL_BUDGET` of 38, and the backstop drops the last four (loudly — it logs them at
ERROR — but it drops them).

The budget deliberately sits under the ~40-tool reasoning cliff, so raising it is not the
answer. The real options are to split `training` (project/venv/run management is a
different job from cell editing), or to merge the two notebooks behind one tool set with
a target argument. Both are larger than the rename and neither is done.

## The fine-tuning workspace

The `training` preset (🧠) is the whole loop in one frame — write the recipe, run
it, watch the curves, convert the checkpoint, score it — rather than five panes
opened one at a time from the command palette.

```
┌──────────────┬───────────────────────────────┬──────────────────┐
│ Training     │  (document area — empty)      │ Training Metrics │
│ Projects     │  notebook · recipe land here  │ LocalTrack       │
│ Explorer     ├───────────────────────────────┤                  │
│              │  Evals · llama.cpp            │                  │
└──────────────┴───────────────────────────────┴──────────────────┘
                 Observability (bottom, closed)   Agent chat (right)
```

The pairing that carries the idea is **evals directly under the notebook**: a
regression in Results names a case, and the code that produced it is one pane up.
`llamacpp.server` shares that lower area because converting a checkpoint and
serving it to be scored are the same errand, and the right column is where a run is
*watched* — `training.metrics` live, `localtrack.workspace` for comparing it against
previous runs.

The document area is seeded **empty** on purpose. `training.notebook` and
`training.recipe` are params-bound (`{projectId, notebook}`) and a preset's `tabs`
carry no params, so seeding them would open two panes reading "No project — open me
from the Training projects pane". Which is exactly why that pane is *first* in the
left dock: it is the entry point, and what it opens lands in the empty area.

A preset that names a view the registry does not have is **skipped in silence**
(`seedFromPreset`), so a typo is a pane that simply never appears — pinned by
`workflow-presets.test.ts`, which seeds the preset against the real ids and against
none at all and requires the two to differ.

### It opens as the fine-tuning agent

`agent: 'trainer'` — the workspace switches the persona and the tool scope, not just
the furniture. The roster spec permits `training`, `evals`, `localtrack`, `editor`
and `files`, and **preloads only `training`**, so reading a recipe costs a
`load_tools` rather than schema space on every turn.

`llamacpp` **now appears in that list, and used not to.** The original reasoning was
right: a group is a tool name's prefix (`_group_of`), the `llamacpp.*` namespace held
only *settings* keys (`llamacpp.diskBudgetGb`), and listing it would have silently
permitted nothing at all — the same trap the connectors rule names when it says a
connector id must equal its tool prefix.

That stopped being true the moment [llama.cpp](llamacpp.mdx) grew real agent tools.
Without the group this agent could convert a checkpoint and then had no way to serve
it, which is the step immediately before the eval its own prompt tells it to run. It
is permitted but **not preloaded** — this flow already sits close to `TOOL_BUDGET`.

`hardware` still does not appear, for the original reason: settings keys only.
