# Module: browser

An **embedded web browser** pane: a URL bar, back/forward/reload/home, and a page
rendered inline. It works in **both** layouts (the `apps/web` browser build and the
Tauri desktop build) with no per-platform fork — behavior branches on a
[capability](../architecture/layout-shell.mdx), never a `__TAURI__` check.

It has **three rendering engines**, selected by the `browser.engine` setting:

- **iframe** (default, always available) — the page renders in a cross-origin
  `<iframe>`. Light and zero-dependency, but opaque: we can't read the DOM, persist
  cookies, or let the agent act on the page, and most large sites send
  `X-Frame-Options` / CSP `frame-ancestors` and **refuse to be framed** (undetectable
  cross-origin). So the module always offers manual escapes rather than guessing.
- **full** — a **real headless Chromium** (Playwright) driven on the local backend and
  **server-rendered** to the pane: JPEG frames stream over `/ws`, and interactions
  (click/scroll/type/navigate) relay back — the same pattern
  [vizdoom](./games.mdx) and the [visualizer](./visualizer.mdx) use. Because the backend
  runs on the **user's own machine** (never a shared host), a server-side browser fits
  the app's trust model, and the server holding the **live DOM** is what makes the
  browser inherently agentic (the agent is handed content + an accessibility snapshot and
  can scrape/click/type). Opt-in and gated — see [Full engine](#full-engine-real-chromium).
- **native** (desktop only, `browser.nativeWebview`) — a **real child webview** the Tauri
  shell composites over the pane's rectangle: an actual browser, with tabs, downloads,
  devtools, saved passwords and a real Edge fingerprint. Fastest of the three by a wide
  margin (no frame encode, no decode, native scrolling, input, clipboard and IME) and no
  site can refuse it. The price is that it is **not part of the HTML layer**: the OS
  paints it above everything the app draws. On **Windows** the agent drives it directly
  over an in-process CDP bridge (`browser.nativeCdp`); elsewhere the agent cannot read
  it. See [Native webview overlay](#native-webview-overlay-desktop).

`auto` (the default) resolves per host:

| Host | `auto` picks | Why |
| --- | --- | --- |
| Desktop, Windows (`browser.nativeCdp`) | **native** | The real browser, and the agent's tools act on the page shown |
| Desktop, macOS/Linux | **full** if enabled, else **native** | The native view isn't agent-drivable there; full keeps human and agent on one page |
| Browser build | **full** if enabled, else **iframe** | No native shell |

The rule underneath: never show the human one page while the agent's tools act on
another. On Windows the native view satisfies that, so it wins; where it can't, full
does.

## Contributions to the layout shell

- **Panels:** `browser.view` (role `document`, **non-singleton** — open as many tabs
  as you like, icon 🌐).
- **Commands:** `browser.open` (Browser: New tab), `browser.focusUrlBar`
  (Browser: Focus URL bar).
- **Keybindings:** `mod+l` → `browser.focusUrlBar`, **scoped** to `browser.view` so it
  only fires in a focused browser pane and never shadows a global shortcut.
- **Settings:** `browser.homePage` (URL for the Home button; blank shows a start page),
  `browser.readerModeDefault` (open every page in reader mode), `browser.engine`
  (`auto` | `full` | `native` | `iframe` — the rendering engine, see above), and
  `browser.saveLibrary` (which library 📥 Save files into).

## The pane

The iframe is cross-origin, so navigation history can't be read from it — the pane
keeps its **own per-instance back/forward stack**. The URL bar accepts a bare host
(prefixed to `https://`) or a search query (routed to a search engine). Bookmarks and
history persist server-side (see below).

**Escaping a site that refuses framing** — always available, no fragile detection:

- **▤ Reader** — server-side reader mode: the backend fetches the page and returns its
  extracted text, rendered inline. Works for any site in any build.
Two more affordances appear in **full mode only**, since both need the live DOM /
backend Chromium that an iframe can't give: **📥 Save**
([to the library](#saving-to-the-library)) and **📡 Network**
([what the page is talking to](#network-observability)).

- **⧉ Pop out / Open tab** — on **desktop** (capability `browser.nativeWindow`) opens
  the URL in a **real native window** (a true browser, bypassing X-Frame-Options
  entirely) via the `WindowControl.openBrowserWindow` seam → the Tauri `browser_open_url`
  command (`apps/desktop/src-tauri/src/window.rs`, http/https only). In the **browser**
  build the seam is null, so it falls back to `window.open` (a new tab).

## Agent tools

The panel declares `agentTools`, so the agent orchestrator can use the browser (pushed
to the backend in the capability manifest whenever the module is registered — always
available, not tied to an open pane).

**Which browser they drive** is decided per call (`engines.ts`):

1. **The native pane the human last used**, when one is open (Windows desktop). Agent and
   human share one real page: the agent's clicks happen in front of the user, who can
   take over mid-task. Over the [CDP bridge](#the-cdp-bridge-windows).
2. **The backend's headless Chromium**, when the full engine is enabled
   (`/api/browser/engine`) — the web build, or the desktop with no native pane open.
3. **Neither** — `browser.read` falls back to a server fetch; the others say to
   `browser.open` a page first.

Both engines evaluate **the same page scripts** (`backend/modules/browser/scripts/`,
served to the native one by `GET /api/browser/scripts`), so a snapshot ref means the same
element on either.

The tools are shaped for the loop real browsing agents use (Playwright MCP, browser-use,
Claude in Chrome): read the page as a numbered list of interactable elements, act on one
by ref, and get the **new** snapshot back in the same result — the agent never acts on
refs from a page that has since changed, and never pays a round trip just to look again.

- **`browser.read`** (read-only) — return a page's readable text (title + extracted
  content, capped). This is how the agent **reads / researches the web**. With a live
  browser it navigates it and reads the post-JS DOM (omit `url` to read the page already
  open); otherwise it runs the SSRF-guarded `/api/browser/read` fetch, so the agent
  can't reach internal services. Read-only, never permission-gated.
- **`browser.open`** (side-effecting) — open a page in the browser pane so the user can
  see it, and make it the page the other tools act on. On Windows it drives an open
  native pane in place (bringing it forward), or opens one and returns once it has
  loaded. Gated by the permission engine via a `{url}` specifier.
- **`browser.snapshot`** (read-only) — the page's **on-screen interactable elements**,
  each with a numeric `ref`, `role`, accessible `name`, and `value` (a tagged
  accessibility snapshot via injected JS). The agent's "what can I click?" affordance.
  When the page shows a CAPTCHA or bot check it adds `challenge: true` and a note
  telling the agent to hand the page to the user — it must not try to solve it.
- **`browser.click{ref}`** / **`browser.type{ref,text,submit?}`** (side-effecting) — act
  on an element by its snapshot `ref`; `type` replaces the field's contents and
  `submit` presses Enter after. Both return the page afterwards.
- **`browser.press{key}`** (side-effecting) — one key on whatever has focus (`Enter`,
  `Tab`, `Escape`, arrows, …). **`browser.scroll{direction,screens?}`** (read-only)
  and **`browser.back`** (side-effecting) complete the loop: snapshot only lists what is
  on screen, and a wrong click needs a way back. All return the page afterwards.
- **`browser.scrape{selector}`** (read-only) — pull structured data (text / href /
  outerHTML, capped) for every element matching a CSS selector.
- **`browser.media`** (read-only) — the page's images and videos, each with its `src`,
  alt text, caption, and surrounding context, plus a `described` flag saying whether
  `browser.save` would accept it.
- **`browser.save{target,src?,library?,tags?}`** (side-effecting) — file the page
  (`target: "page"`), one media item (`"media"` + `src`), or every described asset
  (`"allMedia"`) into a [library](./library.mdx). See
  [Saving to the library](#saving-to-the-library).

`browser.read` + `browser.save` are the **write half of RAG** — `library.search` is the
read half. Without `save`, the agent can read the whole web and remember none of it.

Parameterized actions have to be `agentTools` rather than agent-exposed commands here,
because agent commands currently ignore their args (see
[agent tools](../architecture/agent-tools.mdx)).

## Saving to the library

The browser is where the app meets the web, so it's where things worth keeping are
found. **📥 Save** (full engine only) files the open page or its media into a
[knowledge library](./library.mdx), where it's chunked, embedded, and semantically
searchable. The human button and the agent's `browser.save` both go through
`packages/core/src/modules/browser/capture.ts`, so a page saved by hand and one saved by
the agent are the same kind of source.

- **The page** → a `page` source: the new `capture` op archives the live
  **post-JS DOM** as one self-contained HTML artifact (images/CSS inlined as
  `data:` URIs, scripts stripped, stored server-side in the
  [artifact store](research.mdx#the-artifact-store)) and the source points at it —
  openable offline in the research module's Page Viewer. Subresources are fetched
  with the session's own cookies, under the same per-hop public-host egress
  policy as navigation. If the op fails (older backend, mid-navigation), Save
  falls back to the previous behavior — a `blog` source the backend re-fetches
  and text-extracts.
- **Images / videos** → `image` / `video` sources.

The `capture` op now takes two flags, used only by the
[doc viewer](./docviewer.mdx): `keep_scripts` preserves the page's JavaScript
instead of sanitizing it away, and `store=False` returns the built HTML rather than
filing it (the doc crawler rewrites intra-set links before the bytes are final, and
the artifact store is content-addressed, so storing first would store every page
twice). A scripted archive records `meta.scripts`, which is what makes the byte route
serve it `sandbox allow-scripts` — an opaque origin with no network of its own. It
also fetches and inlines every `<script src>` (a tag whose bytes were never fetched
would point at a URL the archive is not allowed to load, and fail silently) and
injects an in-memory storage shim, because reading `localStorage` in an origin-less
document throws. A page saved from **this** pane is unaffected: Save leaves both
flags off, so what it files stays inert.

The same session type also backs that crawl headlessly:
`browser_manager.open_headless(key)` starts a `BrowserSession` over a null socket
with the screencast off, so a crawl gets this module's Chromium, egress guard and
capture path without encoding frames for a viewer that does not exist.

### Why media is stored by reference and description

The app's embedder is **text-only** (`backend/modules/database/embeddings.py` — a
provider call with a deterministic hash fallback). There is no multimodal model, so an
image cannot be turned into a vector directly. Two consequences shape the design:

1. **Media is embedded by proxy.** An asset becomes searchable through the words around
   it — alt text, `<figcaption>`, the nearest heading, the page title. The `media` op
   harvests those from the **live DOM**, which is the only moment they're cheaply
   available: by the time a URL reaches the ingest pipeline, the context is gone. The
   proxy text is deduped before embedding, because the same string routinely arrives as
   alt *and* title *and* caption, and embedding it three times skews the vector.
2. **An undescribed asset is rejected, not stored.** A spacer GIF with no alt text has
   nothing to match on; storing it would put a row in the store that no query can ever
   reach. `browser.save` returns an error explaining why, and the Save popover greys the
   item out rather than hiding it — a silent drop looks like a bug.

Both of these are consequences of a text-only embedder, and
**[CLIP visual search](./library.mdx#visual-search-clip) removes the second one**: with
it enabled the pixels themselves are indexed, so an undescribed image is savable and
findable, description becomes a bonus rather than a requirement, and the Save popover
shows a 👁 marker with the item labelled *indexed by appearance*. `browser.media`
reports both `described` and `savable` per item so the agent knows which applies.

The **bytes are never copied**: a source holds an `asset` descriptor (`src`, `page_url`,
dimensions, caption) and the client renders from the original URL. That also means media
ingest performs no server-side fetch, so it adds no new SSRF sink — unlike `blog`, which
does fetch (see [Security](#security--ssrf)).

CLIP is a **supplement, not a replacement** — the descriptive fields stay useful either
way, and a hit reports which space found it (`matched_by`). See
[Visual search](./library.mdx#visual-search-clip) for the two-space design.

## Network observability

A browser is the app's largest source of outbound traffic and, before this, its largest
blind spot: the pane fetched hundreds of subresources per page and **none of it was
visible**. The `_route` egress hook already saw every request — it just allowed or
aborted it and recorded nothing.

Every request the embedded Chromium makes is now recorded as an I/O event with
`source: "browser"`, alongside `inbound` / `outbound` / `ws` in the
[observability panel](./observability.mdx). Two extra axes come with it:

- **`resource_type`** — Chromium's own classification (`document`, `script`, `image`,
  `xhr`, `fetch`, `media`, …), the thing that makes a page's traffic legible at a glance.
- **`verdict`** — `allowed` or `blocked`. **A request the egress guard kills stays
  visible**, labelled with its reason. A silently aborted request is exactly what this
  pane exists to expose.

**📡 Network** (`browser.network`) is a **registered view declared as a right-hand
region strip** of `browser.view` — so it resizes, persists per pane instance, toggles
from the area header or `n`, and can be **dragged out** by its region header into a
center area of its own, where the inspector has room. The 📡 button reflects and drives
that region rather than local state. It is declared **`embedded`**, so it is not a destination of its own: no opener command, no rail glyph, no type-switcher entry, and no top-level row in the agent's `list_available_panes` — it is listed under its host, and `show` reaches it by name. See [Embedded views and sections](../architecture/windowing.mdx#embedded-views-and-sections).

- **Open connections** — requests currently *in flight*, pushed live on the `browser`
  channel as `connections` events. These exist only while unresolved, so they can't come
  from the I/O ring buffer, which (like the httpx seam) records on **completion**. This
  is the "why is this page hanging" view.
- **Completed** — finished requests read from the shared telemetry store, filtered to
  `browser`, with a text filter over method/target/resource type. Selecting one opens
  the **same `IoInspector` the observability panel uses** — general/timing/egress
  verdict, request and response headers, and bodies with JSON pretty-print and copy.
  The component is shared from `packages/core/src/telemetry-view.tsx` rather than
  duplicated: both surfaces render the same `IoEvent`, and a module reaching into
  another module's internals is what the registry conventions forbid.

## Seeing how the web actually works

The pane has four views, ordered from passive to active. **Requests** and **Waterfall**
are pure observation. **DNS** and **Route** send packets of their own, so they sit
behind a button rather than running when the pane opens.

### Connection forensics (passive, free)

Chromium *measured* far more about every request than Playwright's API exposes — and
the browser module was throwing all of it away. A DevTools-protocol session
(`backend/modules/browser/cdp.py`) recovers it, sending no extra packets:

| Field | What it answers |
| --- | --- |
| `remote_ip` / `remote_port` | Who actually answered — the thing a URL hides completely |
| `http_protocol` | `h3` / `h2` / `http/1.1` |
| `tls` | Negotiated version and cipher, certificate issuer, subject, SAN list, validity |
| `timing` | Per-phase durations: DNS, TCP connect, TLS handshake, request send, server wait |
| `from_cache` | Nothing crossed the network at all |

**Waterfall** draws those phases as one stacked bar per request on a shared time axis.
It is the most educational view in the app: a URL bar makes fetching a page look
atomic, and seeing 180ms of DNS and 90ms of TLS in front of a 40ms download explains
more about the web than any amount of prose.

Phases that didn't happen are drawn as **nothing**, not as zero-width bars. A
connection reused from the pool genuinely has no DNS or TLS phase, and that absence is
information — it is *why* the second request to a host is faster.

:::note CDP's timing format is a trap
`requestTime` is an absolute value in **seconds**; every other field is a millisecond
offset relative to it, and `-1` means "this phase did not happen". Treating that `-1`
as a duration produces negative bars with no error anywhere, which is why the
conversion is a pure, tested function rather than inline arithmetic.
:::

Correlation between CDP and Playwright is **by URL** — they identify a request
differently with no join key between them. Two in-flight requests to the same URL are
last-write-wins, which is acceptable for an inspector; the alternative is driving the
whole network stack through CDP and giving up the request interception the egress guard
is built on.

### The DNS delegation walk (active, no privileges)

**DNS** resolves a name the long way: ask a root server who runs `.org`, ask *those*
servers who runs `python.org`, and only then get an answer. Your resolver does this
once and hides it behind a cache forever.

Each rung shows who answered, in how long, the nameservers it delegated to, its **glue
records**, and whether the parent published a **DS** record — one link of the DNSSEC
chain of trust. A **CNAME** answer restarts the walk at the target name, which is
usually in a different zone entirely: `docs.python.org` turns out to be an alias for
Fastly, so the ladder continues through `.net`.

Plain UDP port 53 via dnspython, so it needs **no elevated privileges** — which is what
makes this the centrepiece rather than a footnote. Where UDP/53 is blocked it falls
back to DNS-over-HTTPS and says so: a DoH endpoint is a recursive resolver that already
did the walk, so it can answer but has no delegation to show.

### Traceroute and route plotting (active)

**Route** traces the hops between here and a host, then plots the ones it can locate on
a bundled world map.

Raw ICMP sockets need administrator rights on Windows and root on Unix, so this shells
out to the **system** `tracert`/`traceroute` and parses its output. Less elegant, but a
feature only elevated users can see is a feature most people never see. IPv6 hops are
handled: a dual-stack host traces over v6 by default and `tracert` prints those
addresses unbracketed.

A router that doesn't answer ICMP is reported as a hop with no reply rather than
dropped — the packets did cross it.

The map is an inline SVG coastline in equirectangular projection, with **no tile
provider**: a slippy map would mean an external host, an API key, and every pan leaking
the viewport to a third party — in a pane whose entire purpose is showing what leaves
the machine. Unlocatable hops are gaps in the line, never interpolated; the first hops
of any trace are your own router, and inventing coordinates for them would be fiction.

Geolocation uses **DB-IP Lite** (CC BY 4.0, freely redistributable) rather than MaxMind
GeoLite2, which requires an account and a license key. It is an optional extra:

```bash
uv sync --extra geoip
```

then download the DB-IP Lite City `.mmdb` to `$HORRIBLE_DATA_DIR/geoip/dbip-city.mmdb`.
Without it, hops still list — they just have no coordinates. Attribution is required
and is rendered in the pane.

### Probe safety

Every probe target goes through the same public-IP check as the fetch guard. Probing
internal hosts is a reconnaissance primitive, and "the user clicked it" is not a
defence when the target could have been suggested by a page.

| Route | Purpose |
| --- | --- |
| `POST /api/browser/net/dns` | Walk the delegation chain |
| `POST /api/browser/net/trace` | Trace the path to a host |
| `GET /api/browser/net/geo` | Whether locations can be plotted, and how to enable it |

:::note Scope: all browser traffic, not one tab's
The list covers **every** embedded-browser request, not just the pane you are looking
at. `BrowserManager` keys sessions by **WebSocket connection**
(`backend/modules/browser/session.py`) and the app has a single shared `/ws`, so every
`browser.view` pane drives the **same** headless Chromium and the **same page** — there
is only one stream of traffic to show. The header says "All browser traffic" rather than
implying otherwise.

`browser.view` being non-singleton is therefore misleading today: several browser panes
can be open, but they share one engine and one page. **Reproduced 2026-07-21:** with two
panes open, navigating pane B moved the shared page, while pane A went on displaying its
old URL and a stale frame — the panes do not visibly sync, they silently desync, and a
click in pane A would land on pane B's page.

The `browser.open` **agent tool** therefore routes through
[`openDocument`](../architecture/windowing.mdx) rather than `openPanel`: it reuses an
open browser pane instead of splitting a new one per navigation. An agent browsing five
pages is one session, so five panes would have been five views of the same page — four
of them stale. This narrows the desync to panes the *user* opened deliberately; it does
not fix the underlying single-page engine.

Independent tabs need **one persistent context per profile with one `page` per pane** —
not one session per pane. Two Chromium processes on the same `user_data_dir` race on the
cookie store, and separate contexts would stop your own tabs sharing a login. That is a
restructure of `_run`/`_loop_commands`/`_capture_frame`, which currently assume a single
page. Per-pane network scoping is blocked behind it.
:::

:::tip Closing one pane no longer freezes the others
The engine is shared, so `stopSession()` on one pane's unmount used to stop it for
**all** of them: `stop_for` pops the session and sets `_closing`, which kills the frame
pump, while the next request/reply op silently builds a replacement session no pane is
driving. The result was every remaining browser pane frozen on a stale frame, with no
error — `info`/`screenshot` kept working, so the engine looked healthy.

Panes now claim the shared engine with `acquireSession()`
(`packages/core/src/modules/browser/session.ts`), whose release stops Chromium only when
the **last** browser pane lets go. The release is deferred a microtask so React
StrictMode's dev-mode unmount/remount doesn't tear the engine down on every mount.
:::

### Implementation notes

- **Recorded on completion, not amended.** `Recorder.amend` needs an event id, which a
  thread-safe `call_soon_threadsafe` post can't hand back — so `_on_response` /
  `_on_request_failed` record once, and the live in-flight set is tracked separately.
- **Thread affinity.** `_route` and the request/response handlers run on the **Playwright
  worker thread**, while `Recorder` notifies asyncio.Queue subscribers and is loop-affine.
  Every hand-off is posted with `call_soon_threadsafe`; frames keep their blocking
  `_emit_threadsafe` (it backpressures the worker), but network events use a
  non-blocking send — a page fires hundreds, and stalling the worker on each would hold
  up the browser itself.
- **The verdict is stamped in `_route`.** Chromium's `requestfailed` can't distinguish
  our abort from a DNS failure, so `_route` records the reason and
  `_on_request_failed` reads it back.
- **Bodies are text/JSON only**, size-capped (256 KB). Pulling every JPEG and video
  through the ring buffer would dwarf the traffic being observed.
- Like the rest of the I/O buffer, capture is **raw** — treat it as sensitive, since it
  holds cookies and auth headers from sites you browse.

## Backend surface (`/api/browser`)

A normal backend module (`backend/modules/browser`), same shape as `library`:

- `GET /read?url=` — **reader mode**: SSRF-guarded fetch + main-content extraction
  (reuses `library.extract.extract_article`).
- `POST /extract` — the same extraction over HTML the caller already holds (the native
  pane's live DOM). No fetch, so no SSRF surface.
- `GET /scripts` — the page scripts both engines evaluate (`snapshot`, `media`), verbatim
  from `scripts/`, so the native engine never carries a stale copy.
- `GET/POST/DELETE /history` and `GET/POST /bookmarks`, `DELETE /bookmarks/{id}` — a
  SQLite catalog (`browser_history`, `browser_bookmarks`) in the shared app DB. History
  is upserted per URL; bookmarks are deduped per URL.

### Security — SSRF

`GET /read` fetches an arbitrary user-supplied URL server-side, so `fetch.py` enforces
an SSRF policy before **every** request and each redirect hop: `http`/`https` only;
resolve the host and reject if any IP is loopback / private / link-local / multicast /
reserved (blocks `localhost`, `169.254.169.254`, RFC1918, …); follow redirects manually
and re-validate each `Location`; cap response size and content type. A TOCTOU
DNS-rebind is mitigated but not fully eliminated (full protection needs pinning the
validated IP into the connection). The `library` blog ingest — which used to be the
one unguarded copy of this sink — now routes through the same guard
(`fetch_readable`), as do the research module's capture and PDF fetches; `fetch.py`
is the single egress policy for every server-side URL fetch.

## Full engine (real Chromium)

Full mode drives a **headless Chromium** on the local backend
(`backend/modules/browser/session.py`) and server-renders it to the pane.

**Engine.** One `BrowserSession` per `/ws` connection; a process-global
`BrowserManager` owns them and tears each down on disconnect (`stop_for`, wired in
`backend/app.py` alongside `visualizer_manager`). Chromium is driven via **Playwright's
_sync_ API on a dedicated worker thread**, not the async API — Windows'
`SelectorEventLoop` under `uvicorn --reload` can't spawn subprocesses via asyncio (see
`backend/modules/lsp` / the visualizer for the same constraint). The worker owns all
Playwright objects; the event loop posts commands over a queue and reads results back
through per-command futures, and frames are relayed to the loop with
`run_coroutine_threadsafe`. A **persistent context**
(`$HORRIBLE_DATA_DIR/browser/<profile>`) persists cookies, cache, localStorage,
IndexedDB, and site data across restarts.

**Frames come from CDP `Page.startScreencast`**, not a screenshot poll. Chromium pushes
a frame when the page actually *changes* rather than on our timer, encodes it inside the
browser process, and attaches the viewport geometry the panel needs. Its
`screencastFrameAck` handshake is also real backpressure: Chromium holds frame N+1 until
N is acked, so a slow socket throttles the producer instead of growing a queue. The
screencast rides the **same CDP session** as the network instrumentation.

Three things about that path are easy to get wrong and are pinned by tests:

- **`maxWidth`/`maxHeight` must equal the viewport.** Let Chromium scale the frame and
  frame pixels stop being page pixels, so every relayed click lands somewhere else —
  silently, because a downscaled frame still looks like a valid page.
- **The ack is queued by the frame handler and sent by the pump**, never sent inline.
  The handler runs on the Playwright dispatcher greenlet, where re-entering the driver
  can deadlock. For the same reason it reads `page.url` (a cached attribute) but never
  calls `page.title()` (a round trip) — the pump refreshes a cached title instead.
- **Sync Playwright only dispatches CDP events while inside a driver call**, and the
  command loop's `queue.get()` is not one. So an idle page needs `_pump` — a short
  `wait_for_timeout` that yields to the dispatcher — or frames would simply never
  arrive. This is the non-obvious cost of the sync API and the reason the loop looks
  the way it does.

If the screencast can't be armed (no CDP session, or a Chromium that rejects it) the
session falls back to the original `page.screenshot()` poll at
`_IDLE_FRAME_INTERVAL_S`, skipping byte-identical frames.

**`browser` `/ws` channel.** The session pushes `frame` events
(`{frame: <data:image/jpeg>, url, title, metadata}`), where `metadata` carries CDP's
`deviceWidth`/`deviceHeight`, `pageScaleFactor`, `offsetTop`, `scrollOffset{X,Y}` and
`timestamp` (absent on fallback-poll frames). The panel relays input back as
`navigate` / `back` / `forward` / `reload` / `click{x,y}` / `scroll{dx,dy}` /
`type{text}` / `key{key}`; agent ops (`content` / `snapshot` / `scrape` / `click_ref` /
`type_ref` / `screenshot` / `info`) carry an `id` and get a correlated `result` event —
so the frontend `session.ts` request/reply layer serves both the human panel and the
agent tools off one shared session.

**Painting.** Frames are JPEG **stills**, so the frontend decodes with WebCodecs'
`ImageDecoder` (falling back to `createImageBitmap`) and blits onto a `<canvas>` on
`requestAnimationFrame`. There is deliberately **no `VideoDecoder`**: CDP screencast
emits `jpeg`/`png` only, with no H.264/VP8 elementary stream for it to accept. An
OffscreenCanvas worker would buy nothing either — the expensive half (JPEG decode) is
already off-thread in both APIs, and the remaining half is a GPU blit.

Two rules the pipeline depends on: **only the newest frame matters** (a frame arriving
mid-decode replaces the pending one rather than queueing, so a slow decode drops frames
instead of accumulating latency), and **every decoded frame must be `close()`d** —
`ImageBitmap`/`VideoFrame` hold GPU memory that GC does not promptly reclaim, and
leaking one per frame exhausts it in minutes.

**Viewport & coordinates.** The viewport is **not fixed**: a `ResizeObserver` on the pane
pushes its real size through the `resize` op to `page.set_viewport_size` (debounced —
each resize costs a Chromium relayout plus a screencast restart, since `maxWidth`/
`maxHeight` are fixed at start time). Sizes come from a `getBoundingClientRect()` in the
browser, so the backend **clamps** rather than trusts them: a collapsed pane reports 0,
and nothing upstream should be able to ask Chromium for a 60000px surface. Clicks are
then scaled against the **frame's own** `deviceWidth`/`deviceHeight`, which keeps the
mapping correct through a resize even before the next frame lands.

**Keyboard.** The viewport takes `keyboard` [capture](../architecture/keybindings.mdx#input-capture)
while focused: unmodified keys go to the remote page (this is a browser — `t` has
to type a `t`), while `mod+`/`alt+` chords still reach the shell so the palette and
the pane verbs keep working. Without capture the app's plain-letter bindings fired
*alongside* the keystrokes being relayed, so typing into a remote page toggled
region strips.

### Gating & security

A backend Chromium makes **real network requests to any host**, including the user's
own localhost / LAN / cloud-metadata. Even on the user's machine, a hostile page or a
misused agent tool could pivot inward, so full mode is:

- **Opt-in**: `HORRIBLE_ENABLE_SERVER_BROWSER=1` (mirrors `GAMES_ENABLE_CODE_EXEC`). Off →
  the panel stays in iframe mode and the full-engine agent tools return a "not enabled"
  notice. `GET /api/browser/engine` reports `{enabled, installed}`.
- **Egress-guarded**: every request is routed through Chromium's `context.route` and
  aborted if its host resolves to a private / loopback / link-local / reserved IP
  (reusing `fetch._check_host_public`, resolution cached per host). `file://` and other
  non-`http(s)` schemes are blocked; `data:` / `blob:` / `about:` pass. Navigation
  re-checks the scheme + host. `browser.eval` (arbitrary in-page JS) is behind the same
  gate.
- **Bounded**: one context per connection, released on disconnect / pane close.

### Dependency & cross-platform

Playwright is an **optional extra** (`browser-engine`), lazy-imported like the
`games-native` ViZDoom extra, so the core app installs everywhere without it:

```bash
uv sync --extra browser-engine
uv run playwright install chromium   # one-time, ~150 MB, prebuilt per-OS
```

The main backend isn't containerized (it runs on the user's machine), so there's no
Dockerfile change. Without the extra, `GET /api/browser/engine` reports
`installed: false` and the panel stays iframe-only.

## Native webview overlay (desktop)

`browser.nativeWebview` renders a page in a **real child webview** that the Tauri shell
parks over the pane's rectangle (`apps/desktop/src-tauri/src/webview.rs`;
`NativeBrowserView.tsx` is the frontend half, and renders nothing but a placeholder
`<div>`). No iframe restrictions, no frame encode or decode, native scrolling and input.

It is built on Tauri's multi-webview API (`Window::add_child`), which is gated behind
the crate's **`unstable` feature** — so `tauri` is pinned to `~2.11` rather than floating:
an overlay that stops compiling is better than one that quietly changes behaviour.

**The overlay is not part of the HTML layer.** The OS composites it *above* everything
the frontend draws, and no z-index reaches it. That is the defining property of the
approach, not a bug to be fixed, and it drives the whole design:

- Geometry must be **pushed, not inherited**, and *position* is the half with no
  event to listen for. `ResizeObserver` fires on size; `scroll`/`resize` fire on the
  viewport. Dragging a desktop window moves the placeholder without any of them — the
  rect changes every frame and nothing announces it — which left the overlay parked
  where the window used to be while the pane slid out from under it. So the geometry
  watcher **samples** the rect instead: an animation-frame loop while anything is
  moving (woken by the observers *and* by any pointer gesture, so tracking starts on
  the drag's first frame), backing off to a 250 ms poll once it has been still for
  ~20 frames. The poll is the backstop for movement no event covers at all — a layout
  written straight to the store, or a pane moved by an agent tool.
- Anything drawing over that region must **claim suppression** via
  `suppressNativeOverlays()` (`packages/core/src/modules/browser/overlay.ts`), which
  hides the overlay for as long as it's held. The command palette does this; **any new
  full-window UI should too**. The registry is reference-counted so a dropdown closing
  inside a modal doesn't un-hide it early.
- **Anything else on top is caught by hit-testing.** On a floating desktop, raising or
  dragging another window over the browser fires no event on the pane, and the page
  used to paint over the window in front of it. So the region is hit-tested every
  250 ms and on every pointer release (`document.elementFromPoint` on a 3x3 grid inset
  12 px from the edges): when something else is topmost inside it, the page's photo,
  which is plain HTML and so obeys z-order, takes the surface's place until the pane
  is uncovered. This is also the backstop for UI that forgets to suppress.
- **Invisible is not unmounted.** A pane on a non-visible workspace still owns its
  native surface, which would otherwise float over whatever replaced it — so an
  `IntersectionObserver` and `visibilitychange` hide it as well, and **unmounting the
  component hides it too**. That last one is not the same as closing it (the page and
  its session survive — see the lifetime note below): the component unmounts while its
  pane lives on whenever the pane switches to reader mode or another engine, and a
  surface left visible then floats over its replacement, which reads exactly like a
  frozen page that cannot be closed.

Lifetime is the **pane's**, not the component's. A workspace switch unmounts panes (see
[`unmount-is-not-close`](../architecture/layout-shell.mdx)), and destroying the webview
there would drop the user's page, scroll position and logged-in state — so
`BrowserPanel`'s pane session ties `close_browser_webview` (one per tab) to the pane
actually closing. A remount **re-attaches** to the live surface rather than calling
`create_browser_webview` again: create on an existing webview navigates it, which is a
reload that throws the user back to where the tab started.

The one path with no owner is a **frontend reload**: it destroys every pane session
while the OS window and its children live on, leaving overlays composited over the app
that no pane will ever hide or close again. `close_all_browser_webviews` sweeps them,
called once at boot before any pane mounts (`apps/web/src/main.tsx`). Nothing is lost —
a pane still in the restored layout re-creates its own surface on mount.

Only `http`/`https` URLs load, enforced in Rust: a child webview steered at
`file:`/`tauri:` would run against local resources with app privileges. All six commands
are `async` because `add_child` dispatches to the main thread and blocks on the reply —
a sync command already runs there and would deadlock the app.

**A menu over the page shows a photo of it, not a hole.** With the CDP bridge, the tab is
photographed (`Page.captureScreenshot`, within a 150 ms budget) before suppression hides
the surface, and the photo stands in until it comes back. Without the bridge (or past the
budget) the region is blank while hidden, as before.

### Tabs, downloads, devtools, logins

- **Tabs.** Each tab is its own child webview (`<paneId>:<tabId>` to the shell), so a
  background tab keeps its page, scroll and form state. The tab list lives in the
  pane's session, not React state, so a workspace switch keeps it. The shell reports
  what pages do on their own as `browser-webview` events (`webview.rs`): **loads** keep
  the URL bar honest when a link is clicked *inside* the page, **titles** label the
  tabs, and **`target=_blank` / `window.open(url)` open a tab** here. A popup that asks
  for a size or position is let through as a real window instead — OAuth and payment
  flows post their result back through `window.opener`.
- **Back/forward** read the tab's real history over CDP (`Page.getNavigationHistory`) on
  Windows; elsewhere a per-tab stack built from load events stands in.
- **Downloads** land where WebView2 puts them by default (the user's Downloads folder,
  with its own progress flyout); the pane shows a status line with *Show folder*.
- **Devtools**: F12 inside the page, the toolbar button, or the `browser.devtools`
  command. Enabled on the browser webviews only. On Windows that includes release
  builds, through WebView2's own `OpenDevToolsWindow`. On macOS and Linux the
  inspector is Tauri's `Webview::open_devtools`, which only exists in debug builds
  (or with Tauri's `devtools` feature, which this crate does not enable), so a
  release build answers the command with an error. Calling it unconditionally broke
  every non-Windows release build of v0.4.0.
- **Logins**: cookies persist in the WebView2 profile, so sites stay signed in across
  restarts, and password autosave + form autofill are on. The child webviews share the
  app window's WebView2 environment (Tauri creates them in it), so site data lives in
  the app's WebView2 user-data folder.

### The CDP bridge (Windows)

`browser.nativeCdp` (`apps/desktop/src-tauri/src/browser_cdp.rs`) gives the frontend the
Chrome DevTools Protocol **in-process, scoped to one webview**:
`ICoreWebView2::CallDevToolsProtocolMethod` for calls and
`GetDevToolsProtocolEventReceiver` for events (re-emitted as `browser-cdp`). The agent's
native engine (`native-engine.ts`) is built on it: `Runtime.evaluate` runs the shared page
scripts, `Input.dispatchMouseEvent` / `insertText` / `dispatchKeyEvent` act (trusted
events — `isTrusted` is true, which sites guarding against scripted clicks check), and
`content` posts the live DOM to `POST /api/browser/extract`.

**Why not `--remote-debugging-port`.** A debug port is a local TCP listener that hands
*every* webview in the process — the app's own UI, its origin and the tokens it holds —
to any program on the machine. The in-process API reaches one webview and nothing outside
the process can call it.

The frontend is trusted but not given the whole protocol. Methods are allowlisted:
`Page`, `Runtime`, `DOM`, `Input`, `Accessibility`, and `Network.enable/disable/
getResponseBody`. Events: `Page`, `Runtime`, `DOM`, `Network`. Refused: `Browser.*`
(the browser process), `Target.*` (attaching to other targets, the app included),
`Storage.*`, `Fetch.*` (interception), `Security.*`, and `Emulation.*` — fingerprint
overrides are exactly what bot walls look for. `Page.navigate` keeps the http(s)-only
guard. Calls run on the webview's UI thread (WebView2 ignores them anywhere else) and
reply over a channel.

macOS (WKWebView) and Linux (WebKitGTK) have no CDP, so the capability is Windows-only;
there `auto` keeps preferring the full engine.

## Browser vs desktop

| | Browser build | Desktop (Tauri) |
| --- | --- | --- |
| Inline framable sites | ✅ iframe | ✅ iframe |
| Reader mode (any site) | ✅ | ✅ |
| Full Chromium engine (any site, live DOM, agentic) | ✅ (gated + extra) | ✅ (gated + extra) |
| Native in-pane webview (any site, fastest, tabs, downloads, logins) | ❌ | ✅ (`browser.nativeWebview`) |
| Agent drives the page the human sees | full engine only | ✅ native on Windows (`browser.nativeCdp`); full elsewhere |
| Blocked-site escape (iframe mode) | Open in new tab (`window.open`) | **Native browser window** (`browser.nativeWindow`) |

The full engine renders **the same backend Chromium** in both builds, so it's the general
answer to framing-blocked sites in the browser build and on macOS/Linux. On Windows the
native pane is the browser, for the human and the agent alike; the native-window pop-out
remains an iframe-mode escape hatch.

## Known limitations / future

- Frames are **not HiDPI**. The screencast captures at the CSS-pixel viewport, so on a
  2× display the image is upscaled and soft. The fix is a `deviceScaleFactor` on the
  context plus `Emulation.setDeviceMetricsOverride`, which needs the click mapping to
  learn the difference between CSS and device pixels — currently they're assumed equal.
- Frame streaming is now paint-driven (CDP `Page.startScreencast`) rather than polled,
  but it's still JPEG stills over a JSON socket: `WsConnection` has no binary path, so
  every frame pays base64's ~33%. A real encoded stream would need server-side H.264
  (PyAV/ffmpeg) and a licensing call, and was deliberately not taken. Chromium is heavy,
  so full mode stays bounded (one context per connection, released on disconnect).
- Deferred full-engine work: in-pane **tabs** (multiple pages per context — the native
  pane has them), a smart URL
  bar / start page with favicons & titles, a history/bookmarks manager, and
  multi-profile switching.
- Media search is proxy-text only **unless [CLIP visual search](./library.mdx#visual-search-clip)
  is enabled** — without it, an image with no alt text, caption, or nearby heading can't
  be saved at all (its only index would be a filename). With CLIP on, the pixels become
  the index and 📥 accepts it. OCR and video transcripts are still not done; video is
  embedded from its poster frame only.
- Saved media is stored **by reference**: if the origin removes the asset or it sits
  behind auth, the library keeps a searchable record pointing at a URL that no longer
  renders.
- The network view covers the **full engine only** — an iframe's requests are made by
  the user's own browser and are invisible to the backend.
- Iframe-block detection is best-effort; in iframe mode the manual escapes are always
  shown rather than auto-triggered.
- The **native pane** is agent-drivable on Windows only, and is **invisible to the
  network view** on every platform: the strip reads the backend session's telemetry.
  The bridge already forwards `Network.*` events, so feeding them to the strip is the
  remaining work. Saving a native page files its extracted text (`blog`), not a
  self-contained archive — `capture` re-fetches subresources with the *backend*
  session's cookies, which a native page doesn't have. The native pane also rides
  Tauri's `unstable` multi-webview, so a Tauri upgrade needs it re-checked.
- The agent tools can't hand the model a **screenshot**: tool results reach the model
  as text, so a vision fallback for canvas-heavy pages needs image support in the tool
  relay first.
- Full-window UI should still call `suppressNativeOverlays()`: the occlusion check
  catches anything it misses, but only on its next 250 ms poll, so an unsuppressed
  modal shows the page over it for a moment first.
- Not to be confused with the external **Claude-in-Chrome** automation, which drives the
  user's *real* Chrome; this module renders pages *inside* the dashboard.
