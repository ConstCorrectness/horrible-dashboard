# Module: browser

An **embedded web browser** pane: a URL bar, back/forward/reload/home, and a page
rendered inline. It works in **both** layouts (the `apps/web` browser build and the
Tauri desktop build) with no per-platform fork — behavior branches on a
[capability](../architecture/layout-shell.mdx), never a `__TAURI__` check.

It has **two rendering engines**, selected by the `browser.engine` setting:

- **iframe** (default, always available) — the page renders in a cross-origin
  `<iframe>`. Light and zero-dependency, but opaque: we can't read the DOM, persist
  cookies, or let the agent act on the page, and most large sites send
  `X-Frame-Options` / CSP `frame-ancestors` and **refuse to be framed** (undetectable
  cross-origin). So the module always offers manual escapes rather than guessing.
- **full** — a **real headless Chromium** (Playwright) driven on the local backend and
  **server-rendered** to the pane: JPEG frames stream over `/ws`, and interactions
  (click/scroll/type/navigate) relay back — the same pattern
  [vizdoom](./games.mdx) and the [visualizer](./visualizer.mdx) use. Because the backend
  runs on the **user's own machine** (never a shared host), a server-side browser fits
  the app's trust model, and the server holding the **live DOM** is what makes the
  browser inherently agentic (the agent is handed content + an accessibility snapshot and
  can scrape/click/type). Opt-in and gated — see [Full engine](#full-engine-real-chromium).

`auto` (the default) uses **full** when the backend reports it enabled, else **iframe**.

## Contributions to the layout shell

- **Panels:** `browser.view` (role `document`, **non-singleton** — open as many tabs
  as you like, icon 🌐).
- **Commands:** `browser.open` (Browser: New tab), `browser.focusUrlBar`
  (Browser: Focus URL bar).
- **Keybindings:** `mod+l` → `browser.focusUrlBar`, **scoped** to `browser.view` so it
  only fires in a focused browser pane and never shadows a global shortcut.
- **Settings:** `browser.homePage` (URL for the Home button; blank shows a start page),
  `browser.readerModeDefault` (open every page in reader mode), `browser.engine`
  (`auto` | `full` | `iframe` — the rendering engine, see above), and
  `browser.saveLibrary` (which library 📥 Save files into).

## The pane

The iframe is cross-origin, so navigation history can't be read from it — the pane
keeps its **own per-instance back/forward stack**. The URL bar accepts a bare host
(prefixed to `https://`) or a search query (routed to a search engine). Bookmarks and
history persist server-side (see below).

**Escaping a site that refuses framing** — always available, no fragile detection:

- **▤ Reader** — server-side reader mode: the backend fetches the page and returns its
  extracted text, rendered inline. Works for any site in any build.
Two more affordances appear in **full mode only**, since both need the live DOM /
backend Chromium that an iframe can't give: **📥 Save**
([to the library](#saving-to-the-library)) and **📡 Network**
([what the page is talking to](#network-observability)).

- **⧉ Pop out / Open tab** — on **desktop** (capability `browser.nativeWindow`) opens
  the URL in a **real native window** (a true browser, bypassing X-Frame-Options
  entirely) via the `WindowControl.openBrowserWindow` seam → the Tauri `browser_open_url`
  command (`apps/desktop/src-tauri/src/window.rs`, http/https only). In the **browser**
  build the seam is null, so it falls back to `window.open` (a new tab).

## Agent tools

The panel declares `agentTools`, so the agent orchestrator can use the browser (pushed
to the backend in the capability manifest whenever the module is registered — always
available, not tied to an open pane). They come in two tiers, chosen automatically by
whether the full engine is enabled (`/api/browser/engine`):

**Light (always available):**

- **`browser.read`** (read-only) — return a page's readable text (title + extracted
  content, capped). This is how the agent **reads / researches the web**. With the full
  engine on it navigates the **live shared** browser and reads its content (omit `url` to
  read the page already open); otherwise it runs the SSRF-guarded `/api/browser/read`
  fetch, so the agent can't reach internal services. Read-only, never permission-gated.
- **`browser.open`** (side-effecting) — open a page in a browser pane in the UI so the
  user can see it. Gated by the permission engine via a `{url}` specifier.

**Full engine (when enabled) — the same live Chromium the human panel drives becomes the
agent's browser (one WS connection ⇒ one shared session):**

- **`browser.snapshot`** (read-only) — the page's **interactable elements**, each with a
  numeric `ref`, `role`, accessible `name`, and `value` (a tagged accessibility snapshot
  via injected JS). The agent's "what can I click?" affordance.
- **`browser.click{ref}`** / **`browser.type{ref,text}`** (side-effecting) — act on an
  element by its snapshot `ref`.
- **`browser.scrape{selector}`** (read-only) — pull structured data (text / href /
  outerHTML, capped) for every element matching a CSS selector.
- **`browser.media`** (read-only) — the page's images and videos, each with its `src`,
  alt text, caption, and surrounding context, plus a `described` flag saying whether
  `browser.save` would accept it.
- **`browser.save{target,src?,library?,tags?}`** (side-effecting) — file the page
  (`target: "page"`), one media item (`"media"` + `src`), or every described asset
  (`"allMedia"`) into a [library](./library.mdx). See
  [Saving to the library](#saving-to-the-library).

`browser.read` + `browser.save` are the **write half of RAG** — `library.search` is the
read half. Without `save`, the agent can read the whole web and remember none of it.

Parameterized actions have to be `agentTools` rather than agent-exposed commands here,
because agent commands currently ignore their args (see
[agent tools](../architecture/agent-tools.mdx)).

## Saving to the library

The browser is where the app meets the web, so it's where things worth keeping are
found. **📥 Save** (full engine only) files the open page or its media into a
[knowledge library](./library.mdx), where it's chunked, embedded, and semantically
searchable. The human button and the agent's `browser.save` both go through
`packages/core/src/modules/browser/capture.ts`, so a page saved by hand and one saved by
the agent are the same kind of source.

- **The page** → a `blog` source: the backend re-fetches and extracts it, identical to
  adding the URL in the Library panel.
- **Images / videos** → `image` / `video` sources.

### Why media is stored by reference and description

The app's embedder is **text-only** (`backend/modules/database/embeddings.py` — a
provider call with a deterministic hash fallback). There is no multimodal model, so an
image cannot be turned into a vector directly. Two consequences shape the design:

1. **Media is embedded by proxy.** An asset becomes searchable through the words around
   it — alt text, `<figcaption>`, the nearest heading, the page title. The `media` op
   harvests those from the **live DOM**, which is the only moment they're cheaply
   available: by the time a URL reaches the ingest pipeline, the context is gone. The
   proxy text is deduped before embedding, because the same string routinely arrives as
   alt *and* title *and* caption, and embedding it three times skews the vector.
2. **An undescribed asset is rejected, not stored.** A spacer GIF with no alt text has
   nothing to match on; storing it would put a row in the store that no query can ever
   reach. `browser.save` returns an error explaining why, and the Save popover greys the
   item out rather than hiding it — a silent drop looks like a bug.

Both of these are consequences of a text-only embedder, and
**[CLIP visual search](./library.mdx#visual-search-clip) removes the second one**: with
it enabled the pixels themselves are indexed, so an undescribed image is savable and
findable, description becomes a bonus rather than a requirement, and the Save popover
shows a 👁 marker with the item labelled *indexed by appearance*. `browser.media`
reports both `described` and `savable` per item so the agent knows which applies.

The **bytes are never copied**: a source holds an `asset` descriptor (`src`, `page_url`,
dimensions, caption) and the client renders from the original URL. That also means media
ingest performs no server-side fetch, so it adds no new SSRF sink — unlike `blog`, which
does fetch (see [Security](#security--ssrf)).

CLIP is a **supplement, not a replacement** — the descriptive fields stay useful either
way, and a hit reports which space found it (`matched_by`). See
[Visual search](./library.mdx#visual-search-clip) for the two-space design.

## Network observability

A browser is the app's largest source of outbound traffic and, before this, its largest
blind spot: the pane fetched hundreds of subresources per page and **none of it was
visible**. The `_route` egress hook already saw every request — it just allowed or
aborted it and recorded nothing.

Every request the embedded Chromium makes is now recorded as an I/O event with
`source: "browser"`, alongside `inbound` / `outbound` / `ws` in the
[observability panel](./observability.mdx). Two extra axes come with it:

- **`resource_type`** — Chromium's own classification (`document`, `script`, `image`,
  `xhr`, `fetch`, `media`, …), the thing that makes a page's traffic legible at a glance.
- **`verdict`** — `allowed` or `blocked`. **A request the egress guard kills stays
  visible**, labelled with its reason. A silently aborted request is exactly what this
  pane exists to expose.

**📡 Network** (`browser.network`) is a **registered view declared as a right-hand
region strip** of `browser.view` — so it resizes, persists per pane instance, toggles
from the area header or `n`, and can be **dragged out** by its region header into a
center area of its own, where the inspector has room. The 📡 button reflects and drives
that region rather than local state.

- **Open connections** — requests currently *in flight*, pushed live on the `browser`
  channel as `connections` events. These exist only while unresolved, so they can't come
  from the I/O ring buffer, which (like the httpx seam) records on **completion**. This
  is the "why is this page hanging" view.
- **Completed** — finished requests read from the shared telemetry store, filtered to
  `browser`, with a text filter over method/target/resource type. Selecting one opens
  the **same `IoInspector` the observability panel uses** — general/timing/egress
  verdict, request and response headers, and bodies with JSON pretty-print and copy.
  The component is shared from `packages/core/src/telemetry-view.tsx` rather than
  duplicated: both surfaces render the same `IoEvent`, and a module reaching into
  another module's internals is what the registry conventions forbid.

:::note Scope: all browser traffic, not one tab's
The list covers **every** embedded-browser request, not just the pane you are looking
at. `BrowserManager` keys sessions by **WebSocket connection**
(`backend/modules/browser/session.py`) and the app has a single shared `/ws`, so every
`browser.view` pane drives the **same** headless Chromium and the **same page** — there
is only one stream of traffic to show. The header says "All browser traffic" rather than
implying otherwise.

`browser.view` being non-singleton is therefore misleading today: several browser panes
can be open, but they share one engine and one page. **Reproduced 2026-07-21:** with two
panes open, navigating pane B moved the shared page, while pane A went on displaying its
old URL and a stale frame — the panes do not visibly sync, they silently desync, and a
click in pane A would land on pane B's page.

Independent tabs need **one persistent context per profile with one `page` per pane** —
not one session per pane. Two Chromium processes on the same `user_data_dir` race on the
cookie store, and separate contexts would stop your own tabs sharing a login. That is a
restructure of `_run`/`_loop_commands`/`_capture_frame`, which currently assume a single
page. Per-pane network scoping is blocked behind it.
:::

:::tip Closing one pane no longer freezes the others
The engine is shared, so `stopSession()` on one pane's unmount used to stop it for
**all** of them: `stop_for` pops the session and sets `_closing`, which kills the frame
pump, while the next request/reply op silently builds a replacement session no pane is
driving. The result was every remaining browser pane frozen on a stale frame, with no
error — `info`/`screenshot` kept working, so the engine looked healthy.

Panes now claim the shared engine with `acquireSession()`
(`packages/core/src/modules/browser/session.ts`), whose release stops Chromium only when
the **last** browser pane lets go. The release is deferred a microtask so React
StrictMode's dev-mode unmount/remount doesn't tear the engine down on every mount.
:::

### Implementation notes

- **Recorded on completion, not amended.** `Recorder.amend` needs an event id, which a
  thread-safe `call_soon_threadsafe` post can't hand back — so `_on_response` /
  `_on_request_failed` record once, and the live in-flight set is tracked separately.
- **Thread affinity.** `_route` and the request/response handlers run on the **Playwright
  worker thread**, while `Recorder` notifies asyncio.Queue subscribers and is loop-affine.
  Every hand-off is posted with `call_soon_threadsafe`; frames keep their blocking
  `_emit_threadsafe` (it backpressures the worker), but network events use a
  non-blocking send — a page fires hundreds, and stalling the worker on each would hold
  up the browser itself.
- **The verdict is stamped in `_route`.** Chromium's `requestfailed` can't distinguish
  our abort from a DNS failure, so `_route` records the reason and
  `_on_request_failed` reads it back.
- **Bodies are text/JSON only**, size-capped (256 KB). Pulling every JPEG and video
  through the ring buffer would dwarf the traffic being observed.
- Like the rest of the I/O buffer, capture is **raw** — treat it as sensitive, since it
  holds cookies and auth headers from sites you browse.

## Backend surface (`/api/browser`)

A normal backend module (`backend/modules/browser`), same shape as `library`:

- `GET /read?url=` — **reader mode**: SSRF-guarded fetch + main-content extraction
  (reuses `library.extract.extract_article`).
- `GET/POST/DELETE /history` and `GET/POST /bookmarks`, `DELETE /bookmarks/{id}` — a
  SQLite catalog (`browser_history`, `browser_bookmarks`) in the shared app DB. History
  is upserted per URL; bookmarks are deduped per URL.

### Security — SSRF

`GET /read` fetches an arbitrary user-supplied URL server-side, so `fetch.py` enforces
an SSRF policy before **every** request and each redirect hop: `http`/`https` only;
resolve the host and reject if any IP is loopback / private / link-local / multicast /
reserved (blocks `localhost`, `169.254.169.254`, RFC1918, …); follow redirects manually
and re-validate each `Location`; cap response size and content type. A TOCTOU
DNS-rebind is mitigated but not fully eliminated (full protection needs pinning the
validated IP into the connection). The existing `library` blog ingest has the same
sink with **no** guard today — a worthwhile follow-up is to route it through
`safe_fetch_html`.

## Full engine (real Chromium)

Full mode drives a **headless Chromium** on the local backend
(`backend/modules/browser/session.py`) and server-renders it to the pane.

**Engine.** One `BrowserSession` per `/ws` connection; a process-global
`BrowserManager` owns them and tears each down on disconnect (`stop_for`, wired in
`backend/app.py` alongside `visualizer_manager`). Chromium is driven via **Playwright's
_sync_ API on a dedicated worker thread**, not the async API — Windows'
`SelectorEventLoop` under `uvicorn --reload` can't spawn subprocesses via asyncio (see
`backend/modules/lsp` / the visualizer for the same constraint). The worker owns all
Playwright objects; the event loop posts commands over a queue and reads results back
through per-command futures, and frames are relayed to the loop with
`run_coroutine_threadsafe`. A **persistent context**
(`$HORRIBLE_DATA_DIR/browser/<profile>`) persists cookies, cache, localStorage,
IndexedDB, and site data across restarts.

**`browser` `/ws` channel.** The session pushes `frame` events
(`{frame: <data:image/jpeg>, url, title}`) after every interaction plus on an idle
cadence (byte-identical frames are skipped). The panel relays input back as
`navigate` / `back` / `forward` / `reload` / `click{x,y}` / `scroll{dx,dy}` /
`type{text}` / `key{key}`; agent ops (`content` / `snapshot` / `scrape` / `click_ref` /
`type_ref` / `screenshot` / `info`) carry an `id` and get a correlated `result` event —
so the frontend `session.ts` request/reply layer serves both the human panel and the
agent tools off one shared session.

**Coordinates** are scaled by the panel from the rendered `<img>` to the fixed
1280×800 backend viewport.

### Gating & security

A backend Chromium makes **real network requests to any host**, including the user's
own localhost / LAN / cloud-metadata. Even on the user's machine, a hostile page or a
misused agent tool could pivot inward, so full mode is:

- **Opt-in**: `HORRIBLE_ENABLE_SERVER_BROWSER=1` (mirrors `GAMES_ENABLE_CODE_EXEC`). Off →
  the panel stays in iframe mode and the full-engine agent tools return a "not enabled"
  notice. `GET /api/browser/engine` reports `{enabled, installed}`.
- **Egress-guarded**: every request is routed through Chromium's `context.route` and
  aborted if its host resolves to a private / loopback / link-local / reserved IP
  (reusing `fetch._check_host_public`, resolution cached per host). `file://` and other
  non-`http(s)` schemes are blocked; `data:` / `blob:` / `about:` pass. Navigation
  re-checks the scheme + host. `browser.eval` (arbitrary in-page JS) is behind the same
  gate.
- **Bounded**: one context per connection, released on disconnect / pane close.

### Dependency & cross-platform

Playwright is an **optional extra** (`browser-engine`), lazy-imported like the
`games-native` ViZDoom extra, so the core app installs everywhere without it:

```bash
uv sync --extra browser-engine
uv run playwright install chromium   # one-time, ~150 MB, prebuilt per-OS
```

The main backend isn't containerized (it runs on the user's machine), so there's no
Dockerfile change. Without the extra, `GET /api/browser/engine` reports
`installed: false` and the panel stays iframe-only.

## Browser vs desktop

| | Browser build | Desktop (Tauri) |
| --- | --- | --- |
| Inline framable sites | ✅ iframe | ✅ iframe |
| Reader mode (any site) | ✅ | ✅ |
| Full Chromium engine (any site, live DOM, agentic) | ✅ (gated + extra) | ✅ (gated + extra) |
| Blocked-site escape (iframe mode) | Open in new tab (`window.open`) | **Native browser window** (`browser.nativeWindow`) |

The full engine renders **the same backend Chromium** in both builds, so it's the
general answer to framing-blocked sites; the native-window pop-out remains an
iframe-mode escape hatch on desktop.

## Known limitations / future

- Frame streaming is functional but not buttery — a CDP `Page.startScreencast`
  (paint-driven frames) is the planned upgrade. Chromium is heavy, so full mode is
  bounded (one context per connection, released on disconnect).
- Deferred full-engine work: in-pane **tabs** (multiple pages per context), a smart URL
  bar / start page with favicons & titles, a history/bookmarks manager, and
  multi-profile switching.
- Media search is proxy-text only **unless [CLIP visual search](./library.mdx#visual-search-clip)
  is enabled** — without it, an image with no alt text, caption, or nearby heading can't
  be saved at all (its only index would be a filename). With CLIP on, the pixels become
  the index and 📥 accepts it. OCR and video transcripts are still not done; video is
  embedded from its poster frame only.
- Saved media is stored **by reference**: if the origin removes the asset or it sits
  behind auth, the library keeps a searchable record pointing at a URL that no longer
  renders.
- The network view covers the **full engine only** — an iframe's requests are made by
  the user's own browser and are invisible to the backend.
- Iframe-block detection is best-effort; in iframe mode the manual escapes are always
  shown rather than auto-triggered.
- A **true in-pane native webview** on desktop (Tauri's `unstable` multi-webview) is
  superseded by the server engine and deferred.
- Not to be confused with the external **Claude-in-Chrome** automation, which drives the
  user's *real* Chrome; this module renders pages *inside* the dashboard.
