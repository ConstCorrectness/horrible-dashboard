# The desktop shell

The shell presents itself like an operating system: you arrive at a **desktop** with a
backdrop, open things as free-floating **windows**, snap them to edges, and find them
again on the taskbar. There is one desktop, and every pane on it is a window.

This page covers the desktop as an interaction model: windows, the backdrop, the
taskbar. The _data_ those windows live in is `FrameState`, documented in
[windowing.mdx](windowing.mdx).

:::info Status
All of it has landed: the window model and its migrations, the window layer, the
backdrop providers, the taskbar and start menu, the boot splash and first-run flow,
the spotlight, the themes, the wallpaper routes, and the agent verbs.
:::

## There is one shell view

```
ShellView = 'boot' | 'oobe' | 'desktop'
```

`home` — the avatar and ask bar — was once a second landing screen competing with the
desktop for the same job; it survives as the `splash` **backdrop**, which is strictly
more useful, because windows can float over it. Nothing in the shell "navigates".

Installing the engine is the **shell's** job, not any one component's. The controller
the agent tools drive, the debounced autosave, the `frame` module's commands and
hydration all live in `packages/ui/src/layout/install.ts` and run from the shell. They
used to sit in the tiling frame's mount effect, which was survivable only while the
frame was the only place you could be: once the desktop became the landing surface, a
fresh boot installed none of it — no layout agent tools, no region or backdrop
commands, no hydrated layout. Every one of those failures is silent.

## One desktop, no tiling

Until 2026-10 a desktop could be **floating** or **tiling** — a Blender-style centre
grid with tool docks, activity rails and a workspace tab strip — and there could be
many of them: a dozen pre-arranged `frames:` presets (AI Research, Training, Lab…)
plus any the user made, each of which could open in its own OS window. All of it was
removed rather than hidden. Two paradigms meant a lossy convert between them, a mode
menu to choose, a setting for which kind a new desktop was, and every feature built
twice — and the floating desktop was the one actually in use.

What that leaves:

- **One desktop**, stored as the `desktop` workspace row. Other rows the backend may
  still hold are neither loaded nor deleted.
- **No mode.** The `desktop.defaultMode`, `desktop.workspaces` and
  `desktop.bootWorkspace` settings are gone; a stale value in the settings store is
  simply never read.
- **Saved layouts carry over.** A tiling-era blob's grid and docks become windows on
  load — see [windowing.mdx](windowing.mdx#persistence).
- **SDK v3.** `defaultDock`, `defaultDockSize`, `dockable`, `DockSide` and
  `ModuleManifest.frames` are gone; a plugin built against v2 is skipped by the loader
  until it is rebuilt.

### What boots

`hydrate()` loads the `desktop` row, creating it on a clean install with an empty
frame on `DEFAULT_BACKDROP` — the home surface (see
[the default must be an interactive backdrop](#the-default-must-be-an-interactive-backdrop)).
It retries the read, because boot races the backend; on real failure the store stays
un-hydrated so nothing can autosave a blank screen over the layout on disk.

:::warning The titlebar has to be grabbable
Under `chrome.workspaceTabs` the native window is undecorated and `TitleBar.tsx` is its
titlebar: a slim `frame-tabs--bare` strip carrying `data-tauri-drag-region` and the
min/max/close cluster. (The capability is named for the workspace tab strip that used
to be that titlebar.) In the browser it renders nothing.

The drag region must be given the strip's **full height** explicitly
(`.frame-tabs--bare .frame-tabs-scroll { align-self: stretch }`). The strip centres its
window controls, which overrides `align-items: stretch`, and the drag region's only
content is nothing at all — so it measured full width and **zero height**, leaving a
28px titlebar with no grabbable pixel anywhere. Nothing looks wrong when this breaks:
the attribute is present and correct on an element with no area to hit.
:::

## Backdrops

A backdrop is a **registered provider** (`BackdropDecl`, contributed through
`ModuleManifest.backdrops` and exported from the SDK), not a settings string — a
wallpaper, a procedural animation, a live node-state view and a full dashboard are
the same kind of thing to the desktop, and a plugin should be able to add one.

| id       | What it is                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| `none`   | Flat `--bg`.                                                                                                        |
| `aurora` | Three blurred CSS gradients drifting on a long keyframe, built from theme tokens.                                   |
| `grid`   | Canvas: a drifting grid with a scanline sweep. Pairs with `hud`.                                                    |
| `image`  | A wallpaper the user uploaded. `params: { url, fit, dim }`.                                                         |
| `splash` | **The default.** The home screen — avatar, ask bar, connector tiles — with windows over the top, and a wallpaper of its own behind. Collapses to a docked ask bar over that wallpaper; see below. |
| `pulse`  | Canvas: one ripple per request through this node, read from the same `telemetryStore` the observability panel uses. |
| `board`  | Widgets laid straight onto the desktop.                                                                             |

Nothing here bundles third-party imagery: the drawn ones are arithmetic, the live
ones render the node's own state, and `image` shows what the user supplied. Same
rule as the maps and the search engines.

A provider declares `interactive` when it wants pointer events (`splash`, `board`).
A decorative one stays `pointer-events: none` and a transparent catcher over it
collects the clicks, so the desktop's right-click menu works across the whole
surface. That catcher is skipped entirely for an interactive backdrop, which would
otherwise be sealed behind it.

### The default must be an interactive backdrop

`DEFAULT_BACKDROP` (`packages/core/src/layout/types.ts`) is `splash`, and that is a
product decision rather than a cosmetic one. `HomeView` — the avatar, ask bar,
connector tiles and first-run `SetupCard` — is rendered by **exactly one thing in
the app**, the `splash` backdrop. While the default was `aurora`, a clean install
opened on a wallpaper and a taskbar, and the whole tier-1 entry surface (the one
PRODUCT.md says must work for someone who never opens a terminal) was unreachable
unless the user happened to pick "Home" out of a list of seven wallpapers.

`packages/core/src/__tests__/front-door.test.ts` enforces this: the default must be
a backdrop declared `interactive`, and that backdrop must still mount `HomeView`.
It is the reachability invariant the panes already have, applied to a *surface*.

**An unregistered backdrop id falls back rather than blanking the desktop.** A
plugin can be uninstalled while a saved workspace still names its backdrop; losing a
wallpaper is not a reason to lose the windows on top of it.

The switch commands (`desktop.backdrop:<id>`) are **synthesized by the registry**,
one per registered provider, exactly as the pane openers are — so a plugin's
backdrop gets its command without a second list that can fall out of step.

### The home screen minimizes

`splash` was the one surface in the app with no way to get it out of the way. It
is a backdrop, so it has no title bar to hang a control on and no taskbar button
to restore it from, and it is `interactive`, so it takes pointer events across the
whole desktop. The only escape was knowing that the desktop's right-click menu can
swap the backdrop entirely — which is also the wrong verb: swapping throws the ask
bar away in order to hide the greeting.

So it collapses instead, to a strip at the bottom holding the ask bar and nothing
else. Everything the collapse drops is *landing screen* — a greeting and an avatar
are worth seeing when you arrive and worth nothing when you are working over the
top of them — and the ask bar is the reason to keep the surface at all.

The flag lives in the **backdrop's own `params`** (`{ collapsed: true }`), so it is
per-desktop and persisted with the rest of the layout: a desktop you work in stays
collapsed and one you land on stays open, with no global setting for the two to
disagree about. `setHomeCollapsed` merges into the existing params rather than
replacing them, because `setBackdrop` takes a whole `BackdropRef`.

Three ways in, because a control nobody finds is a control that does not exist: a
**Minimize** button on the home column itself, `desktop.toggleHome` in the command
palette, and an entry in the desktop's right-click menu — which appears **only on a
desktop actually showing the home screen**, since an item that silently switched
you to the home screen in order to collapse it would be a trap.

The palette also carries `desktop.hideHome` and `desktop.showHome`, the two
directions named. A toggle is the wrong shape for the palette and for the agent:
both act without seeing the screen, so "toggle" means "put it in whichever state it
is not in", and running one twice leaves the home screen hidden. The toggle stays
for the keyboard and the menu, where the current state is visible.

### The home screen carries its own wallpaper

Collapsing had nowhere to collapse *to*. A desktop has exactly one backdrop slot
and `splash` is in it, so minimizing the home screen revealed a flat
theme-coloured void — the wallpaper that would have been there is precisely what
`splash` displaced. The floating desktop the collapse is supposed to land on did
not exist.

So the home surface paints a second, decorative backdrop **behind** itself:
`resolveHomeUnderlay` (`packages/core/src/layout/home-surface.ts`) reads
`params.under`, defaulting to `aurora` — the id that was `DEFAULT_BACKDROP` before
the home screen took the slot, so a desktop still looks like the one people know.
Collapsing now lands on a genuine floating desktop: wallpaper, taskbar, and the ask
bar docked at the bottom.

The underlay is painted in **both** states, not swapped in on collapse. The landing
screen has always been translucent over whatever is behind it, and a wallpaper that
appeared only once you minimized would read as a rendering glitch rather than as
the same desktop seen from closer up. A scrim between the two keeps the front door
legible over an arbitrary wallpaper — including a photograph the user supplied —
so "pick a wallpaper" and "read the home screen" are not a trade-off. It is scoped
to the expanded form only; veiling the whole desktop for a single docked control
would defeat having collapsed at all.

`params.under` sits beside `params.collapsed` in the same bag, which is why both
writers go through one merging `patchHome`: either written as a replacement
silently discards the other. The picker is the desktop menu's **Wallpaper behind
home**, listed after **Backdrop** so the two read in order — what this desktop is,
then what it looks like underneath.

:::warning The underlay may never be interactive
Two ids are refused, and both fail badly rather than visibly. `splash` under
`splash` mounts `HomeView` inside `HomeView` forever — the symptom is a hung tab,
not a wrong wallpaper. Any *other* `interactive` backdrop (`board`) puts two
surfaces that both want the pointer in one square of screen with the lower one
unreachable, which reads as the widgets having stopped working. `resolveHomeUnderlay`
enforces it at render time and `homeUnderlayMenuItems` filters the menu, so the
picker never offers what the renderer would refuse. An unregistered id falls back to
the default the way the main slot does.
:::

### The transition

Collapsing and expanding swap one form of `HomeView` for the other, so the motion
is an **entrance on whichever form arrived** rather than a cross-fade: the outgoing
DOM is gone by the time React commits, and keeping both mounted to animate an exit
would mean two live agent request states — a question asked in the strip would be
lost on expand. The landing screen lifts away to the wallpaper; the strip rises
from the taskbar. Under `prefers-reduced-motion` both keep the fade and drop the
travel. Nothing animates the wallpaper itself: it is present in both states, and
flashing it would make one desktop look like two.

:::warning The collapsed surface must stop eating clicks
`splash` is registered `interactive`, so its layer takes pointer events over the
entire desktop. That is right when the home screen fills it and completely wrong
when it is a strip: the desktop underneath would stop responding while *looking*
like it should. `.os-backdrop-splash[data-collapsed]` is `pointer-events: none`
and only the strip and its answer panel take clicks back.
:::

### Canvas backdrops

`backdrops/canvas.ts` gathers the three things a canvas backdrop always has to get
right, so a new one cannot forget one:

- **Theme tokens are read through `readThemeTokens` and the effect resubscribes on
  `useThemeId`.** A canvas cannot use a CSS variable, so it resolves colours once —
  and this is a repeat bug in this codebase, so the hook makes it structural.
- **The loop stops on `visibilitychange`.** `requestAnimationFrame` does not fire in
  a hidden window at all, so a loop driving its own clock off frame deltas resumes
  with a multi-minute jump. `dt` is clamped and the clock resets on resume.
- **The backing store follows `devicePixelRatio`**, via `setTransform` rather than
  `scale` — this runs on every resize and `scale` compounds.

`pulse` adds one of its own: events are upserted by `(source, id)` (the backend
re-emits one to fill in a streamed body), so "new" has to mean _a key never seen_,
not "the array got longer". Ripples are placed by hashing the endpoint, so the same
target always pulses in the same spot and the backdrop reads as a map of what this
node talks to rather than as noise.

### Wallpapers

The one piece of the desktop that needs the server, because it is a _file_:
`backend/modules/desktop/` serves `GET`/`POST /api/desktop/wallpapers` and
`GET`/`DELETE /api/desktop/wallpapers/{id}` out of `$HORRIBLE_DATA_DIR/wallpapers/`
(via `backend.paths`, never an inline `os.environ.get`).

Four rules there are load-bearing:

- **The stored extension comes from the content-type table, never the uploaded
  filename.** Trusting the client's extension is how an upload route starts writing
  `.html` into a directory it also serves.
- **The id is 32 hex characters, pattern-enforced at the route boundary**, and
  `_resolve` re-checks that the resolved path is inside the wallpaper directory. The
  pattern is the guard; the check is the assertion that the guard held. A `..` here
  is how a read route becomes an arbitrary-file-read.
- Uploads land via `.part` + rename, so a truncated image is never listed.
- The stored `url` is **api-relative** (`/desktop/wallpapers/<id>`). The backend
  origin differs between the dev server, a packaged desktop build and a LAN-bound
  node, so an absolute URL baked into a saved workspace stops resolving the moment
  any of that changes. The frontend prepends `/api` — `apiUrl` prepends the _origin_
  only, and getting that wrong fails **silently**, because a `background-image` that
  404s simply paints nothing and the desktop looks like the wallpaper was never set.

## The taskbar

`layout/taskbar.ts` derives the buttons, pure over `FrameState` + the registry — the
taskbar has no opinion of its own about what is open. The strip itself is a zone
container driven by the `desktop.taskbar` setting (`start`, `windows`, `mx`, `tray`,
`clock`, `agent`, `spacer`); a stored config is **merged** over the defaults so a
config written by an older build does not silently lose a zone the user never
removed, and an unknown zone name is skipped rather than rendered as an error strip.

**Right-click the strip to customize it** (the `taskbar` context-menu kind): which
zones show, top or bottom, labels, auto-hide, and a reset. The config was always a
setting; what it had no way of being was *edited*, short of typing JSON into the
settings page — which is not something anyone discovers about their own taskbar. The
menu writes that same setting through the same merge, so it and a hand-written value
cannot mean different things. Zones are toggles rather than a reorderable list (a
menu is a poor reordering surface), and a zone switched back on is spliced in at its
canonical position — `zoneRank`, i.e. `ZONES`' own key order — rather than appended
past the clock. _Reset the taskbar_ is the escape hatch that makes hiding everything
safe: a bare strip still right-clicks, so there is no way to customize yourself out
of reach of it.

A stored `zones` array is otherwise taken **whole** — it is an explicit choice, and
quietly adding to it would defeat the point of being able to hide a zone. That leaves
one problem, and `ZONES_VERSION`/`ZONE_SINCE` is the answer to it: a zone introduced
*after* the stored config was written is inserted, and a zone the user actually
removed is not. Without the version the two are indistinguishable, and someone who
customized their taskbar once would never receive another zone again. Bump the
version and add the entry in the same change that adds the zone.

The default zones are `start`, `windows`, `spacer`, `mx`, `tray`, `clock`, `agent`.

**`agent` is last, past the clock.** `agent.chat` is the pane you reach for
constantly, and without a button of its own it was available only through the palette
or the Start menu. The button **toggles** rather than reopening: an
already-open chat goes through `activateTaskbarEntry`, the same verb a window button
runs, so a second click hides it. Calling `openPanel` unconditionally would look like
nothing happened.

**Window buttons are a fixed width** (`--taskbar-btn-w`, 168px), not shrink-wrapped
around their label. Width used to track the text, so the strip was a ragged run of
boxes whose click targets moved whenever a pane retitled itself — an editor button
resizing as you switched buffers. Shrink is still allowed, so a crowded strip tightens
before it starts scrolling, but nothing grows to fit its text; the label ellipsises
inside the fixed box, and with labels off (`is-iconic`) the button collapses to a
square rather than leaving most of a text-width box empty.

The strip must scroll, which is why the window buttons run `useHorizontalWheel`, so
a plain vertical wheel moves them sideways. They are `overflow-x: auto` with the
scrollbar hidden, so before that the overflow was reachable only by trackpad or
shift+wheel — on a mouse, the later buttons simply did not exist. The hook also stamps
`data-overflowing` when it measures real overflow, which is what the edge fade keys
off; fading unconditionally dims the first button of a strip that fits, and reads as a
rendering fault.

### The `mx` zone, and where the minibuffer went

The minibuffer used to be the tiling frame's bottom row, so on a floating desktop it
was not merely hidden but absent: `alt+x` flipped a store that nothing rendered, and —
the part that was actually broken — every `dialogs.prompt()` waited forever on an
answer the user was never shown, since the minibuffer is what serves prompts inline.

So the shell mounts it as `<Minibuffer variant="overlay" />`, floating just above the
taskbar and rendering **nothing when idle**. Idle is the whole difference: a permanent
status strip stacked over a taskbar is a second status bar saying much the same
thing. The taskbar's `mx` zone carries the
idle half instead — the M-x button and the echo area — which is also the answer to
"where is M-x?": a keystroke with no visible presence is one nobody finds, the same
argument the tray's fullscreen button already makes.

Two decisions in the derivation matter:

**A button is per pane instance, not per window.** A window merged into three tabs
is three things the user can switch to, and one button for it would make two of them
unreachable from here.

**The order is stable** — by the numeric suffix of the instance id, i.e. by the
order panes were opened. Nothing about focus, z-order or minimizing may reorder it,
because a taskbar that reshuffles on focus moves the button out from under a pointer
already travelling toward it. (Comparing the ids as plain strings would put `#10`
before `#2`, so panes would visibly reshuffle the tenth time you opened one.)

Clicking follows the universal convention, in one verb (`activateTaskbarEntry`):
clicking the thing you are already looking at **minimizes** it, clicking anything
else brings it forward. A taskbar whose focused button does nothing silently
swallows every second click. **Double-clicking always minimizes** (`minimizePane`),
whatever the first click did — a direct "put this away" that does not depend on
what state the button happened to be in.

The taskbar is also what makes minimize usable at all — a minimized window is off
screen, and this is the only route back to it. `minimizePane` minimizes the pane's
whole window, tabs and all.

### Attention: a pane that finished while you were elsewhere

Minimizing is non-destructive, and panes keep working while put away — a deep-research
run, a training job, an ingest, a compile. `requestPaneAttention(instanceId)` sets
`PaneState.attention`, and the pane's taskbar button pulses until the user looks at it.

- **Cleared by `activateTaskbarEntry`, nowhere else.** Looking at the pane is what
  acknowledges it; clearing on a timer or on any focus change would let a button keep
  pulsing after the user had plainly dealt with it.
- **Refused for the focused pane.** Flashing a button for the thing on screen is noise,
  so `requestPaneAttention` returns `false` and changes nothing.
- **A boolean, not a count.** The button is a flash, not an inbox; "three things
  happened" is a story the pane tells once you are in it.
- **Absent rather than `false`** on the pane, so a serialized layout never carries a
  stale "was flashing once" flag for every pane ever opened.
- The accessible name becomes `"<title> — finished"`, because a pulsing border conveys
  nothing to a screen reader; reduced-motion keeps the ring and drops the animation.

The **start menu** lists `registry.panels` + `registry.widgets` minus `embedded`,
filtered exactly as the palette's openers are — an embedded view lives inside a host
pane, and a launcher entry would present it as a second, competing home.

It is **grouped into seven fixed categories** (`PaneCategory`, labelled by
`PANE_CATEGORY_LABELS`): AI Research, Agents, Build, Data & Knowledge, Play & Media,
People, System — plus **Plugins** for a third-party view that declares none. A
module declares `category` once on its manifest; a pane may override it
(`registry.viewCategory`). `start-menu-categories.test.ts` fails the build on a
built-in module without one, since it would otherwise land under Plugins silently.

Inside a category, a module with **more than one launchable pane folds into one
row** (its title, a count, a chevron) that opens in place; single-pane modules list
flat. This replaced grouping by owning module, which gave a heading per feature —
most over a single row — and a catch-all "All panes" band that had become the
longest list in the menu. Search still matches title, id, module and category, and
flattens the groups.

Above the groups sits a **Recent** band: the last six panes opened, most recent
first, from `layout/recents.ts`. It is recorded in `registry.openPanel`, so every
route to a pane — launcher, command palette, spotlight, an agent tool — feeds one
history. It lives in `localStorage` rather than settings deliberately: it is a
per-device convenience, it changes on every open (a settings PUT per launch would
be absurd), and `GET /api/settings` hands the whole bag to the browser. Ids are
resolved against the live registry on read, so a renamed or uninstalled pane drops
out instead of offering a dead entry. The band is absent until something has been
opened — an empty "Recent" heading is a promise the launcher has not kept — and it
is hidden while searching, where it would compete with the results.

The grouping used to be by **`PaneRole`**: Documents / Tools / Widgets. Sixty-odd
entries in one alphabetical run did say nothing, but the role answers a question
nobody browsing a launcher is asking — it describes what kind of pane something is,
and everything in this menu opens in a window either way. The feature a pane belongs to is
what someone is actually hunting for, and it was already the axis the search box
matched on: a view's title says what the pane is, the module's says what feature it
is part of, and those are frequently different words — the Observability module's pane
is called *Data flow*, so a search for the feature came back empty on a pane sitting
right there under Tools. Promoting the module from a trailing suffix on each row to
the heading above them makes browsing and searching agree, and drops the "Settings ·
Settings" repetition the suffix had to dodge. Searching still flattens the groups —
three headings over four results is more structure than content.

Its **footer** is Settings / Setup / Theme. The bottom-left corner is where people go
for settings, and the menu previously offered it only as one row of sixty, filed under
S. Theme opens the tray's own `taskbar.theme` menu rather than a second list.

## Boot and first run

`AppRoot` shows the boot splash until `bootReady()`, then mounts the shell. That
gate is **not cosmetic**: `AppShell` installs the frame engine on mount, and that
hydrates the desktop — which prunes panes whose views are not registered.
Mounting the shell before `boot()` has registered its modules and awaited
`loadPlugins()` would not just look wrong, it would silently delete the user's
layout and then save the result.

The splash narrates the **real** boot (`bootStore`), one step per thing that
actually happened, with real timings. A fake progress bar that always takes 800 ms
says nothing when the backend is not answering, which is exactly the moment the user
most needs to be told something. Individual steps are non-fatal — a plugin that
failed to load degrades the app rather than stopping it — and only a throw sets
`phase: 'failed'`. The step list is time-gated (1.2 s), so a fast boot is a logo and
a fade while a stalled one explains itself without being asked. The progress bar is
deliberately **indeterminate**: the step count is known but their durations are not
remotely comparable, so a real percentage would sit at 90% through the one step that
actually takes time.

First run (`desktop.oobeComplete` unset) goes through a three-step wizard — who you
are, what it looks like, what it can reach — before the desktop. The third step is
the **existing** `SetupCard`, not a copy of it: model / account / connectors already
had one flow with a carefully argued shape (the account and the connectors are two
steps on purpose — see that component), and a first-run duplicate would be a second
thing to keep in step with reality. Every step is skippable, and "Skip setup" leaves
the whole wizard rather than advancing one screen — a setup flow you cannot leave is
one people close the app to escape.

The name the first step asks for is a **setting** (`shell.userName`), not
localStorage. It used to be the latter, "a per-browser nicety" — but the greeting is
a fact about the node, so a fresh browser profile, or a cleared origin, meant the
wizard introduced itself to someone it had already met. As an ordinary declared
setting it is also editable and resettable on the settings page afterwards, which is
where a first-run answer belongs once first run is over. It is committed on leaving
the step rather than per keystroke, and `Finish`/`Skip setup` **await** both it and
`desktop.oobeComplete` before dismissing the wizard, warning by toast if the backend
refused — firing the write and navigating away is how a failed save became a wizard
that silently reappeared. (The bug underneath it was in the backend's settings bag —
see [the settings module](../modules/settings.mdx#backend-surface).)

The wizard is a **view, not a modal**. It owns the screen until it is finished or
skipped; a dismissible overlay over a half-configured desktop is exactly the "did I
finish that?" state it exists to avoid.

## Spotlight

`mod+k` opens one surface that takes anything: commands, panes you already have
open, and the agent. It **replaced** the command palette rather than sitting beside
it — the agent is meant to be always available, and two overlays competing for one
keystroke means the user has to decide which one they want before they can start
typing.

`spotlight.ts` resolves the list, pure over the registry + a frame snapshot. Three
things it settles:

- **Open panes rank above commands.** Typing "terminal" almost always means the
  terminal you have, not the command that opens another one.
- **`>` / `@` / `?`** restrict to commands / panes / the agent.
- **The agent is the fallback.** It is offered last when other things matched, and
  first — alone — when nothing did. A palette that answers a typed sentence with "no
  matching commands" is the failure this surface exists to remove. It is _not_
  offered for an empty query, so opening the surface is not a prompt.

An ask keeps the spotlight open, unlike every other action: the answer is the point,
and closing to deliver it somewhere else would mean going to find it.

**The empty state is a hub, not a list.** With nothing typed, Spotlight shows the AI
briefing (the week's top papers and AI headlines), quick settings and notifications
instead of every command in registry order, a list nobody read, since anyone who knew
what they wanted typed it. The first keystroke swaps the hub for the results, so
nothing reached by typing moved, and `Enter` and the arrows do nothing while the hub
shows. The `briefing.showInSpotlight` setting restores the plain list. See
[briefing.mdx](../modules/briefing.mdx).

## Windows

A window's content is an `AreaNode` — a tab list — so a plain window is an area with
one tab and a merged window is an area with several. See
[windowing.mdx](windowing.mdx#model).

The active tab is rendered through **`PaneWithRegions`**, so a pane keeps its
[region strips](panel-groups.mdx#where-a-region-host-may-live). Windows used to render
a bare `PaneHost`, which dropped every strip a region host declared with nothing to
say one had gone. That wrapper brings a constraint with it — `.os-window-body` must be
`display: flex`, because `PaneWithRegions`'s root carries `flex: 1` and no height —
and getting it wrong empties **every** window (`region-host-is-flex.test.ts`).

### Geometry

Rects are **pixels**, against `FrameState.windowViewport`. The window layer measures
itself and owns the single `SET_WINDOW_VIEWPORT` dispatch, because every rect in the
store is relative to that number and exactly one element may be its authority.

Two rules that are bugs if forgotten:

- **The viewport must be re-reported after every layout load.** `LOAD_WORKSPACE`
  replaces the whole frame with the deserialized one, whose `windowViewport` is
  whatever was stored — null for a fresh or migrated blob. The element has not
  resized, so a `ResizeObserver` alone stays silent, and a migrated v1 window (saved
  on a 1×1 basis) would never scale up into pixels: it would render a few pixels wide.
- **`SET_WINDOW_VIEWPORT` must not bump `revision`.** It is a projection, not an edit.
  Marking it dirty makes every browser resize dirty the layout and drives the 600 ms
  autosave debounce into a continuous write loop.

Geometry is committed to the store on pointer-**up**; the in-flight rect is local
component state. Dispatching per frame would bump `revision` a hundred times per drag.

Clamping lives in the **reducer**, not the drag handler, so a rect arriving from an
agent tool obeys the same rules as one dragged by hand. `clampRect` keeps a strip of
titlebar on the surface and never allows a negative `y` — a window above the surface
hides its own titlebar behind the app's title strip, where dragging moves the OS
window and the user cannot get it back.

### Snapping

`layout/snap.ts` is pure geometry, shared by the drag preview and the agent's snap
verb so the two cannot disagree — a preview promising one rect while the drop delivers
another is a bug nobody reports precisely.

- Corners are tested **before** edges: inside a corner box the pointer is within the
  edge threshold of two sides at once, and whichever edge test ran first would win
  arbitrarily.
- The **top edge maximizes** rather than snapping to a top half — the near-universal
  convention, and a "top half" is the one snap nobody reaches for.
- Halves, quarters and thirds tile the surface exactly; the far cell absorbs the odd
  pixel of an odd width, so they always sum to the full extent instead of overlapping
  or leaving a seam.
- The zones are `left`/`right`/`top`/`bottom`, the four corners, `center` (a centred
  two-thirds box), the three full-height `third-*`, and `max`. `center` and the thirds
  are **keyboard and palette only** — `snapZoneAt` never returns them. There is no
  unambiguous pointer gesture for "the middle third" that does not also redefine what
  dragging near an edge means, and the edge gesture is tuned.
- `SNAP_ZONES` in `snap.ts` is the **one** list. It used to be spelled out three more
  times — a `Set` in `serialize.ts`, an array in `window-placement.ts`, another in the
  agent's `tool-exec.ts` — and each is a *filter* that drops what it does not
  recognize. A zone added to the type and to `rectForZone` but missed in one of them
  fails silently: the snap works, and the window comes back somewhere else after a
  reload.
- A snapped or maximized window **re-derives** its rect from the zone when the surface
  resizes, rather than being scaled: half of the new surface is exactly half, where a
  scaled rect would carry the rounding of the old one.

The drop decision is resolved **synchronously** during the drag and kept in a ref.
Reading it back from React state at pointerup loses the last frame's zone whenever the
move and the release land in the same frame — an intermittent failure to snap that
only shows up when moving fast.

#### Snap assist: the other half fills itself

Snapping a window to a half over a **maximized** window used to leave the maximized one
full-width underneath, so the result was one window on top of another rather than the
split the gesture asks for. `SET_WINDOW_MODE` now takes a `fill` flag: when the action
lands on a half, whatever was covering the other half is snapped into it.

- `complementZone` is **halves only**. A quarter leaves an L-shaped remainder that no
  single zone describes, a third leaves two, `center` leaves a frame and `max` leaves
  nothing. Picking a "closest" zone for those would move a second window somewhere the
  user did not point, which is worse than not moving it — the value of the fill is that
  the result is the split they were already looking at.
- The candidate is the topmost window that is maximized, snapped to the *same* zone, or
  overlapping the newly-taken half by half its own area. A window already sitting in
  the complement is skipped: re-snapping it would overwrite the `restoreRect` it holds
  for its own un-snap.
- **One** window moves, never several. Filling every overlapping window into the same
  zone would stack them, and the second one to arrive would be a window the user never
  touched appearing from behind the first.
- `fillTarget` lives in `snap.ts` beside `rectForZone` for the same reason everything
  else there does: `SnapOverlay` draws the complement rect **only when a fill will
  actually happen**, and a second copy of "is there a candidate" would drift into a
  preview promising a split and a drop delivering an overlap.
- `fill` is **opt-in**. The drag handler and the snap chords pass it, because a person
  snapping is arranging a screen. The `window_state` agent tool does not: it is moving
  one named window, and a second one shifting under it would be an effect with no
  visible cause.

### The snap palette

The four halves are bare chords (`mod+shift+<arrow>`). The other nine zones sit behind
a **two-stroke prefix**, `mod+alt+s`, laid out as the 3x3 block under the left hand:

```
q w e    top-left    top half     top-right
a s d    left half   centred      right half
z x c    bottom-left bottom half  bottom-right
1 2 3    left third  middle third right third
f        maximized       arrows   the four halves
```

`mod+shift+<arrow>` was already the halves family and `mod+alt+up`/`down` are maximize
and minimize, so a third modifier on either risks a collision that shows up on one
platform only. A prefix has room for all thirteen zones and gives the palette
something to draw.

`SnapAssist.tsx` renders that grid while the prefix is pending. It owns **no keyboard
handling**: the two-stroke bindings are the only listener, and the component is a pure
renderer of the dispatcher's pending-chord state — so it cannot fall out of step with
what the keys do, and the Escape ladder's first rung (abandon a half-typed chord) keeps
working. Each cell's thumbnail is drawn from `rectForZone` on a unit surface, the same
trick `SnapOverlay` uses, so a cell pictures the rect it will actually produce.

The commands run `snapFocused`, which snaps the focused window — or, when no window
holds focus, the window of the focused pane.

### Merging and tearing

Dropping a window on another window's titlebar merges them into tabs
(`MERGE_INTO_WINDOW`). The titlebar is marked with `data-window-titlebar` for the
hit-test — and **never** with `data-tauri-drag-region`, which belongs to the app's own
titlebar. On a window, that attribute would drag the whole OS window instead of the
window under the pointer.

A tab torn out of a merged window gets a window of its own (`WINDOW_FROM_PANE`, the
`window.tearOff` command).

### The titlebar's right-click menu

Right-clicking a window's titlebar opens the `window.titlebar` context menu, which the
`desktop` module contributes as two groups:

- **Help.** `Help: <pane>` opens that pane's module page on the published docs, and
  `All documentation` opens the docs home. The page is found by module id
  (`registry.viewOwnerId`) in `ui/desktop/help-links.ts`; a module with no page gets
  no per-pane item rather than a guessed URL, and `help-links.test.ts` checks every
  listed page exists in `docs/`.
- **Window verbs.** Minimize, Maximize or Restore (named by the window's state),
  `Move to its own window` when the window holds more than one tab, and Close.

A right-click on a tab is about **that** tab, not the active one: the tab buttons
carry `data-instance-id` and the handler reads the target from the tab under the
pointer.

Dragging a window also **releases keyboard/pointer capture** first. A captured pane —
a game, a terminal, the server-rendered browser — otherwise keeps the pointer and the
drag never reaches the handler.

### Minimize, maximize, close

- **Minimize keeps the pane mounted.** A minimized terminal keeps running and a
  minimized game keeps its socket. See
  [windowing.mdx](windowing.mdx#pane-lifetime-unmount-is-not-close) for the two ways
  this is easy to break.
- **Maximize** stores the rect it came from and restores to it. Capturing a restore
  rect only happens when leaving a _free-floating_ state, so maximizing an
  already-snapped window does not overwrite the rect it was originally dragged to.
- **Minimize remembers the mode, not just the rect.** `WindowMode` is a single enum, so
  `'minimized'` overwrites `'maximized'` — and the restore path *consumes* `restoreRect`,
  which meant a maximized window came back at whatever small size it had before it was
  maximized. The rect was never lost; losing the mode is what discarded it.
  `WindowState.minimizedFrom` records `{ mode, snap }` on the way down, and un-minimizing
  resumes exactly that, leaving `restoreRect` intact for the un-maximize that comes
  later. It carries a zone and never a rect, so the rect is **re-derived** and a window
  minimized before the app was resized comes back filling the new surface.
  `minimizedFrom` is cleared by anything that redefines where the window belongs — an
  explicit `SET_WINDOW_RECT` (which drops `restoreRect` with it), a maximize, a snap —
  and it is persisted, so the round trip survives a reload.
- **Close** runs the existing `closePaneGuarded`, so a dirty pane still prompts.

### Motion

Windows move the way a native window manager's do: short, decisive, decelerating
(`desktop/window-motion.ts`, timings mirrored by `--dur-enter`, `--dur-exit`,
`--dur-move`, `--ease-out` and `--ease-in` in `themes.css`).

| Change | What plays |
| --- | --- |
| A window opens | Fades in from 97% scale and 8px low, 180ms, expo-out |
| A window closes | Fades to 96%, 130ms, accelerating; then it is removed |
| Minimize / restore | Shrinks into its taskbar button (`data-taskbar-instance`) and grows back out; straight down when the taskbar is hidden |
| Maximize, restore-down, a snap, the neighbour snap assist moves | Slides from the old box to the new one, 220ms |
| A tab is picked, a pane opens | The pane's content fades in, 180ms (`.frame-pane-host`) |

- **All of it is the Web Animations API on the window's own element**, so there is
  no animation state in React and nothing to clean up. `DesktopWindow` measures its
  layout box after every render and animates any difference it did not cause
  itself. A drag needs no special case: its last frame and its committed rect are
  the same box.
- **Geometry slides by transform (FLIP), never by left/top/width/height.** A window
  can hold a canvas, a terminal or a browser engine, and resizing those every frame
  costs far more than one composited transform. The content is briefly scaled
  during the slide, as on macOS.
- **Closing waits for the exit** through `setPaneExitAnimator`
  (`core/layout/pane-exit.ts`). `closePaneGuarded` is every close's path, so the ✕,
  keybindings, the taskbar and agent tools all get it. It plays only after the close
  guard has agreed, and a close never waits more than `PANE_EXIT_MAX_MS` (200ms).
  Only a window whose last pane is closing animates; closing one tab of several does
  not.
- **Restored windows do not animate in.** The windows a desktop arrives with at
  startup appear at once. Only windows opened after that
  play an entrance.
- **Resizing the app does not animate.** The layer rescales every window's rect on
  every frame of a resize, so geometry changes within 300ms of one are applied as
  they come.
- **The pane fade is opacity only.** A transform on `.frame-pane-host`, even
  mid-animation, would make it the containing block of every `position: fixed` menu
  inside the pane.
- **Off** with the `desktop.animations` setting (mirrored onto
  `<html data-motion>` for the stylesheet) and whenever the system asks for reduced
  motion. Every change is then instant, closes included.

### Presenting a pane

Maximize fills the window layer, which is inset below the titlebar and above the
taskbar. **Presenting** goes past both: `FrameState.presentedInstanceId` names a
pane, and the stylesheet promotes its window to `position: fixed; inset: 0` at
z-index 48 — over the taskbar and the titlebar, still under the spotlight, so `mod+k`
reaches the user while a game fills the screen.

Four things here are load-bearing.

**The window is promoted in place, never re-rendered somewhere else.** Rendering the
pane into a separate full-screen layer reconciles as a different element and remounts
it — killing a live PTY, socket or browser engine, the exact failure
[pane-lifetime](windowing.mdx#pane-lifetime-unmount-is-not-close) exists to prevent.
The window keeps its position in the React tree and only its CSS changes.

**The keybinding presents the focused window's showing pane** (`presentFocusedPane`,
behind the `area.fullscreen` command, which keeps its old id so saved keymap
overrides still name it).

**The reducer refuses an id that names no pane**, and `sanitizeFocus` clears the id
the moment it stops naming one. Both matter more than the focus equivalents: a stale
id here is not a mis-aimed keybinding but a screen with the chrome hidden and no
visible way out. Closing the pane or its window orphans it — one sweep covers both.

**It is never serialized.** `serialize` deletes the field and `deserialize` forces it
null. It is a momentary way of looking at a pane, not a property of the workspace, and
restoring a layout into a chrome-less full-screen pane is a state the user has to
guess their way out of.

A view opts in with **`fullscreen: true`** (`PanelDecl`/`WidgetDecl`) — `hassault.play`,
`karaoke.stage`, `games.arcade`, `browser.view`, `visualizer.pane`. Only those get the
fullscreen titlebar button (ahead of minimize), and only those escalate to **OS-window fullscreen** on a native
shell. Escalating every presented pane would turn an ordinary "show me this bigger"
into something that swallows the display; and the escalation remembers whether the app
was *already* fullscreen, so leaving a presented game does not drop an app the user had
fullscreened themselves back into a window.

Escape unwinds it through the existing ladder — `installKeymap`'s `exitFullscreen`
calls `presentPane(null)`.

### App-window fullscreen

Distinct again: this is the OS window (or, in the browser, the page), not a pane.
`toggleAppFullscreen` in `core/fullscreen.ts` picks the mechanism — the `windowControl`
seam under Tauri, the DOM Fullscreen API otherwise — so `window.fullscreen` is now
granted in **both** layouts and the browser is no longer stuck windowed.

What the capability does **not** grant is the `f11` binding. `keymap/reserved.ts`
declares that key browser-owned with `preventable: false`, so a binding there would
silently never fire; the key stays gated on the native seam, and the visible controls
are what make the feature reachable in the browser: a `⛶` button in the tray (both
layouts) and a fourth button at the head of the titlebar cluster under
`chrome.workspaceTabs`. Both read live state through `subscribeFullscreen`, because a
control that only re-reads on its own click shows the wrong icon the moment the user
leaves fullscreen any other way — which is most of the ways people leave it.

On the native shell the command **un-maximizes before it fullscreens**, and re-applies
the maximized state on the way out (`enter_fullscreen`/`leave_fullscreen` in
`src-tauri/src/window.rs`). The app window is undecorated, and Windows clips an
undecorated _maximized_ window's client area to the monitor's **work area** so the
taskbar stays usable. That clip survives the switch: the window frame grows to cover
the whole monitor while the webview inside it stays work-area tall — which renders as
a taskbar-shaped black band along the bottom of a fullscreen app, the OS taskbar
hidden behind it. Dropping the maximized state first leaves Windows no work area to
clip against. The previous state is remembered per window label, so someone who
fullscreens a maximized window does not get a small one back.

Un-maximizing on the way *in* is only half of it, because nothing stopped the window
being maximized again once it was already fullscreen — and the band is back the moment
it is. Three routes reached it, and all three are now closed:

| Route                                                     | Fix                                                                       |
| --------------------------------------------------------- | ------------------------------------------------------------------------- |
| The titlebar's maximize button (`window_toggle_maximize`)   | While fullscreen it **leaves fullscreen** instead — the same "restore" the gesture means on a maximized window, rather than a button that does nothing. |
| Double-clicking the titlebar                                | That is `data-tauri-drag-region`, handled **natively inside the webview** — it never reaches a command, so it cannot be guarded in Rust. `TitleBar` stops emitting the attribute while fullscreen. |
| Dragging an edge grip (`window_start_resize_dragging`)      | The command refuses while fullscreen, and `WindowResizeHandles` renders nothing there, so the cursor never suggests the gesture. |

The frontend half is not belt-and-braces: the drag region is the one route with no
server side to guard, so the attribute has to go. The Rust guards cover the same
gestures arriving from anywhere else.

`mode` and `snap` are set through **one** action (`SET_WINDOW_MODE`) rather than
several, so `restoreRect` is written and consumed in a single place.

### Page zoom

Ctrl+= (or Ctrl++), Ctrl+- and Ctrl+0 zoom the whole dashboard the way a browser zooms
a page, and so does Ctrl+wheel. The steps are Chromium's own (50% … 300%).

| Layout  | Who zooms |
| ------- | --------- |
| Browser | **The browser.** Its page zoom already owns those keys, so the app binds nothing — a binding would `preventDefault` a working feature away. |
| Desktop | **`core/zoom.ts`**, through the shell's `window_set_zoom` (`src-tauri/src/window.rs`). Tauri turns WebView2's own zoom keys off, so without this the keys did nothing. The commands are `shell.zoomIn`, `shell.zoomOut`, `shell.zoomReset`, registered only where the seam has `setZoom`. |

Rules that are quiet if wrong:

- **Native zoom, not CSS `zoom`.** Every pane — canvases, CodeMirror, pointer maths,
  the 3D views — sees an ordinary page at a different device-pixel ratio, exactly as
  under browser zoom, so none of them has to know.
- **Native browser panes are separate webviews** placed in *window* pixels, while a
  pane measures itself in CSS pixels, which zoom makes bigger. `tauriWindow.ts` scales
  their bounds by the zoom factor on the way to the shell; the panes' bounds polling
  re-syncs them after a zoom change.
- **Ctrl+wheel yields** to anything that handled the event first: a canvas that zooms
  itself (the model graph) calls `preventDefault` and keeps its gesture. The listener is
  in the bubble phase on `window` for exactly that reason.
- **Remembered per machine** (localStorage, guarded): a zoom belongs to the screen you
  are sitting at, not to your account. It is restored at boot.

## Where it mounts

The window layer is a **sibling of the shell's views**, inside `.shell-content`:

```
.shell
├── TitleBar               ← native shell only: Tauri drag region + window controls
├── .shell-content         (position: relative)
│   ├── Oobe               first run
│   ├── .shell-view        the desktop (backdrop)
│   └── .os-window-layer   ← windows, over both
├── Minibuffer (overlay)
└── Taskbar
```

Sibling rather than child because `.shell-view[hidden]` is `display: none` — a window
layer nested inside the view would vanish with it. Inside `.shell-content` rather than
`.shell` because that bounds the coordinate space below the titlebar, which is what
stops a window titlebar sliding under the drag region.

The layer is `pointer-events: none` with `auto` on each window, so the backdrop
underneath stays clickable.

## Z-index scale

Windows sit above the shell's views and below every overlay that can appear over them.
Declared once, in `packages/ui/src/desktop/desktop.css`:

| Layer          | z-index |
| -------------- | ------- |
| backdrop       | 0       |
| shell views    | 1       |
| window layer   | 30      |
| taskbar        | 40      |
| start menu     | 45      |
| clock panel    | 45      |
| presented pane | 48      |
| spotlight      | 50      |
| toasts         | 9999    |
| dialogs        | 10000   |

A presented pane sits above the taskbar and the titlebar — that is the point of it — but deliberately **below** the spotlight, so `mod+k` still reaches the user while
a game fills the screen. The window layer also drops its `overflow: hidden` while
something is presented, since the promoted window has to escape the layer's box.

On desktop the browser pane's **native child webview composites above all HTML**, so
any overlay that must appear over it calls `suppressNativeOverlays()` — the treatment
the command palette already uses.

## Agent verbs

Split across two groups, deliberately.

**Arranging** lives in the existing `layout` group: `open_window` (give a pane a
window of its own, with `snap` or an exact `rect`), `window_state`
(`minimize`/`maximize`/`restore`/`snap`/`present`/`unpresent` in one schema rather
than six), and `arrange_windows`. Two panes side by side is two snaps, `left` and
`right`.

**Appearance** is its own lazily-loaded `desktop` group: `desktop.set_backdrop`,
`desktop.set_theme`, `desktop.configure_taskbar`. It is not in
the always-on core on purpose. Restyling the desktop is a rare request, the core was
cut 34 → 11 tools for a measured reason (see
[agent-chat.mdx](../modules/agent-chat.mdx)), and anything in the core is paid for on
every turn by every agent — including the ones that never touch it. The group loads
on demand, or when the prompt mentions a theme, wallpaper, backdrop or taskbar.

`get_layout` reports the open `windows`, `desktop.backdrop`, and the
**catalogs** (`desktop.backdrops`, `desktop.themes`) — so the appearance verbs have
ids the model cannot guess without two more always-on `list_*` schemas.

Every one of these refuses bad input **with the valid options** rather than guessing:
an unknown backdrop returns the registered ids, an unknown snap zone returns every
zone in `SNAP_ZONES`.

## Theming

All window and taskbar chrome reads a `--win-*` / `--taskbar-*` token group, so a
theme restyles the whole desktop by redefining tokens and touching no component. The
bevel is why `--win-border-light` and `--win-border-dark` exist as a pair: a retro
theme sets them to contrasting values and gets a raised edge; every other theme sets
them equal and the bevel disappears, with no branching anywhere.

That pair is also why **nothing may set `border-color` on a window**: the shorthand
overrides all four sides and flattens the bevel. Focus is carried by the titlebar
(`--win-titlebar-bg-active`) and the shadow instead. Control placement is not
themeable: minimize, maximize and close sit at the right end of the titlebar in every
theme.

See [theming.mdx](theming.mdx).
