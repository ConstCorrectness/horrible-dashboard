# The desktop shell

The shell presents itself like an operating system: you arrive at a **desktop** with a
backdrop, open things as free-floating **windows**, snap them to edges, and switch
between **desktops**. The tiling frame is not retired — it is one of the two modes a
desktop can be in.

This page covers the desktop: windows as an interaction model, the backdrop, and the
mode switch. The _data_ those windows live in is `FrameState`, documented in
[windowing.mdx](windowing.mdx).

:::info Status
All of it has landed: the window model and its migration, the window layer, the
backdrop providers, the taskbar and start menu, the boot splash and first-run flow,
the spotlight, the four extra themes, the wallpaper routes, and the agent verbs.
:::

## There is one shell view

A desktop **is** a workspace, and whether it shows the tiling frame or free windows
is that desktop's `mode`. So there is exactly one main surface, not two:

```
ShellView = 'boot' | 'oobe' | 'desktop'
```

Both of the old views are gone, for the same reason. `workspace` was never a
surface — making it one meant a single fact (this desktop tiles) had two homes that
could disagree, and switching paradigm became a _navigation_ rather than a property
change. And `home` — the avatar and ask bar — was a second landing screen competing
with the desktop for the same job; it survives as the `splash` **backdrop**, which
is strictly more useful, because windows can float over it.

The consequence worth remembering: flipping a desktop between tiling and floating is
a mount, never a route change, and nothing in the shell "navigates" any more.

Installing the frame engine is correspondingly **not** the tiling frame's job. The
controller the agent tools drive, the debounced autosave, the `frame` module's
commands and workspace hydration all live in `packages/ui/src/layout/install.ts` and
run from the shell. They used to sit in `Frame.tsx`'s mount effect, which was
survivable only while the frame was the only place you could be: once the desktop
became the landing surface, a fresh boot installed none of it — no layout agent
tools, no region or backdrop commands, no hydrated workspace — until the user
happened to visit the workspace. Every one of those failures is silent.

## The two modes

A desktop is either **floating** or **tiling** (`FrameState.mode`), i3-style. It is a
property of the desktop, not a global setting, so "documents tiled on desktop 2,
everything loose on desktop 1" is expressible.

|                   | `floating`                 | `tiling`                     |
| ----------------- | -------------------------- | ---------------------------- |
| Windows           | the primary way panes open | allowed, as the escape hatch |
| Center split tree | retained, not shown        | the main surface             |
| Rails and docks   | hidden                     | shown                        |
| Backdrop          | visible edge to edge       | covered by the frame         |

Windows exist in **both** modes. A floating window on a tiling desktop is deliberate —
it is i3's floating layer, the thing you reach for when a pane should not participate
in the tiling.

### The paradigm belongs to the workspace

You choose it when you **make** a desktop — Start ▸ *New tiled desktop* / *New
floating desktop*, or *Save this arrangement as a desktop* to keep what is on screen
— and you switch paradigms by switching desktops. `createNamedWorkspace(name, {mode,
fromCurrent})` is the one entry point; the agent tool and the commands share it.

This replaced a one-click tray toggle, which invited the one operation the shell
cannot do well (see below): every flip degraded the arrangement a little, so having
both paradigms meant repeatedly paying for a round trip instead of just keeping two
desktops. The tray's ▦/❐ is now an **indicator** that opens a menu; converting in
place is still there, listed last and labelled with what it costs.

**No ambient control flips a desktop.** The tray indicator, the app menu (logo) and
the desktop's right-click menu all open the same `modeMenuItems` list — make a
desktop, save this arrangement as one, and only last, convert in place. There is
also **no keybinding**: `mod+alt+t` used to toggle, and a lossy whole-desktop
rewrite is not something a mistyped chord should be able to do. `desktop.toggleMode`
/ `desktop.tiling` / `desktop.floating` remain as palette commands and agent verbs,
with titles that say sizes are not preserved.

Because the mode is per workspace, the shell adapts to it:

| | tiling desktop | floating desktop |
| --- | --- | --- |
| Top workspace strip | shown — it is the switcher | **hidden** (a desktop has no tab bar) |
| Workspace management | strip's right-click menu, and the Start menu | Start menu |

The taskbar carries **no workspace switcher at all**, in either mode. It briefly had
one — a `desktops` pip zone, auto-injected on a floating desktop by a `zonesForMode`
helper, since that is the mode where the top strip hides itself. Both are now gone.
Switching desktops is a rare, deliberate act, and it does not earn six labels of
permanent strip width in the one place whose width belongs to the panes you actually
have open; the pips could also only *switch*, so anything else still meant opening the
Start menu.

That the Start menu's **Desktops** group both switches and manages (rename, create,
reset, delete) is what made removing them possible — it was the missing half that kept
them alive, and hiding the top strip needed it moved there first.

### What boots

`hydrate()` opens the desktop named by the **`desktop.bootWorkspace`** setting, which
defaults to `desktop` — the empty floating one. Logging in should feel like logging
into a machine, not like resuming whatever you happened to stop on: an experiment on a
tiled workspace three days ago should not decide what you see today. Nothing is lost
either way, since autosave has already persisted that layout and it is one Start-menu
click away.

Set it to `last` for the old behaviour (reopen the active workspace), or to any
workspace or preset id. A preset that has never been visited has no workspace row yet,
so boot creates it from the preset seed the same way `switchWorkspace` does. An id
this build does not know — a deleted workspace, a preset from an uninstalled plugin —
falls back to the last-active desktop rather than stranding you on an empty screen.

:::warning The strip is also the titlebar
Under `chrome.workspaceTabs` the strip **is** the undecorated native window's titlebar
— it carries `data-tauri-drag-region` and the min/max/close cluster. So a floating
desktop cannot simply not render it: it renders a slim bare drag bar
(`frame-tabs--bare`) instead, or the window becomes unmovable and unclosable.
:::

### Flipping a desktop

`setDesktopMode` runs one of two pure conversions in `layout/windows.ts`:

- **`explodeToWindows`** — one window per non-empty center area, carrying its tabs
  whole, positioned at the **pixel rect that area currently occupies**, so the flip is
  visually continuous rather than a pile of cascaded boxes. Docked tools become
  windows too: a visible one at the dock's geometry, a hidden one **minimized** —
  which is the honest analogue, since it was already mounted and reachable from the
  rail rather than on screen.
- **`tileWindows`** — windows return to the center tree in z-order, alternating split
  orientation. A pane whose view belongs in a dock goes back to that dock rather than
  into the document grid, and a minimized window's panes become **background tabs**:
  mounted but not showing, which is what minimized meant.

**The round trip is not lossless, and the code does not pretend otherwise.** Going to
floating cannot express split ratios as anything but the rects they occupy; coming
back cannot recover the ratios you had dragged. What _is_ guaranteed — and what the
tests assert — is that the set of open pane instances is preserved exactly: no pane is
ever dropped and none is duplicated. Everything else is a best effort at continuity.

The registry is consulted by the _caller_, not the model: `setDesktopMode` resolves a
`viewId → DockSide` map and passes it in, keeping `layout/model.ts` and the reducer
registry-free, the same arrangement `seedFromPreset` uses for `regionsFor`.

## Backdrops

A backdrop is a **registered provider** (`BackdropDecl`, contributed through
`ModuleManifest.backdrops` and exported from the SDK), not a settings string — a
wallpaper, a procedural animation, a live node-state view and a full dashboard are
the same kind of thing to the desktop, and a plugin should be able to add one.

| id       | What it is                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| `none`   | Flat `--bg`.                                                                                                        |
| `aurora` | **The default.** Three blurred CSS gradients drifting on a long keyframe, built from theme tokens.                  |
| `grid`   | Canvas: a drifting grid with a scanline sweep. Pairs with `hud`.                                                    |
| `image`  | A wallpaper the user uploaded. `params: { url, fit, dim }`.                                                         |
| `splash` | The old home screen — avatar, ask bar, connector tiles — with windows over the top.                                 |
| `pulse`  | Canvas: one ripple per request through this node, read from the same `telemetryStore` the observability panel uses. |
| `board`  | Widgets laid straight onto the desktop.                                                                             |

Nothing here bundles third-party imagery: the drawn ones are arithmetic, the live
ones render the node's own state, and `image` shows what the user supplied. Same
rule as the maps and the search engines.

A provider declares `interactive` when it wants pointer events (`splash`, `board`).
A decorative one stays `pointer-events: none` and a transparent catcher over it
collects the clicks, so the desktop's right-click menu works across the whole
surface. That catcher is skipped entirely for an interactive backdrop, which would
otherwise be sealed behind it.

**An unregistered backdrop id falls back rather than blanking the desktop.** A
plugin can be uninstalled while a saved workspace still names its backdrop; losing a
wallpaper is not a reason to lose the windows on top of it.

The switch commands (`desktop.backdrop:<id>`) are **synthesized by the registry**,
one per registered provider, exactly as the pane openers are — so a plugin's
backdrop gets its command without a second list that can fall out of step.

### Canvas backdrops

`backdrops/canvas.ts` gathers the three things a canvas backdrop always has to get
right, so a new one cannot forget one:

- **Theme tokens are read through `readThemeTokens` and the effect resubscribes on
  `useThemeId`.** A canvas cannot use a CSS variable, so it resolves colours once —
  and this is a repeat bug in this codebase, so the hook makes it structural.
- **The loop stops on `visibilitychange`.** `requestAnimationFrame` does not fire in
  a hidden window at all, so a loop driving its own clock off frame deltas resumes
  with a multi-minute jump. `dt` is clamped and the clock resets on resume.
- **The backing store follows `devicePixelRatio`**, via `setTransform` rather than
  `scale` — this runs on every resize and `scale` compounds.

`pulse` adds one of its own: events are upserted by `(source, id)` (the backend
re-emits one to fill in a streamed body), so "new" has to mean _a key never seen_,
not "the array got longer". Ripples are placed by hashing the endpoint, so the same
target always pulses in the same spot and the backdrop reads as a map of what this
node talks to rather than as noise.

### Wallpapers

The one piece of the desktop that needs the server, because it is a _file_:
`backend/modules/desktop/` serves `GET`/`POST /api/desktop/wallpapers` and
`GET`/`DELETE /api/desktop/wallpapers/{id}` out of `$HORRIBLE_DATA_DIR/wallpapers/`
(via `backend.paths`, never an inline `os.environ.get`).

Four rules there are load-bearing:

- **The stored extension comes from the content-type table, never the uploaded
  filename.** Trusting the client's extension is how an upload route starts writing
  `.html` into a directory it also serves.
- **The id is 32 hex characters, pattern-enforced at the route boundary**, and
  `_resolve` re-checks that the resolved path is inside the wallpaper directory. The
  pattern is the guard; the check is the assertion that the guard held. A `..` here
  is how a read route becomes an arbitrary-file-read.
- Uploads land via `.part` + rename, so a truncated image is never listed.
- The stored `url` is **api-relative** (`/desktop/wallpapers/<id>`). The backend
  origin differs between the dev server, a packaged desktop build and a LAN-bound
  node, so an absolute URL baked into a saved workspace stops resolving the moment
  any of that changes. The frontend prepends `/api` — `apiUrl` prepends the _origin_
  only, and getting that wrong fails **silently**, because a `background-image` that
  404s simply paints nothing and the desktop looks like the wallpaper was never set.

## The taskbar

`layout/taskbar.ts` derives the buttons, pure over `FrameState` + the registry — the
same shape and for the same reason as `railEntries`. The strip itself is a zone
container driven by the `desktop.taskbar` setting (`start`, `windows`, `mx`, `tray`,
`clock`, `agent`, `spacer`); a stored config is **merged** over the defaults so a
config written by an older build does not silently lose a zone the user never
removed, and an unknown zone name is skipped rather than rendered as an error strip.

**Right-click the strip to customize it** (the `taskbar` context-menu kind): which
zones show, top or bottom, labels, auto-hide, and a reset. The config was always a
setting; what it had no way of being was *edited*, short of typing JSON into the
settings page — which is not something anyone discovers about their own taskbar. The
menu writes that same setting through the same merge, so it and a hand-written value
cannot mean different things. Zones are toggles rather than a reorderable list (a
menu is a poor reordering surface), and a zone switched back on is spliced in at its
canonical position — `zoneRank`, i.e. `ZONES`' own key order — rather than appended
past the clock. _Reset the taskbar_ is the escape hatch that makes hiding everything
safe: a bare strip still right-clicks, so there is no way to customize yourself out
of reach of it.

A stored `zones` array is otherwise taken **whole** — it is an explicit choice, and
quietly adding to it would defeat the point of being able to hide a zone. That leaves
one problem, and `ZONES_VERSION`/`ZONE_SINCE` is the answer to it: a zone introduced
*after* the stored config was written is inserted, and a zone the user actually
removed is not. Without the version the two are indistinguishable, and someone who
customized their taskbar once would never receive another zone again. Bump the
version and add the entry in the same change that adds the zone.

The default zones are `start`, `windows`, `spacer`, `mx`, `tray`, `clock`, `agent`.
There is deliberately no workspace switcher among them — see [the paradigm
section](#the-paradigm-belongs-to-the-workspace).

**`agent` is last, past the clock.** `agent.chat` is a `role: 'tool'` widget, so on a
tiling desktop it has a rail glyph and a dock — but a floating desktop renders
neither, which left the pane you reach for constantly available only through the
palette or the Start menu. The button **toggles** rather than reopening: an
already-open chat goes through `activateTaskbarEntry`, the same verb a window button
runs, so a second click hides it. Calling `openPanel` unconditionally would look like
nothing happened.

**Window buttons are a fixed width** (`--taskbar-btn-w`, 168px), not shrink-wrapped
around their label. Width used to track the text, so the strip was a ragged run of
boxes whose click targets moved whenever a pane retitled itself — an editor button
resizing as you switched buffers. Shrink is still allowed, so a crowded strip tightens
before it starts scrolling, but nothing grows to fit its text; the label ellipsises
inside the fixed box, and with labels off (`is-iconic`) the button collapses to a
square rather than leaving most of a text-width box empty.

The strip must scroll, which is why both it and
the taskbar's window buttons run `useHorizontalWheel`, so a plain vertical wheel moves
them sideways. They are `overflow-x: auto` with the scrollbar hidden, so before that
the overflow was reachable only by trackpad or shift+wheel — on a mouse, the later
tabs simply did not exist. The hook also stamps `data-overflowing` when it measures
real overflow, which is what the edge fade keys off; fading unconditionally dims the
first tab of a strip that fits, and reads as a rendering fault.

### The `mx` zone, and where the minibuffer went

The minibuffer is the **frame's** bottom row, and the frame only mounts on a tiling
desktop. On a floating one it was therefore not merely hidden but absent: `alt+x`
flipped a store that nothing rendered, and — the part that was actually broken —
every `dialogs.prompt()` waited forever on an answer the user was never shown, since
the minibuffer is what serves prompts inline.

So the shell mounts a second instance for the floating desktop,
`<Minibuffer variant="overlay" />`, floating just above the taskbar and rendering
**nothing when idle**. Idle is the whole difference: a permanent status strip is
right as the frame's bottom row and wrong stacked over a taskbar, where it is a
second status bar saying much the same thing. The taskbar's `mx` zone carries the
idle half instead — the M-x button and the echo area — which is also the answer to
"where is M-x?": a keystroke with no visible presence is one nobody finds, the same
argument the tray's fullscreen button already makes.

Two decisions in the derivation matter:

**A button is per pane instance, not per window.** A window merged into three tabs
is three things the user can switch to, and one button for it would make two of them
unreachable from here.

**The order is stable** — by the numeric suffix of the instance id, i.e. by the
order panes were opened. Nothing about focus, z-order or minimizing may reorder it,
because a taskbar that reshuffles on focus moves the button out from under a pointer
already travelling toward it. (Comparing the ids as plain strings would put `#10`
before `#2`, so panes would visibly reshuffle the tenth time you opened one.)

Clicking follows the universal convention, in one verb (`activateTaskbarEntry`):
clicking the thing you are already looking at **minimizes** it, clicking anything
else brings it forward. A taskbar whose focused button does nothing silently
swallows every second click. **Double-clicking always minimizes** (`minimizePane`),
whatever the first click did — a direct "put this away" that does not depend on
what state the button happened to be in.

The taskbar is also what makes minimize usable at all — a minimized window is off
screen, and this is the only route back to it. It is the reason flipping a desktop
to floating is safe: `explodeToWindows` turns hidden dock tools into _minimized_
windows, and without a taskbar those panes would be unreachable.

### Minimizing is not window-only

"Minimize" originally meant `SET_WINDOW_MODE: 'minimized'` and nothing else, so on a
**tiling** desktop — which is most workspaces — the hide half of that verb did
nothing at all: the taskbar listed nine panes and could put none of them away.
`minimizePane` resolves the gesture against where the pane actually lives:

| Where the pane is | What minimize does                                        |
| ----------------- | --------------------------------------------------------- |
| a window          | `SET_WINDOW_MODE: 'minimized'` — the whole window, tabs and all |
| a dock tool       | closes its dock, the same state its rail button toggles    |
| a centre area     | sets `PaneState.minimized` (`SET_PANE_MINIMIZED`)          |

A dock tool deliberately gets **no flag of its own**: its dock's `visible` already is
the hidden state, and a per-pane flag beside it would be a second mechanism for one
visible thing.

#### A pane with nowhere to be drawn is minimized

On a floating desktop the centre tree is retained but never rendered, so a pane
sitting in it cannot be on screen whatever its area says. `taskbarEntries` reports
that as **`minimized`**, and `activateTaskbarEntry` restores it by making it a
**window**.

Without those two, "Dock back into the frame" on a floating desktop was a trap: the
window vanished, the taskbar button stayed, clicking it did nothing, and flipping the
whole desktop to tiling was the only way to see the pane again. The pane was never
closed — it simply had no surface, which is exactly what minimized means everywhere
else in the shell.

Which is also why **dock-back is not offered on a floating desktop at all**: it and
Minimize would produce the same visible result and take the same recovery, so the
window's ⤵ button and the taskbar menu's *Dock back into the frame* are both hidden
when `frame.mode === 'floating'`. Both check the mode rather than assuming it from
"we are drawing a window" — a window on a **tiling** desktop docks back into a frame
that is genuinely there, and keeps the control.

#### Attention: a pane that finished while you were elsewhere

Minimizing is non-destructive, and panes keep working while put away — a deep-research
run, a training job, an ingest, a compile. `requestPaneAttention(instanceId)` sets
`PaneState.attention`, and the pane's taskbar button pulses until the user looks at it.

- **Cleared by `activateTaskbarEntry`, nowhere else.** Looking at the pane is what
  acknowledges it; clearing on a timer or on any focus change would let a button keep
  pulsing after the user had plainly dealt with it.
- **Refused for the focused pane.** Flashing a button for the thing on screen is noise,
  so `requestPaneAttention` returns `false` and changes nothing.
- **A boolean, not a count.** The button is a flash, not an inbox; "three things
  happened" is a story the pane tells once you are in it.
- **Absent rather than `false`** on the pane, so a serialized layout never carries a
  stale "was flashing once" flag for every pane ever opened.
- The accessible name becomes `"<title> — finished"`, because a pulsing border conveys
  nothing to a screen reader; reduced-motion keeps the ring and drops the animation.

A centre pane's flag lives on the pane and it **stays in its area, at its index**.
That is the whole design: the split geometry, the tab order and the area itself all
survive, so restoring puts the pane back exactly where it was. Lifting it out of the
tree instead would collapse a single-pane area, and no verb can rebuild a split — the
pane would come back merged into a neighbour's tab strip and the user's layout would
be quietly worse every time they minimized something.

Two consequences: the tab strip renders `area.tabs` **by index, skipping minimized
ones** (filtering the array would misaddress every tab verb, which all take
positions), and a minimized pane can still be `activeTab` when every tab in the area
is minimized — the area then shows the view picker, which is honest and reversible.
`taskbarEntries` checks the flag before anything else, or such a pane would report as
`focused` and its button would offer to minimize what is already minimized.

The flag is **persisted** (`serialize`), because a minimized pane is part of the
arrangement the user made; reopening a workspace with everything they had tidied away
popped back open is the frame undoing their work on every reload.

The **start menu** lists `registry.panels` + `registry.widgets` minus `embedded`,
filtered exactly as the palette's openers are — an embedded view lives inside a host
pane, and a launcher entry would present it as a second, competing home.

It is **grouped by the owning module** (`registry.viewOwner`) — Browser, Library,
Games — with headings alphabetical and an `Other` bucket, for a view whose module
declares no title, pinned last.

The grouping used to be by **`PaneRole`**: Documents / Tools / Widgets. Sixty-odd
entries in one alphabetical run did say nothing, but the role answers a question
nobody browsing a launcher is asking — it decides where a pane *lands* by default, and
everything in this menu opens and tiles either way. The feature a pane belongs to is
what someone is actually hunting for, and it was already the axis the search box
matched on: a view's title says what the pane is, the module's says what feature it
is part of, and those are frequently different words — the Observability module's pane
is called *Data flow*, so a search for the feature came back empty on a pane sitting
right there under Tools. Promoting the module from a trailing suffix on each row to
the heading above them makes browsing and searching agree, and drops the "Settings ·
Settings" repetition the suffix had to dodge. Searching still flattens the groups —
three headings over four results is more structure than content.

Its **footer** is Settings / Setup / Theme. The bottom-left corner is where people go
for settings, and the menu previously offered it only as one row of sixty, filed under
S. Theme opens the tray's own `taskbar.theme` menu rather than a second list.

## The app menu

The logo at the top-left opens the `shell.app` context menu: Setup, Settings, Theme,
Backdrop, the spotlight, a **Desktops** submenu, and re-running first-run setup.
That submenu is `modeMenuItems()` — the same list the tray indicator and the
desktop's right-click menu open — and it reports which paradigm this desktop is,
rather than offering to flip it. See [the paradigm belongs to the
workspace](#the-paradigm-belongs-to-the-workspace).

It previously ran `shell.home`, which **could not do anything**. `home` is the desktop
now, and the desktop is the only view the logo is ever visible from — so the one piece
of permanent chrome in the corner every OS reserves for its menu was inert. The items
here are the app-level destinations: the ones about the *installation* rather than
about what is on screen.

`shell.oobe` is new and is why "Run first-run setup again" works without a restart.
`desktop.oobeComplete` is read **once**, at mount (reading it reactively yanks the user
back into the wizard the moment the settings store republishes), so clearing the
setting alone did nothing until the next launch — which the setting's own description
had to admit. The command clears it *and* sets the shell view.

The backdrop submenu is shared with the desktop's right-click menu through one
`backdropMenuItems()`; two lists resolved from the same registry are two lists that
drift.

## Boot and first run

`AppRoot` shows the boot splash until `bootReady()`, then mounts the shell. That
gate is **not cosmetic**: `AppShell` installs the frame engine on mount, and that
hydrates the active workspace — which prunes panes whose views are not registered.
Mounting the shell before `boot()` has registered its modules and awaited
`loadPlugins()` would not just look wrong, it would silently delete the user's
layout and then save the result.

The splash narrates the **real** boot (`bootStore`), one step per thing that
actually happened, with real timings. A fake progress bar that always takes 800 ms
says nothing when the backend is not answering, which is exactly the moment the user
most needs to be told something. Individual steps are non-fatal — a plugin that
failed to load degrades the app rather than stopping it — and only a throw sets
`phase: 'failed'`. The step list is time-gated (1.2 s), so a fast boot is a logo and
a fade while a stalled one explains itself without being asked. The progress bar is
deliberately **indeterminate**: the step count is known but their durations are not
remotely comparable, so a real percentage would sit at 90% through the one step that
actually takes time.

First run (`desktop.oobeComplete` unset) goes through a three-step wizard — who you
are, what it looks like, what it can reach — before the desktop. The third step is
the **existing** `SetupCard`, not a copy of it: model / account / connectors already
had one flow with a carefully argued shape (the account and the connectors are two
steps on purpose — see that component), and a first-run duplicate would be a second
thing to keep in step with reality. Every step is skippable, and "Skip setup" leaves
the whole wizard rather than advancing one screen — a setup flow you cannot leave is
one people close the app to escape.

The wizard is a **view, not a modal**. It owns the screen until it is finished or
skipped; a dismissible overlay over a half-configured desktop is exactly the "did I
finish that?" state it exists to avoid.

## Spotlight

`mod+k` opens one surface that takes anything: commands, panes you already have
open, and the agent. It **replaced** the command palette rather than sitting beside
it — the agent is meant to be always available, and two overlays competing for one
keystroke means the user has to decide which one they want before they can start
typing.

`spotlight.ts` resolves the list, pure over the registry + a frame snapshot. Three
things it settles:

- **Open panes rank above commands.** Typing "terminal" almost always means the
  terminal you have, not the command that opens another one.
- **`>` / `@` / `?`** restrict to commands / panes / the agent.
- **The agent is the fallback.** It is offered last when other things matched, and
  first — alone — when nothing did. A palette that answers a typed sentence with "no
  matching commands" is the failure this surface exists to remove. It is _not_
  offered for an empty query, so opening the surface is not a prompt.

An ask keeps the spotlight open, unlike every other action: the answer is the point,
and closing to deliver it somewhere else would mean going to find it.

## Windows

A window's content is an `AreaNode` — the same node the center grid uses — so a plain
window is an area with one tab and a merged window is an area with several. See
[windowing.mdx](windowing.mdx#model) for why that matters.

### Geometry

Rects are **pixels**, against `FrameState.windowViewport`. The window layer measures
itself and owns the single `SET_WINDOW_VIEWPORT` dispatch, because every rect in the
store is relative to that number and exactly one element may be its authority.

Two rules that are bugs if forgotten:

- **The viewport must be re-reported after every workspace load.** `LOAD_WORKSPACE`
  replaces the whole frame with the deserialized one, whose `windowViewport` is
  whatever was stored — null for a fresh or migrated blob. The element has not
  resized, so a `ResizeObserver` alone stays silent, and a migrated v1 window (saved
  on a 1×1 basis) would never scale up into pixels: it would render a few pixels wide.
- **`SET_WINDOW_VIEWPORT` must not bump `revision`.** It is a projection, not an edit.
  Marking it dirty makes every browser resize dirty the workspace and drives the 600 ms
  autosave debounce into a continuous write loop.

Geometry is committed to the store on pointer-**up**; the in-flight rect is local
component state. Dispatching per frame would bump `revision` a hundred times per drag.

Clamping lives in the **reducer**, not the drag handler, so a rect arriving from an
agent tool obeys the same rules as one dragged by hand. `clampRect` keeps a strip of
titlebar on the surface and never allows a negative `y` — a window above the surface
hides its own titlebar behind the app's title strip, where dragging moves the OS
window and the user cannot get it back.

### Snapping

`layout/snap.ts` is pure geometry, shared by the drag preview and the agent's snap
verb so the two cannot disagree — a preview promising one rect while the drop delivers
another is a bug nobody reports precisely.

- Corners are tested **before** edges: inside a corner box the pointer is within the
  edge threshold of two sides at once, and whichever edge test ran first would win
  arbitrarily.
- The **top edge maximizes** rather than snapping to a top half — the near-universal
  convention, and a "top half" is the one snap nobody reaches for.
- Halves and quarters tile the surface exactly; the far half absorbs the odd pixel of
  an odd width, so the two always sum to the full extent instead of overlapping or
  leaving a seam.
- A snapped or maximized window **re-derives** its rect from the zone when the surface
  resizes, rather than being scaled: half of the new surface is exactly half, where a
  scaled rect would carry the rounding of the old one.

The drop decision is resolved **synchronously** during the drag and kept in a ref.
Reading it back from React state at pointerup loses the last frame's zone whenever the
move and the release land in the same frame — an intermittent failure to snap that
only shows up when moving fast.

### Merging and tearing

Dropping a window on another window's titlebar merges them into tabs
(`MERGE_INTO_WINDOW`). The titlebar is marked with `data-window-titlebar` for the
hit-test — and **never** with `data-tauri-drag-region`, which belongs to the app's own
top strip. On a window, that attribute would drag the whole OS window instead of the
window under the pointer.

Dragging a window also **releases keyboard/pointer capture** first. A captured pane —
a game, a terminal, the server-rendered browser — otherwise keeps the pointer and the
drag never reaches the handler.

### Minimize, maximize, close

- **Minimize keeps the pane mounted.** A minimized terminal keeps running and a
  minimized game keeps its socket. See
  [windowing.mdx](windowing.mdx#pane-lifetime-unmount-is-not-close) for the two ways
  this is easy to break.
- **Maximize** stores the rect it came from and restores to it. Capturing a restore
  rect only happens when leaving a _free-floating_ state, so maximizing an
  already-snapped window does not overwrite the rect it was originally dragged to.
- **Close** runs the existing `closePaneGuarded`, so a dirty pane still prompts.

### Presenting a pane

Maximize fills the window layer, which is inset below the workspace strip and above
the taskbar. **Presenting** goes past both: `FrameState.presentedInstanceId` names a
windowed pane, and the stylesheet promotes that window to `position: fixed; inset: 0`
at z-index 48 — over the taskbar and the strip, still under the spotlight, so `mod+k`
reaches the user while a game fills the screen.

Four things here are load-bearing.

**The window is promoted in place, never re-rendered somewhere else.** Rendering the
pane into a separate full-screen layer reconciles as a different element and remounts
it — killing a live PTY, socket or browser engine, the exact failure
[pane-lifetime](windowing.mdx#pane-lifetime-unmount-is-not-close) exists to prevent.
The window keeps its position in the React tree and only its CSS changes.

**`presentPane` is one verb over two mechanisms.** A windowed pane sets
`presentedInstanceId`; a centre or docked pane goes through the existing
`fullscreenAreaId`. Callers — and the keybinding — should not have to know which, and
`fullscreenFocusedArea` reads the focused *window* before the focused area, because on
a floating desktop `focusedAreaId` still names whatever centre area was focused last
and checking it first fullscreens an invisible area of the hidden tiling tree.

**The reducer refuses a pane that is not in a window**, and `sanitizeFocus` clears the
id the moment it stops naming one. Both matter more than the focus equivalents: a
stale id here is not a mis-aimed keybinding but a screen with the chrome hidden and no
visible way out. Closing the pane, closing the window, docking it back, and flipping
to tiling all orphan it — four verbs, one sweep.

**It is never serialized.** `serialize` deletes the field and `deserialize` forces it
null. It is a momentary way of looking at a pane, not a property of the workspace, and
restoring a layout into a chrome-less full-screen pane is a state the user has to
guess their way out of.

A view opts in with **`fullscreen: true`** (`PanelDecl`/`WidgetDecl`) — `hassault.play`,
`karaoke.stage`, `games.arcade`, `browser.view`, `visualizer.pane`. Only those get the
`⛶` titlebar button, and only those escalate to **OS-window fullscreen** on a native
shell. Escalating every presented pane would turn an ordinary "show me this bigger"
into something that swallows the display; and the escalation remembers whether the app
was *already* fullscreen, so leaving a presented game does not drop an app the user had
fullscreened themselves back into a window.

Escape unwinds it through the existing ladder — `installKeymap`'s `exitFullscreen`,
extended to call `presentPane(null)`. Checking only `fullscreenAreaId` there left a
presented pane with no Escape at all.

### App-window fullscreen

Distinct again: this is the OS window (or, in the browser, the page), not a pane.
`toggleAppFullscreen` in `core/fullscreen.ts` picks the mechanism — the `windowControl`
seam under Tauri, the DOM Fullscreen API otherwise — so `window.fullscreen` is now
granted in **both** layouts and the browser is no longer stuck windowed.

What the capability does **not** grant is the `f11` binding. `keymap/reserved.ts`
declares that key browser-owned with `preventable: false`, so a binding there would
silently never fire; the key stays gated on the native seam, and the visible controls
are what make the feature reachable in the browser: a `⛶` button in the tray (both
layouts) and a fourth button at the head of the titlebar cluster under
`chrome.workspaceTabs`. Both read live state through `subscribeFullscreen`, because a
control that only re-reads on its own click shows the wrong icon the moment the user
leaves fullscreen any other way — which is most of the ways people leave it.

On the native shell the command **un-maximizes before it fullscreens**, and re-applies
the maximized state on the way out (`enter_fullscreen`/`leave_fullscreen` in
`src-tauri/src/window.rs`). The app window is undecorated, and Windows clips an
undecorated _maximized_ window's client area to the monitor's **work area** so the
taskbar stays usable. That clip survives the switch: the window frame grows to cover
the whole monitor while the webview inside it stays work-area tall — which renders as
a taskbar-shaped black band along the bottom of a fullscreen app, the OS taskbar
hidden behind it. Dropping the maximized state first leaves Windows no work area to
clip against. The previous state is remembered per window label, so someone who
fullscreens a maximized window does not get a small one back.

`mode` and `snap` are set through **one** action (`SET_WINDOW_MODE`) rather than
several, so `restoreRect` is written and consumed in a single place.

## Where it mounts

The window layer is a **sibling of the shell's views**, inside `.shell-content`:

```
.shell
├── WorkspaceTabs          ← saved layouts + Tauri drag region + app controls
├── .shell-content         (position: relative)
│   ├── .shell-view        home
│   ├── .shell-view        workspace (the frame)
│   └── .os-window-layer   ← windows, over both
└── (taskbar)
```

Sibling rather than child because `.shell-view[hidden]` is `display: none` — a window
layer nested inside a view would vanish the moment you went home. Inside
`.shell-content` rather than `.shell` because that bounds the coordinate space below
the workspace strip, which is what stops a window titlebar sliding under the drag
region.

The layer is `pointer-events: none` with `auto` on each window, so the backdrop and
the frame underneath stay clickable.

## Z-index scale

Windows sit above the shell's views and below every overlay that can appear over them.
Declared once, in `packages/ui/src/desktop/desktop.css`:

| Layer          | z-index |
| -------------- | ------- |
| backdrop       | 0       |
| shell views    | 1       |
| window layer   | 30      |
| taskbar        | 40      |
| start menu     | 45      |
| clock panel    | 45      |
| presented pane | 48      |
| spotlight      | 50      |
| toasts         | 9999    |
| dialogs        | 10000   |

A presented pane sits above the taskbar and the workspace strip — that is the point of
it — but deliberately **below** the spotlight, so `mod+k` still reaches the user while
a game fills the screen. The window layer also drops its `overflow: hidden` while
something is presented, since the promoted window has to escape the layer's box.

On desktop the browser pane's **native child webview composites above all HTML**, so
any overlay that must appear over it calls `suppressNativeOverlays()` — the treatment
the command palette already uses.

## Agent verbs

Split across two groups, deliberately.

**Arranging** lives in the existing `layout` group: `open_window` (with `snap` or an
exact `rect`), `dock_window`, `window_state`
(`minimize`/`maximize`/`restore`/`snap`/`move_to_desktop` in one schema rather than
five), and `arrange_windows`. `move_pane` also gained `edge`, which splits the
destination and drops the pane into the new half — the fix for the long-standing gap
where a pane opened into the wrong place could not be moved beside another one at
all. `edge` **alone** is a valid call: it means "split where this pane already is".

**Appearance** is its own lazily-loaded `desktop` group: `desktop.set_backdrop`,
`desktop.set_theme`, `desktop.set_mode`, `desktop.configure_taskbar`. It is not in
the always-on core on purpose. Restyling the desktop is a rare request, the core was
cut 34 → 11 tools for a measured reason (see
[agent-chat.mdx](../modules/agent-chat.mdx)), and anything in the core is paid for on
every turn by every agent — including the ones that never touch it. The group loads
on demand, or when the prompt mentions a theme, wallpaper, backdrop or taskbar.

`get_layout` reports `desktop.mode`, `desktop.backdrop`, the open `windows`, and the
**catalogs** (`desktop.backdrops`, `desktop.themes`) — so the appearance verbs have
ids the model cannot guess without two more always-on `list_*` schemas.

Every one of these refuses bad input **with the valid options** rather than guessing:
an unknown backdrop returns the registered ids, an unknown snap zone returns the nine
zones.

## Theming

All window and taskbar chrome reads a `--win-*` / `--taskbar-*` token group, so a
theme restyles the whole desktop by redefining tokens and touching no component. The
bevel is why `--win-border-light` and `--win-border-dark` exist as a pair: a retro
theme sets them to contrasting values and gets a raised edge; every other theme sets
them equal and the bevel disappears, with no branching anywhere.

That pair is also why **nothing may set `border-color` on a window**: the shorthand
overrides all four sides and flattens the bevel. Focus is carried by the titlebar
(`--win-titlebar-bg-active`) and the shadow instead. Control placement (left vs
right) is a flex `order` token, not a JS branch.

See [theming.mdx](theming.mdx).
