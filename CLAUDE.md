# horrible-dashboard

A unified one-stop app for everything — "emacs for the agentic era". One web UI serves
two layouts: a browser app and a cross-platform desktop app (Tauri shell wrapping the
same frontend).

## Current state

Scaffolded and verified: pnpm monorepo (apps/web, apps/desktop, packages/core,
packages/ui), FastAPI backend, the **dashboard module** end to end, and the
**agent module** — a Gemini-style `home` view (default on open) with
3D avatar, local-model onboarding via Ollama (default `gemma4:e2b`), and an ask
bar wired to the **agent orchestrator**: a backend tool-calling loop (Ollama
`/api/chat` with tools) that drives the UI — first slice is **layout control**
(open/close panes, manage workspaces) with tool calls relayed to the frontend
over the shared `/ws` `agent` channel. See docs/modules/agent-chat.mdx. The `workspace` view is a **dockable window manager** (dockview,
wrapped): module **panes — panels and widgets alike** — open as tabbed/split/
floating windows. **Widgets are first-class panes** (no separate grid); the
**dashboard is the default seeded one of several named workspaces** you switch
between via a tab strip, each layout persisted server-side. A minimal `scratch`
panel is the reference non-singleton panel. A `clubhouse` module onboards a
Clubhouse account via a widget (unofficial API, token held server-side). An `observability` module shows live data flow
(client/inbound/outbound I/O) — instrumented at the chokepoints, streamed over
the shared `/ws` socket. A **public plugin SDK** (`packages/sdk`,
`@horribledashboard/sdk`) plus a `marketplace` module let third-party frontend plugins
(panels/widgets/commands/keybindings) be installed from a catalog and loaded at
boot — see docs/architecture/plugin-sdk.mdx. A **backend plugin SDK** (`backend/sdk`,
`backend.sdk`) is the server-side counterpart: plugins contribute HTTP routes,
agent tools, `/ws` channels, lifespan hooks, and `dash` REPL facades, discovered
from bundled dirs, `HORRIBLE_PLUGINS_DIR`, and pip entry points — see
docs/architecture/backend-plugin-sdk.mdx. The **`dash`** Python REPL handle scripts
the running app (panes/workspaces/layout/I-O/settings; `dash.help()`) — see
docs/architecture/python-sdk.mdx. A `settings` module gives a
VS Code–style settings page where any module or plugin contributes its own
settings (declared in its manifest, read live via `useSetting`/`host.settings`,
overrides persisted server-side) — see docs/modules/settings.mdx. Note `GET /api/settings` returns the whole bag to the browser, so a **client secret / API key must never be a setting** (a client id is fine — it's public). A **connectors** module is the integration surface: external accounts the node holds credentials for, rendered as a **row of tiles above the ask bar on the home page**. A connector owns its connect flow (`oauth` device/redirect, `api-key`, or a `custom` multi-step form), its credential (Fernet-encrypted in `secrets.db` under `connector:<id>`, **never handed to the browser**; the master key lives outside `$HORRIBLE_DATA_DIR` at `~/.horrible/secrets.key` so copying the data dir leaks nothing), and the agent tools it unlocks. Contributed via `host.add_connector` (`backend/sdk`), so backend plugins register like built-ins. **GitHub is implemented** (device flow — OAuth Apps have no PKCE, so an authorization-code flow would mean shipping a secret; `read:user`+`repo`; `github.searchCode/searchRepos/listRepos/readFile/listIssues`). **Google is implemented** (loopback authorization-code + **PKCE**, because Google's device flow can't carry `drive.readonly`; scope is Drive read-only only; `google.driveSearch/driveRead/syncDrive`) and is deliberately **bring-your-own-client** — `drive.readonly` is a Google _restricted_ scope, so a published app would need verification + an annual CASA assessment, and an app in Testing expires refresh tokens after **7 days**; with your own Cloud project you're your own sole test user. `google.syncDrive` / `POST /api/connectors/google/sync` walks Drive into a **library** as `note` sources (Google Docs exported, PDFs parsed with **pypdf** — _not_ PyMuPDF, which is AGPL), paginated and **incremental** via Drive's `changes` feed, with a `google_drive_files` map in `app.db` so a re-sync replaces rather than duplicates. A connector's `id` **must** equal its agent-tool prefix — the orchestrator groups tools by name prefix, and `AgentTool.group` does _not_ name the group. Distinct from the games sign-in, which is identity-only: it runs on the separate game server and discards the provider token — see docs/modules/connectors.mdx. A **database** module is a plug-and-play, psql-like database inspector: a query console pane that reaches any connected database through a pluggable driver layer. Drivers declare a **dialect**: `sql` (sqlite / postgres+pgvector / duckdb / mysql / **oracle**, incl. 23ai AI Vector Search) or `json` (**lancedb / chroma / qdrant / weaviate**), because vector stores have no SQL dialect — a collection, a metadata filter and a query vector is all they take, so the console sends a native JSON operation body (`{"op": "search", …}`) rather than faking SQL over them. Both dialects return the same columns/rows grid. Two built-in connections: `app` (the node's SQLite database, `$HORRIBLE_DATA_DIR/app.db` — library sources, browser history, code symbols, tasks) and `vectors` (the app's own **LanceDB** store under `$HORRIBLE_DATA_DIR/lancedb`, one table per collection, also used by agent-commons matchmaking). LanceDB is a _directory_, not a SQL-attachable file — that's precisely why it needed a json-dialect driver to become queryable. A similarity `score` is only derived for **cosine** spaces; Chroma and LanceDB default to squared L2, where `1 - distance` is negative and meaningless, so those show raw `distance` instead. Non-core clients are optional extras (`uv sync --extra chroma|qdrant|weaviate|vectordb|oracle`), lazy-imported. See docs/modules/database.mdx. A **library** module is a personal knowledge base built on that vector store: ingest website blogs (by URL, extracted with trafilatura), notes, and **images/videos** (PDF/EPUB deferred) as **sources + chunks** — a `library_sources` catalog in `app.db` plus per-chunk rows in the library's LanceDB table — then semantic-search a library for RAG, with live ingestion status on the `library` `/ws` channel. The default embedder is **text-only**, so media is embedded by _proxy_ (alt text, caption, nearby heading harvested from the live DOM) and referenced by URL rather than copied. Optional **CLIP visual search** (`uv sync --extra clip` + the `library.clipEnabled` setting) adds a second space so media is findable by _appearance_ — undescribed images included: a 512-dim ViT-B/32 ONNX vector in an additive `<library>__clip` sibling table (LanceDB fixes vector width per table), fused with the text hits by Reciprocal Rank Fusion. The agent tools (`library.search/listSources/addSource`) are the retrieval half of RAG; `browser.save` is the write half — see docs/modules/library.mdx. A **visualizer** module renders HTML5 Canvas, Three.js, and Babylon.js dynamic client-side animations, and streams headless Pygame frames from backend subprocesses — see docs/modules/visualizer.mdx. A **browser** module is an **embedded web browser** pane with two engines: a light cross-origin `<iframe>` (default), and — opt-in via `HORRIBLE_ENABLE_SERVER_BROWSER=1` + the `browser-engine` extra — a **real headless Chromium** driven on the local backend and server-rendered to the pane (JPEG frames over `/ws`, interactions relayed back, persistent cookies/cache), built **agent-first**: the same live session backs the human panel and the agent tools (`browser.read`/`snapshot`/`scrape`/`click`/`type`/`media`/`save`), so the agent is handed the DOM content + an accessibility snapshot and can scrape, act, and **remember** — `browser.save` files a page or its images/videos into a library (the write half of RAG). Every request the Chromium makes is recorded as a `browser` I/O event (resource type + allowed/blocked egress verdict) and shown live in the pane's 📡 Network view and the observability panel. That view is now **four views, passive to active**: a CDP session harvests the per-request DNS/TCP/TLS/TTFB timing, peer IP, HTTP version and certificate Chromium already measured and Playwright hides (**Waterfall** — phases that didn't happen are drawn as nothing, because a reused connection genuinely has none; CDP's `-1` sentinel is a trap); **DNS** walks the delegation from the root servers down over plain UDP/53 (no privileges needed), showing referrals, glue, DS records, and restarting the walk on a CNAME; **Route** shells out to the system `tracert`/`traceroute` (raw ICMP needs admin) and plots locatable hops on a bundled SVG world map with no tile provider. Probe targets go through the same public-IP check as the fetch guard. Egress is SSRF-guarded; reader mode + bookmarks/history persist server-side — see docs/modules/browser.mdx. A **search** module is the open-web discovery layer: pluggable engines (Tavily/Brave/Exa/Serper by API key, a self-hosted **SearXNG**, and a keyless DuckDuckGo fallback so search works with zero configuration) behind one `SearchProvider` protocol, plus an AI layer of our own on top — query fan-out, canonical-URL dedupe, **Reciprocal Rank Fusion** (extracted from the library's hybrid search; fusion is rank-based because provider scores are incomparable units), guarded fetch+extract of the top hits, and an embedding rerank that **refuses to run on hash-fallback vectors**. `quick_search` (sub-second) vs `deep_search` (2–8s) is a latency contract, not a quality knob — an eight-second tool call mid-chat-turn is unusable, which is why `search.web` and `search.deep` are separate tools. API keys live in a single `search` **connector** (Fernet-encrypted, never a setting); the engine _name_ is a setting because it's public. SearXNG is AGPL so it is **supported, never bundled** (the pypdf/SingleFile precedent). A **focused crawler** indexes a curated seed list of ML sites, blogs and API docs into a dedicated `webindex` LanceDB collection — not a user library, which it would swamp — and is exposed as _just another provider_, so local hits fuse with live web hits for free. Re-crawls are near-free via three skip levels (304 → unchanged content hash → real change); the frontier is seeded from previously-indexed URLs, because a 304 on the start page yields no HTML and so no links. Writes batch **across pages** (`merge_insert` is a whole-table ~1.5s operation). Egress differs by leg and is the easy thing to get wrong: vendor APIs and the settings-supplied SearXNG URL go over plain httpx (loopback allowed for the latter), while **every result URL and crawled URL** rides `_fetch_guarded`. See docs/modules/search.mdx. A **network** module is the **distributed peer fabric**: a process-global `PeerHub` lets this backend node connect to other users' nodes over TCP/IP (hybrid direct/relay/LAN transports, Ed25519 node identity, settings-driven trust), so users collaborate via **agent-to-agent** (`agent.ask_peer` — your agent asks a peer's agent, gated read-only by default) and **collaborative shared panes** (a `collab` channel; scratch is the reference) — see docs/modules/network.mdx and docs/architecture/distributed.mdx. A **social** module is the human face of that fabric: a friends roster keyed by **person**, not machine. A second Ed25519 **person key** yields a `person_id` (same `base32(sha256(pubkey))[:16]` scheme as a node id), rendered as a checksummed **friend code** (`HD-XXXX-…`); each machine carries a **device certificate** signed by the person key, so one human with three boxes is one roster row. Verifying a cert has a third step `verify_device_cert` deliberately leaves to its caller — that the cert names _the node it arrived from_ — and skipping it lets anyone replay a friend's cert to impersonate them. **Accepting a friend grants fabric trust** to every one of their devices, which is exactly what makes peer chat, shared panes, and `agent.ask_peer` work between friends with no second pairing; friendship grants reachability, not authority (a remote agent turn is still gated by `network.allowRemoteAgent`). The roster is **local** (`social_friends`/`social_devices` in `app.db`) so it survives any directory going away, and presence is _derived_ from the hub's connection table, never stored. Note `resolve_person_id` tells a friend code from a bare id by **length**, not by whether the checksum passes — falling back to "treat it as a raw id" on failure would defeat the checksum and dial a mistyped code as if it were real. Discovery off the LAN goes through an **Atlas presence directory** (`social/directory.py`, collection `presence`): person*id → dialable addresses, self-published and **signed by the person key**, so a hostile directory can withhold a record but never point you at an impostor. The social *graph* is never written to Atlas — only "where is this person right now" — so losing the cluster downgrades discovery, never the roster. A record publishes the full **ICE candidate list**, not `advertised_address()` alone: that helper auto-detects the **LAN** IP, so publishing it by itself yields a record useless to anyone off your network — the public (STUN reflexive) candidate only appears with `network.iceEnabled` on. `_dial` consults it **last**, after known LAN addresses. The shared client is `backend/atlas.py` (not inside a module — hassault needs the same cluster), configured by `ATLAS_DB_USER`/`ATLAS_DB_PASS`/`ATLAS_CLUSTER_HOST` in `.env` — **env only, never settings**. Note `.env` is now loaded by `backend/__init__.py` too, because `scripts/dev.mjs` loaded it but the documented bare `uv run uvicorn` command did not, so credentials silently varied by launcher. See docs/modules/social.mdx. A **hassault** module (**HorribleAssault**) is an AssaultCube remix as a dashboard pane — our own client and netcode replacing its ENet/master-server stack. Implemented so far: the **map pipeline**, a port of `load_world`/`rldecodecubes` reading `.cgz` (Cube 1 worlds are a flat grid of columns, not BSP — which is why a Three.js rewrite is tractable). Content is **supported, never bundled**: AssaultCube's media is copyright (source is zlib-like), so maps are read from the user's own install via `hassault.installPath`, auto-detected if blank — same precedent as SearXNG. Four format traps, all pinned by tests: entities start at `headersize`, **not** at the 980-byte struct end (every official 1.3 map carries a 3–6 KB extra-header block between them); a `SOLID` record stores only wtex+vdelta and the rest must come from `sqrdefault`; **v10 scales angles ×10** (verified across all 1741 official spawns, not assumed); and a truncated cube stream is filled with defaults, not rejected. The 65536-cube grid ships as **nine raw byte planes** (`/maps/{name}/cubes`), not JSON — `floor`/`ceil` are signed — with `plane_order` reported by the metadata route so the two sides can't drift. The **renderer** (`hassault.play` pane) is also implemented: three is lazy-loaded, and `world.ts`/`geometry.ts`/`player.ts` never import it so they stay unit-testable headless. Two heightfield rules are easy to get backwards and both are pinned by tests — the **base height comes from the cell while the delta comes from the corner-vertex cell** (taking both from the vertex cell tears heightfields apart at every seam, silently), and the divisors differ on purpose: `vdelta/4` per render vertex vs `(sum of 4)/16` for the height a body stands on. Walls are emitted **from the open side only**, so each surface exists once and needs no back faces; an overhang uses `utex`, not `wtex`. Collision uses the circle's AABB like AC's `rectcollide`, so the player is **2.2 cubes wide and needs 3 cells of clearance**; movement resolves one axis at a time (or corners go sticky) and `dt` is clamped (a backgrounded tab otherwise teleports you through walls). No textures yet — surfaces are tinted by texture id, because texture slots are resolved via map `.cfg` files that aren't parsed. The **netcode** is implemented too: an authoritative match server (`match.py`) simulating on a `hassault` `/ws` channel, with client prediction, reconciliation and remote-player interpolation (`net.ts` pure/testable, `session.ts` holding the socket). Because the server must simulate, the physics exists **twice** — `backend/modules/hassault/physics.py` is a port of `world.ts`+`player.ts` — and the duplication is made safe the way the Kotlin wire is, with vectors both suites replay (`packages/core/src/modules/hassault/__tests__/physics-vectors.json`, carrying both `cases` for movement and `spawns` for placement); the fixture pins *agreement*, each side's unit tests pin correctness. A **`playerstart`'s `z` is not a ground height** — it's the mapper's *eye* at placement time (the modal distance to the floor is exactly 4 = `(int)(floor+4.5)`) and AC's editor flies, so the rest scatter 1–22 cubes up; `spawn_at` therefore takes the height from `_support`, the same query `step` resolves against, making a spawn the fixed point of the first frame. Reading it as a lower bound (`max(floor_at, spawn.z)`) put all 1741 official spawns in mid-air — the clamp fired at only six of them. Three things that look optional and are not: every input carries a **sequence number** and snapshots carry a **per-recipient `ack`** (prediction has nothing to replay without it); the server advances a player only on **that player's own commands with their own `dt`** (ticking by wall clock leaves a permanent jitter even when the prediction was right); and client-supplied `dt` is spent from a **replenishing budget** (~1.1× real time, 0.25s reservoir), which is the only thing stopping a client claiming time faster than it passes. Deliberately **no noclip on the wire**. Wire format is JSON on the shared socket, not binary — 20 Hz × 8 players ≈ 10 KB/s, and legibility in the observability panel is worth more than the bytes. **Cross-node matches** ride the peer fabric (`fabric.py`, wire types declared there not in `network/protocol.py`): a guest's own backend proxies for them, and a remote player is a `PeerPlayerConn` exposing just `send_json`, so `MatchRoom` never learns some of its players aren't browsers — and the guest backend reshapes the host's `welcome` so the browser has one code path, not two. Three things that are load-bearing: every inbound peer message is gated on `session.info.trusted` (knowing a room id is not friendship), remote input goes through the **same** validator as a browser's (a laxer second one is where the gap appears), and a dropped peer's players must be swept — they have no browser socket, so nothing else would ever notice they left. Invites go to **every** online device of a person (you invite a human, they pick a box); `GET /api/hassault/invitees` does the roster join backend-side so the pane never imports across a module boundary. **Weapons** are implemented (`weapons.py`): five of them, server-authoritative hitscan, and firing is a **flag on a movement command** — never its own message — so a shot carries the exact angles/seq of its frame, the rate limiter spends from the same time budget as movement, and the fabric carried weapons to remote matches with zero changes. Hit registration is **lag-compensated**: the client stamps each shot with `viewT` (`SnapshotBuffer.renderTime` — the server-clock instant it was rendering) and the server rewinds a 1s position history to match. That target is client-supplied, so **the clamp is the security boundary**, not tidiness: `PositionHistory.clamp` pins it to `[now-500ms, now]` — it's deliberately *not* range-checked in the wire parser, which doesn't know the time. Two rules do outsized work: a body is only a target if it's **nearer than the wall** (that comparison is the whole of cover), and a negative entry distance with a positive exit is **point blank, not a miss**. Fire rate/reloads run on the budgeted *simulated* clock (commands arrive batched, so a wall-clock gate silently halves a 700rpm rifle), while respawn timers use the wall clock (a dead player sends no commands). Health is public in the shared rows; **ammo is per-recipient** and hitmarkers drain when that envelope is built. Shots batch into the snapshot's `fx` — combat costs the tick rate, not the fire rate. Recoil is client-side (angles are client-owned anyway), the same concession as trusting `dt`. Weapon numbers are **served** (`GET /api/hassault/weapons`), never duplicated in TS — the `plane_order` precedent. **Bots** (`bots.py`) are not a second entity: a bot is a `MatchPlayer` whose input is produced here, enqueued through the same `enqueue`, so there's one simulation and a bot can't do what a player can't. No navmesh — it probes with the movement code's own `can_stand` and checks LOS with the same `raycast_world` a shot traces. Aim is wrong on purpose (rate-limited turn + wandering error), and the trigger fires when the barrel is where the bot *thinks* it's aiming — comparing against the true bearing instead yields a bot that never misses. Bots don't keep a room alive (the empty clock tracks humans), removal is newest-first by **insertion order** (Windows `monotonic` has ~16ms granularity), and they're host-only. Agent tools (`hassault.list_maps/list_matches/host/invite/status/surroundings/add_bot/remove_bot`) run the social side of a game and deliberately **stop short of playing** — 60 Hz input is a bot controller, not a tool; the agent fields bots rather than steering one. Still missing: textures, ammo pickups, weapon models/sounds, game modes beyond deathmatch. See docs/modules/hassault.mdx. A **mobile-android** companion app (`apps/mobile-android/`, Kotlin + Compose) rides that same fabric: it pairs by scanning a QR invite and then appears as an ordinary peer carrying a `mobile` capability — remote control of panes/media (`remote_command`, `backend/modules/network/remote_control.py`), streaming agent chat, and `mobile.*` agent tools pointing back at the phone (`mobile*tools.py`). Because it **reimplements the signed-envelope wire in Kotlin**, two contracts are byte-exact and fail silently (a closed socket, no error) when they drift: the node id is `base32(sha256(pubkey))[:16]`— \_not* base64url — and the signed canonical JSON must match Python's`json.dumps(sort_keys=True, separators=(",",":"))`exactly, which means recursively sorted keys,`ensure_ascii`, an always-present `re`(even as null), and Python's float`repr`(Java's`Double.toString`goes scientific at 1e7, Python at 1e16, and every envelope's`ts`sits in that gap).`backend/tests/test_network_mobile_conformance.py`pins those vectors. The invite QR embeds`trust.advertised_address()`, which auto-detects the **LAN IP** — `localhost`makes every invite undialable from a phone — and the backend must be bound with`pnpm dev:lan`. See docs/modules/mobile-android.mdx. An experimental Electron shell lives on the `electron-shell`branch. The deep-research pipeline runs`plan → [subagents → critique]\* → synthesis → verify → citations → export`: **gap-filling rounds** (the critique names what's missing and spawns a targeted wave; the round is derived from the DB so a restart resumes correctly), a **verification pass** grading claims by \_independent publisher\* — three citations to one domain count as one source — plus a contradiction check, and **steering** (park before subagents run to edit the plan, inject follow-ups mid-run, live per-subagent tool traces). Note `init_research_db` is `CREATE TABLE IF NOT EXISTS`, so new columns need `_ensure_column` or an upgraded install silently never gets them. Remaining modules (editor, terminal, files, full chat cockpit) are unimplemented — see docs/ for their designs.

## Stack (decided, do not re-litigate)

- **Frontend:** React + TypeScript, Vite, pnpm workspaces
- **Desktop shell:** Tauri (Rust) — wraps the same frontend as the browser build
- **Backend:** Python 3.12 + FastAPI, managed with `uv`. The backend is the app's
  brain: agents, data, MCP integrations, websockets to the UI.
- **Extensibility:** built-in modules first. Every feature (chat, dashboard, notes,
  terminal, files) is an internal module registered through a central registry
  (commands, panels, keybindings). The public plugin API (`@horribledashboard/sdk` +
  marketplace) exposes the same contract to third-party frontend plugins, and
  `backend.sdk` exposes a server-side contract for backend plugins (routes, agent
  tools, `/ws` channels); both are trusted/unsandboxed in v1 — see
  docs/architecture/plugin-sdk.mdx and docs/architecture/backend-plugin-sdk.mdx.

First modules, in priority order: agent chat cockpit, dashboard/widgets, notes/editor

## Commands

- `uv run pytest` — backend tests
- `uv run uvicorn backend.app:app --reload --reload-dir backend --reload-exclude "logs/*" --port 8000` — backend dev server (the `--reload-dir`/`--reload-exclude` scoping keeps `logs/backend.log` writes from triggering a reload loop)
- `uv run ruff format .` and `uv run ruff check --fix .` — Python format/lint
- `uv add <pkg>` / `uv add --dev <pkg>` — Python dependencies (never pip)
- `uv sync --extra games-native` — install the native ViZDoom engine (the `vizdoom_toy` / `vizdoom_duel` games). It's an **optional extra** (lazy-imported), so the core app installs on every OS without it; add it only to run a Doom table locally. Prebuilt wheels: Windows amd64, Linux x86_64/aarch64, Apple-Silicon macOS 14+ (Intel/old macOS builds from sdist — needs `brew install cmake boost sdl2 openal-soft`). The Fly game-server image already pulls it.
- `uv sync --extra clip` — install **CLIP visual search** for the library (index media by appearance, not just alt text). Another **optional extra** (lazy-imported, gated by the `library.clipEnabled` setting): ONNX Runtime rather than torch, so it's ~60 MB and installs everywhere; the ViT-B/32 weights (~350 MB) download once on first use. Existing media needs `POST /api/library/reindex-clip` to backfill.
- `uv sync --extra geoip` — install **DB-IP GeoIP lookup** so the browser's Route view can plot traceroute hops on a map. Optional and lazy-imported; the DB-IP Lite City database (CC-BY, freely redistributable — unlike MaxMind GeoLite2, which needs an account and a license key) is downloaded once to `$HORRIBLE_DATA_DIR/geoip/dbip-city.mmdb`. Without it hops still list, they just have no coordinates.
- `uv sync --extra browser-engine && uv run playwright install chromium` — install the real headless-Chromium engine for the **browser** module's "full mode" (server-rendered, agentic). Also an **optional extra** (lazy-imported); the `playwright install` step fetches the ~150 MB per-OS Chromium once. Gated at runtime by `HORRIBLE_ENABLE_SERVER_BROWSER=1` — without the extra or the flag, the browser stays in the light iframe mode.
- `pnpm dev` — browser layout, full stack: starts the backend, the Vite UI (port 5173,
  proxies /api and /ws to 8000), **and** the central game server (:9200) together via
  `scripts/dev.mjs`. `--no-gameserver` (or `HORRIBLE_DEV_NO_GAMESERVER=1`) skips the
  game server. `pnpm dev:web` is UI-only; `pnpm dev:lan` exposes both on 0.0.0.0 (peer fabric).
- `pnpm dev:desktop` — desktop layout (Tauri; **spawns/supervises the backend
  itself** via `src-tauri/src/backend.rs` — reuses one already running on :8000)
- `pnpm typecheck`, `pnpm lint` — whole workspace, from the root
- `cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml` — Rust check
- **Android companion:** open `apps/mobile-android/` in Android Studio and run `app`.
  There's no committed Gradle wrapper yet, so there is no CLI build; `local.properties`
  is git-ignored (machine-local `sdk.dir`). The phone reaches the backend only when it's
  bound to the LAN (`pnpm dev:lan`) and the backend port is allowed through the firewall.

## Conventions

- TypeScript strict mode; no `any` without a comment explaining why.
- Pydantic models for every API boundary; the backend is the source of truth for
  shared types.
- New features go through the module registry — a module declares its commands,
  panels, and keybindings in one place; nothing reaches into another module's
  internals. See `.claude/skills/new-module/SKILL.md` before adding a feature.
- Browser and desktop layouts share one codebase; never fork a component per
  platform — branch on a platform capability check instead.
- Formatting/linting is automatic: a PostToolUse hook runs ruff (Python), prettier +
  eslint (TS/JS), and rustfmt (Rust) on every file you edit. Don't hand-format.
- **Clubhouse App Versioning:** The Clubhouse API requires a current Android app version header (e.g. `26.07.12`). If auth fails with `login did not pass token validation`, update `AppVersion` in `backend/modules/clubhouse/auth_helper/Program.cs` and `routes.py`, then delete `backend/modules/clubhouse/auth_helper/bin/ch-auth-helper.exe` so the backend forces a recompile.

## Documentation (docs/)

`docs/` documents the layout shell and every module — see
[docs/README.mdx](docs/README.mdx) for the index and the full sync policy. The short
version: adding or changing a module, panel, command, capability, backend route, or
layout-shell behavior must update the matching `docs/` page **in the same change**
(new module → new `docs/modules/<name>.mdx`). A Stop hook flags code changes under
`apps/`, `packages/`, or `backend/` that don't touch `docs/`; pure refactors are
exempt — just say so.

The docs are authored as **MDX with Mermaid diagrams** and published as a
[Docusaurus](https://docusaurus.io) site (`website/`, which reads this `docs/`
tree directly). `pnpm --filter @horrible/docs build` builds it locally; pushing to
`main` deploys to GitHub Pages via `.github/workflows/docs.yml`.
