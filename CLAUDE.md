# horrible-dashboard

A unified one-stop app for everything — "emacs for the agentic era". One web UI serves
two layouts: a browser app and a cross-platform desktop app (Tauri shell wrapping the
same frontend).

## Current state

Scaffolded and verified: pnpm monorepo (apps/web, apps/desktop, packages/core,
packages/ui), FastAPI backend, the **dashboard module** end to end, and the
**agent module** — a Gemini-style `home` view (default on open) with
3D avatar, local-model onboarding via Ollama (default `gemma4:e2b`), and an ask
bar wired to the **agent orchestrator**: a backend tool-calling loop (Ollama
`/api/chat` with tools) that drives the UI — first slice is **layout control**
(open/close panes, manage workspaces) with tool calls relayed to the frontend
over the shared `/ws` `agent` channel. See docs/modules/agent-chat.mdx. The `workspace` view is a **dockable window manager** (dockview,
wrapped): module **panes — panels and widgets alike** — open as tabbed/split/
floating windows. **Widgets are first-class panes** (no separate grid); the
**dashboard is the default seeded one of several named workspaces** you switch
between via a tab strip, each layout persisted server-side. A minimal `scratch`
panel is the reference non-singleton panel. A `clubhouse` module onboards a
Clubhouse account via a widget (unofficial API, token held server-side). An `observability` module shows live data flow
(client/inbound/outbound I/O) — instrumented at the chokepoints, streamed over
the shared `/ws` socket. A **public plugin SDK** (`packages/sdk`,
`@horribledashboard/sdk`) plus a `marketplace` module let third-party frontend plugins
(panels/widgets/commands/keybindings) be installed from a catalog and loaded at
boot — see docs/architecture/plugin-sdk.mdx. A **backend plugin SDK** (`backend/sdk`,
`backend.sdk`) is the server-side counterpart: plugins contribute HTTP routes,
agent tools, `/ws` channels, lifespan hooks, and `dash` REPL facades, discovered
from bundled dirs, `HORRIBLE_PLUGINS_DIR`, and pip entry points — see
docs/architecture/backend-plugin-sdk.mdx. The **`dash`** Python REPL handle scripts
the running app (panes/workspaces/layout/I-O/settings; `dash.help()`) — see
docs/architecture/python-sdk.mdx. A `settings` module gives a
VS Code–style settings page where any module or plugin contributes its own
settings (declared in its manifest, read live via `useSetting`/`host.settings`,
overrides persisted server-side) — see docs/modules/settings.mdx. Note `GET /api/settings` returns the whole bag to the browser, so a **client secret / API key must never be a setting** (a client id is fine — it's public). A **connectors** module is the integration surface: external accounts the node holds credentials for, rendered as a **row of tiles above the ask bar on the home page**. A connector owns its connect flow (`oauth` device/redirect, `api-key`, or a `custom` multi-step form), its credential (Fernet-encrypted in `secrets.db` under `connector:<id>`, **never handed to the browser**; the master key lives outside `$HORRIBLE_DATA_DIR` at `~/.horrible/secrets.key` so copying the data dir leaks nothing), and the agent tools it unlocks. Contributed via `host.add_connector` (`backend/sdk`), so backend plugins register like built-ins. **GitHub is implemented** (device flow — OAuth Apps have no PKCE, so an authorization-code flow would mean shipping a secret; `read:user`+`repo`; `github.searchCode/searchRepos/listRepos/readFile/listIssues`). **Google is implemented** (loopback authorization-code + **PKCE**, because Google's device flow can't carry `drive.readonly`; scope is Drive read-only only; `google.driveSearch/driveRead/syncDrive`) and is deliberately **bring-your-own-client** — `drive.readonly` is a Google _restricted_ scope, so a published app would need verification + an annual CASA assessment, and an app in Testing expires refresh tokens after **7 days**; with your own Cloud project you're your own sole test user. `google.syncDrive` / `POST /api/connectors/google/sync` walks Drive into a **library** as `note` sources (Google Docs exported, PDFs parsed with **pypdf** — _not_ PyMuPDF, which is AGPL), paginated and **incremental** via Drive's `changes` feed, with a `google_drive_files` map in `app.db` so a re-sync replaces rather than duplicates. A connector's `id` **must** equal its agent-tool prefix — the orchestrator groups tools by name prefix, and `AgentTool.group` does _not_ name the group. Distinct from the games sign-in, which is identity-only: it runs on the separate game server and discards the provider token — see docs/modules/connectors.mdx. A **database** module is a plug-and-play, psql-like database inspector: a query console pane that reaches any connected database through a pluggable driver layer. Drivers declare a **dialect**: `sql` (sqlite / postgres+pgvector / duckdb / mysql / **oracle**, incl. 23ai AI Vector Search), `json` (**lancedb / chroma / qdrant / weaviate**), because vector stores have no SQL dialect — a collection, a metadata filter and a query vector is all they take, so the console sends a native JSON operation body (`{"op": "search", …}`) rather than faking SQL over them — or `mongo` (**mongodb**, `pymongo` is a core dep). Every dialect returns the same columns/rows grid. `mongo` is deliberately **not** a flavour of `json`: MQL is a real query language, and mapping `find` onto `search` would be exactly the silent reinterpretation the vector drivers refuse — so it gets its own ops (`find`/`aggregate`/`count`/`distinct`/`describe`/`indexes`/`databases`, plus writes) and bodies are parsed as **Extended JSON** (`{"$oid": …}` works; an `ObjectId` renders as bare hex on the way out, so you type it back as `{"$oid": …}` — coercing any 24-hex string in a filter would silently change the meaning of a filter on a string field). Note **`aggregate` is not automatically a read**: a pipeline containing `$out`/`$merge` rewrites a collection, so the read-only gate inspects the pipeline (at any depth) rather than trusting the op name — and `command` counts as a write for the same reason a multi-statement SQL string does. Two built-in connections: `app` (the node's SQLite database, `$HORRIBLE_DATA_DIR/app.db` — library sources, browser history, code symbols, tasks) and `vectors` (the app's own **LanceDB** store under `$HORRIBLE_DATA_DIR/lancedb`, one table per collection, also used by agent-commons matchmaking). A third, `atlas` (the shared MongoDB cluster), appears **only** when `ATLAS_ADMIN` is set — env-only and default-off, because every node on the fabric holds `ATLAS_DB_USER` to publish its presence record, so "credentials are configured" would gate nothing; `1`/`ro` is read-only, `rw` allows writes, and the check lives in the driver (`_guard_writes`) because `database.execute` is an agent tool and a route-only check would leave `run_query` as a back door. `uri` is a **secret field** (a connection string embeds the password) and the `atlas` connection carries no URI at all — `resolve_config` adds it from the env at query time. LanceDB is a _directory_, not a SQL-attachable file — that's precisely why it needed a json-dialect driver to become queryable. A similarity `score` is only derived for **cosine** spaces; Chroma and LanceDB default to squared L2, where `1 - distance` is negative and meaningless, so those show raw `distance` instead. Non-core clients are optional extras (`uv sync --extra chroma|qdrant|weaviate|vectordb|oracle`), lazy-imported. See docs/modules/database.mdx. A **library** module is a personal knowledge base built on that vector store: ingest website blogs (by URL, extracted with trafilatura), notes, and **images/videos** (PDF/EPUB deferred) as **sources + chunks** — a `library_sources` catalog in `app.db` plus per-chunk rows in the library's LanceDB table — then semantic-search a library for RAG, with live ingestion status on the `library` `/ws` channel. The default embedder is **text-only**, so media is embedded by _proxy_ (alt text, caption, nearby heading harvested from the live DOM) and referenced by URL rather than copied. Optional **CLIP visual search** (`uv sync --extra clip` + the `library.clipEnabled` setting) adds a second space so media is findable by _appearance_ — undescribed images included: a 512-dim ViT-B/32 ONNX vector in an additive `<library>__clip` sibling table (LanceDB fixes vector width per table), fused with the text hits by Reciprocal Rank Fusion. The agent tools (`library.search/listSources/addSource`) are the retrieval half of RAG; `browser.save` is the write half — see docs/modules/library.mdx. A **llamacpp** module makes the node serve its own weights rather than depending on somebody else's app: an upstream `llama-server` build downloaded on demand into `$HORRIBLE_DATA_DIR/llamacpp/bin/<tag>-<variant>/` (the geoip-mmdb / `playwright install chromium` precedent — nothing bundled), a GGUF **catalog** spanning our managed directory plus the files Ollama and LM Studio already have (serveable, never touched — `llama-server` mmaps read-only, so duplicating a 20 GB file to "own" it would be absurd; origin gates deletion and `is_managed` resolves both paths, because a `..` is how a delete route becomes an arbitrary-file-delete route), and a supervised process. Chat integration is **one `PROVIDERS` entry with `dialect="openai"`, not a new dialect** — a bespoke one would mean six branches in `providers.py` and would silently lose the `tool_choice="required"` retry, which is gated on `info.dialect == "openai"`. Three things fail _silently_ if forgotten: **`--jinja` passed explicitly, never inherited** (it selects the model's own chat template, which carries its tool-call syntax; upstream currently defaults it on — verified on b10362 — but the default has flipped before, `--no-jinja` exists and `LLAMA_ARG_JINJA` can disable it from the env, and the fallback generic template fails silently: 200, fluent answer, every tool never called, reading as "this model is bad at tool use"); **an accelerator asset is never a substitute for `cpu`** (a CUDA name contains every token a CPU one does plus one, and `cudart-*` — the runtime redistributable, shorter and containing no server — must be excluded by the `llama-` prefix, and the **extension is per-OS** — `.zip` on Windows, `.tar.gz` everywhere else, so the original `endswith(".zip")` filter quietly made the whole module Windows-only and blamed upstream for it); and **`_endpoint_for` checks the live manager BEFORE the saved config** for this provider alone, since it takes an ephemeral port when 8080 is occupied. A digest mismatch aborts and writes nothing; an asset GitHub publishes no digest for installs as `verified: false` rather than pretending. The disk budget is checked **pre-flight** against the declared size (checking as you go means finding the disk full 30 GB into a 40 GB download) and downloads land via `.part`+rename so a truncated GGUF is never scanned as servable. This is also the one provider whose model _path_ is known rather than inferred, so `resolve_model_path` prefers it — matched on the `--alias`, never on "a server is running", because llama-server can be up while the agent talks to Ollama. Alongside it, **provider/endpoint are now per-agent** (`roster.resolve_provider`, `agent.<id>.provider/.endpoint` falling back to `agent.orchestrator.*`): they used to be global while `model` was per-agent, which made "run the coder locally, leave the orchestrator on Ollama" unexpressible, since a model _name_ means nothing on a server that lacks that model. It must be resolved at **all three** `run_agent_loop` call sites (orchestrator, `delegate.py`, the flow executor's Agent node) — a site left on `provider_for(config.provider)` doesn't fail, it quietly runs on the global provider. On top of that sits the **tracer** — the activations path, and a _separate artifact from chat_: chat runs the downloaded `llama-server`, tracing runs whatever libllama the `llama-cpp-python` wheel bundled (`uv sync --extra llamacpp`, pinned `==` because `ggml_abi.py` mirrors `struct ggml_tensor`, which is internal C with no stability promise). A traced pass with attention on is ~1 GB, so it is a **snapshot on disk** (`manifest.json` + `tokens.json` + one append-only `tensors.bin` read back with `Range`, karaoke's handling incl. the suffix form), never a stream. Three containments on the ABI risk: mirror only the first four fields and ask ggml's own functions for everything else; a **self-check on the first tensor** recomputes `nbytes`/`n_dims` and **aborts writing anything** on disagreement; and the tracer is a **subprocess** (Popen on a thread), so a segfault in a ggml callback is an exit code, not a dead backend. Four silent failures: **flash attention must be disabled explicitly** (fused, the score matrix never becomes a node, so attention capture yields nothing and reads as a filter bug), the **`CFUNCTYPE` must be held in a global** (GC'd otherwise → freed memory), **quantized tensors are metadata-only** (no dequantizer — `decode` refuses rather than guessing), and **no chat template is applied** (rendering one would trace a different token sequence than the text shown). Every record declares a **`fidelity`** (`full`/`fp16`/`summary`) and a `summary` has no bytes _by construction_; `modelSha` is the header MiB + size and says so via `modelShaScope`. A trace may only be overlaid on a chat turn when **both** `llamaBuild` and `modelSha` match (`traces.matches_run`) — the two llama.cpps are different runs. See docs/modules/llamacpp.mdx. An **audio** module is the node's default input, default output and the routing between them: a VoiceMeeter-shaped matrix where **strips** (sources) feed any number of **buses** (outputs) at once — which is the whole feature, since "play this into my microphone _and_ my headphones, but keep my voice out of my headphones" is unexpressible in a single output setting. Every module that makes a sound (karaoke, hassault, games, voice comms) now registers a strip instead of opening its own context, and two rules are silent if broken: **nodes cannot cross `AudioContext`s**, so a private `new AudioContext()` is a module the mixer cannot see and nothing says so; and **`ctx.close()` is no longer cleanup** — the context is shared, so closing it on unmount silences the entire app (`handle.release()` instead). A browser cannot _create_ a virtual device, so the per-platform half lives in `backend/modules/audio/providers.py` with two separate capability flags: **Linux** `canCreate` (PipeWire makes the cable on demand, no install), **Windows** `canControl` (Voicemeeter's Remote API over `ctypes`, driving the machine's whole mixer including audio the dashboard does not produce), **macOS** neither (BlackHole detected and linked). Nothing is bundled — the SearXNG precedent. The probe reports **three** states, the hardware module's rule: found it, looked and it is absent, and could not ask. Voicemeeter's strip/bus counts must be read from the running mixer (3×2 / 5×5 / 8×8) and its executable names do not match the marketing ones — `voicemeeterpro.exe` is **Banana**, Potato is `voicemeeter8.exe`. The matrix is deliberately not a setting (`SettingValue` is a scalar and `GET /api/settings` hands the bag to every plugin); it is a document in `app.db`, broadcast on the `audio` `/ws` channel so the agent's `audio.*` tools work with no pane open. An embedded `<iframe>`'s audio can never be routed — there is no element to attach — which is why the karaoke (yt-dlp → same-origin file) path is the one that works. See docs/modules/audio.mdx. A **visualizer** module renders HTML5 Canvas, Three.js, and Babylon.js dynamic client-side animations, and streams headless Pygame frames from backend subprocesses — see docs/modules/visualizer.mdx. A **karaoke** module is a PiKaraoke-shaped karaoke machine as a workspace (stage / queue / search panes plus a `karaoke` frame preset): **yt-dlp** search (biased toward karaoke versions unless the query already says so) and download into a `karaoke_songs` catalog in `app.db` with the media under `$HORRIBLE_DATA_DIR/karaoke/songs/`, a per-singer queue, and ±6-semitone pitch shift. The one idea everything follows from: the **session is process-global on the server** (`session.py`) and every mutation broadcasts the whole `PlayerState` on the `karaoke` `/ws` channel, so every pane — and any phone on the LAN — is a _renderer_, not an owner, and the agent's tools run the room with no pane open. Three rules that are bugs if forgotten: the **stage owns playback but the server owns intent** (the pane holding the `<video>` reconciles toward `playing` and reports its true position back — which is what lets a remote pause a video it isn't rendering); it's keyed by **`entry_id`, not `song_id`**, because the same song queued for three singers is three entries and keying by song would make "add it again for the next singer" a silent no-op; and every mutation bumps **`revision`** so a client drops an out-of-order broadcast instead of showing a queue that jumps backwards. Downloads deliberately **do not ride the shared task queue** (it is serial — a multi-minute download would park every library ingest behind it) but run detached under a semaphore, and an entry is queued **while still downloading** so a guest's song doesn't fall behind ones queued after it. The filename is the **row id**, not the title (the DB is the index, unlike PiKaraoke where the directory listing is) — a title is never safe on every OS. Pitch shift is a **live ffmpeg transcode, not a cached file**: singers hunt for their key by ear, and a cached copy would mean a full re-encode before a single note came out; the chain is `asetrate`+`aresample`+**`atempo`** and dropping that last stage is the classic bug that yields chipmunks. Consequently the transposed stream is unseekable and `?semitones=` deliberately doesn't advertise `accept-ranges`, while the plain path serves real byte ranges (including the suffix form — `bytes=-3` is the _last_ three bytes). yt-dlp is a core dep, lazy-imported; ffmpeg is optional and gates only transposition. Songs are fetched to the user's own node — **content is never bundled**, the SearXNG/AssaultCube precedent. See docs/modules/karaoke.mdx. A **browser** module is an **embedded web browser** pane with two engines: a light cross-origin `<iframe>` (default), and — opt-in via `HORRIBLE_ENABLE_SERVER_BROWSER=1` + the `browser-engine` extra — a **real headless Chromium** driven on the local backend and server-rendered to the pane (JPEG frames over `/ws`, interactions relayed back, persistent cookies/cache), built **agent-first**: the same live session backs the human panel and the agent tools (`browser.read`/`snapshot`/`scrape`/`click`/`type`/`media`/`save`), so the agent is handed the DOM content + an accessibility snapshot and can scrape, act, and **remember** — `browser.save` files a page or its images/videos into a library (the write half of RAG). Every request the Chromium makes is recorded as a `browser` I/O event (resource type + allowed/blocked egress verdict) and shown live in the pane's 📡 Network view and the observability panel. That view is now **four views, passive to active**: a CDP session harvests the per-request DNS/TCP/TLS/TTFB timing, peer IP, HTTP version and certificate Chromium already measured and Playwright hides (**Waterfall** — phases that didn't happen are drawn as nothing, because a reused connection genuinely has none; CDP's `-1` sentinel is a trap); **DNS** walks the delegation from the root servers down over plain UDP/53 (no privileges needed), showing referrals, glue, DS records, and restarting the walk on a CNAME; **Route** shells out to the system `tracert`/`traceroute` (raw ICMP needs admin) and plots locatable hops on a bundled SVG world map with no tile provider. Probe targets go through the same public-IP check as the fetch guard. Egress is SSRF-guarded; reader mode + bookmarks/history persist server-side — see docs/modules/browser.mdx. A **search** module is the open-web discovery layer: pluggable engines (Tavily/Brave/Exa/Serper by API key, a self-hosted **SearXNG**, and a keyless DuckDuckGo fallback so search works with zero configuration) behind one `SearchProvider` protocol, plus an AI layer of our own on top — query fan-out, canonical-URL dedupe, **Reciprocal Rank Fusion** (extracted from the library's hybrid search; fusion is rank-based because provider scores are incomparable units), guarded fetch+extract of the top hits, and an embedding rerank that **refuses to run on hash-fallback vectors**. `quick_search` (sub-second) vs `deep_search` (2–8s) is a latency contract, not a quality knob — an eight-second tool call mid-chat-turn is unusable, which is why `search.web` and `search.deep` are separate tools. API keys live in a single `search` **connector** (Fernet-encrypted, never a setting); the engine _name_ is a setting because it's public. SearXNG is AGPL so it is **supported, never bundled** (the pypdf/SingleFile precedent). A **focused crawler** indexes a curated seed list of ML sites, blogs and API docs into a dedicated `webindex` LanceDB collection — not a user library, which it would swamp — and is exposed as _just another provider_, so local hits fuse with live web hits for free. Re-crawls are near-free via three skip levels (304 → unchanged content hash → real change); the frontier is seeded from previously-indexed URLs, because a 304 on the start page yields no HTML and so no links. Writes batch **across pages** (`merge_insert` is a whole-table ~1.5s operation). Egress differs by leg and is the easy thing to get wrong: vendor APIs and the settings-supplied SearXNG URL go over plain httpx (loopback allowed for the latter), while **every result URL and crawled URL** rides `_fetch_guarded`. See docs/modules/search.mdx. A **network** module is the **distributed peer fabric**: a process-global `PeerHub` lets this backend node connect to other users' nodes over TCP/IP (hybrid direct/relay/LAN transports, Ed25519 node identity, settings-driven trust), so users collaborate via **agent-to-agent** (`agent.ask_peer` — your agent asks a peer's agent, gated read-only by default) and **collaborative shared panes** (a `collab` channel; scratch is the reference) — see docs/modules/network.mdx and docs/architecture/distributed.mdx. A **social** module is the human face of that fabric: a friends roster keyed by **person**, not machine. A second Ed25519 **person key** yields a `person_id` (same `base32(sha256(pubkey))[:16]` scheme as a node id), rendered as a checksummed **friend code** (`HD-XXXX-…`); each machine carries a **device certificate** signed by the person key, so one human with three boxes is one roster row. Verifying a cert has a third step `verify_device_cert` deliberately leaves to its caller — that the cert names _the node it arrived from_ — and skipping it lets anyone replay a friend's cert to impersonate them. **Accepting a friend grants fabric trust** to every one of their devices, which is exactly what makes peer chat, shared panes, and `agent.ask_peer` work between friends with no second pairing; friendship grants reachability, not authority (a remote agent turn is still gated by `network.allowRemoteAgent`). The roster is **local** (`social_friends`/`social_devices` in `app.db`) so it survives any directory going away, and presence is _derived_ from the hub's connection table, never stored. Note `resolve_person_id` tells a friend code from a bare id by **length**, not by whether the checksum passes — falling back to "treat it as a raw id" on failure would defeat the checksum and dial a mistyped code as if it were real. Discovery off the LAN goes through an **Atlas presence directory** (`social/directory.py`, collection `presence`): person*id → dialable addresses, self-published and **signed by the person key**, so a hostile directory can withhold a record but never point you at an impostor. The social *graph* is never written to Atlas — only "where is this person right now" — so losing the cluster downgrades discovery, never the roster. A record publishes the full **ICE candidate list**, not `advertised_address()` alone: that helper auto-detects the **LAN** IP, so publishing it by itself yields a record useless to anyone off your network — the public (STUN reflexive) candidate only appears with `network.iceEnabled` on. `_dial` consults it **last**, after known LAN addresses. The shared client is `backend/atlas.py` (not inside a module — hassault needs the same cluster), configured by `ATLAS_DB_USER`/`ATLAS_DB_PASS`/`ATLAS_CLUSTER_HOST` in `.env` — **env only, never settings**. Note `.env` is now loaded by `backend/__init__.py` too, because `scripts/dev.mjs` loaded it but the documented bare `uv run uvicorn` command did not, so credentials silently varied by launcher. See docs/modules/social.mdx. A **hassault** module (**HorribleAssault**) is an AssaultCube remix as a dashboard pane — our own client and netcode replacing its ENet/master-server stack. Implemented so far: the **map pipeline**, a port of `load_world`/`rldecodecubes` reading `.cgz` (Cube 1 worlds are a flat grid of columns, not BSP — which is why a Three.js rewrite is tractable). AssaultCube content is **supported, never bundled**: its media is copyright (source is zlib-like), so its maps are read from the user's own install via `hassault.installPath`, auto-detected if blank — same precedent as SearXNG. That restriction covers *their* content only, so the game ships **three maps of its own** (`mapsource.py`, `maps/hd\_*.json`) and needs no install to play; an install is an enhancement that adds 44 more. The source of truth is **JSON brushes, not committed `.cgz` binaries** — a blob in a public repo is unreviewable and undiffable, whereas a map here is a few dozen rects (`room`/`solid`/`stairs`painted in order over solid rock).`cgz.write*cgz` is the inverse of the reader, used by the export route (`/maps/{name}/download`, bundled-only) and by the round-trip test that is the writer's *entire* correctness argument — it has no independent spec, so agreement with a reader validated on 44 real maps is all there is. Two traps it pins: a **SOLID record stores only wtex+vdelta** (a solid cube carrying a floor height would be silently rewritten by its own round trip, so the writer refuses it) and a **run length is one byte** (longer runs split, each continuation still repeating the same previous cube). Bundled maps are checked for **playability, not just validity**: every spawn standable at the position `spawn_at`resolves, and a flood fill on foot reaching every standable cell — which is what caught`hd_atrium`'s gallery ring being cut into four pieces by its gates when only two staircases existed. Names are `hd**`and resolve **before** the install, so neither catalog can shadow the other. Textures/models/sounds are still missing and get the same treatment when they land: procedural, geometric, synthesized — never someone else's copyright. Four format traps, all pinned by tests: entities start at`headersize`, **not** at the 980-byte struct end (every official 1.3 map carries a 3–6 KB extra-header block between them); a `SOLID`record stores only wtex+vdelta and the rest must come from`sqrdefault`; **v10 scales angles ×10** (verified across all 1741 official spawns, not assumed); and a truncated cube stream is filled with defaults, not rejected. The 65536-cube grid ships as **nine raw byte planes** (`/maps/{name}/cubes`), not JSON — `floor`/`ceil`are signed — with`plane_order` reported by the metadata route so the two sides can't drift. The **renderer** (`hassault.play`pane) is also implemented: three is lazy-loaded, and`world.ts`/`geometry.ts`/`player.ts`never import it so they stay unit-testable headless. Two heightfield rules are easy to get backwards and both are pinned by tests — the **base height comes from the cell while the delta comes from the corner-vertex cell** (taking both from the vertex cell tears heightfields apart at every seam, silently), and the divisors differ on purpose:`vdelta/4`per render vertex vs`(sum of 4)/16`for the height a body stands on. Walls are emitted **from the open side only**, so each surface exists once and needs no back faces; an overhang uses`utex`, not `wtex`. Collision uses the circle's AABB like AC's `rectcollide`, so the player is **2.2 cubes wide and needs 3 cells of clearance**; movement resolves one axis at a time (or corners go sticky) and `dt`is clamped (a backgrounded tab otherwise teleports you through walls). No textures yet — surfaces are tinted by texture id, because texture slots are resolved via map`.cfg` files that aren't parsed. The **netcode** is implemented too: an authoritative match server (`match.py`) simulating on a `hassault` `/ws` channel, with client prediction, reconciliation and remote-player interpolation (`net.ts`pure/testable,`session.ts`holding the socket). Because the server must simulate, the physics exists **twice** —`backend/modules/hassault/physics.py`is a port of`world.ts`+`player.ts` — and the duplication is made safe the way the Kotlin wire is, with vectors both suites replay (`packages/core/src/modules/hassault/**tests**/physics-vectors.json`, carrying both `cases`for movement and`spawns` for placement); the fixture pins *agreement*, each side's unit tests pin correctness. A **`playerstart`'s `z` is not a ground height** — it's the mapper's *eye* at placement time (the modal distance to the floor is exactly 4 = `(int)(floor+4.5)`) and AC's editor flies, so the rest scatter 1–22 cubes up; `spawn_at` therefore takes the height from `_support`, the same query `step` resolves against, making a spawn the fixed point of the first frame. Reading it as a lower bound (`max(floor_at, spawn.z)`) put all 1741 official spawns in mid-air — the clamp fired at only six of them. Three things that look optional and are not: every input carries a **sequence number** and snapshots carry a **per-recipient `ack`** (prediction has nothing to replay without it); the server advances a player only on **that player's own commands with their own `dt`** (ticking by wall clock leaves a permanent jitter even when the prediction was right); and client-supplied `dt` is spent from a **replenishing budget** (~1.1× real time, 0.25s reservoir), which is the only thing stopping a client claiming time faster than it passes. Deliberately **no noclip on the wire**. Wire format is JSON on the shared socket, not binary — 20 Hz × 8 players ≈ 10 KB/s, and legibility in the observability panel is worth more than the bytes. **Cross-node matches** ride the peer fabric (`fabric.py`, wire types declared there not in `network/protocol.py`): a guest's own backend proxies for them, and a remote player is a `PeerPlayerConn` exposing just `send_json`, so `MatchRoom` never learns some of its players aren't browsers — and the guest backend reshapes the host's `welcome` so the browser has one code path, not two. Three things that are load-bearing: every inbound peer message is gated on `session.info.trusted` (knowing a room id is not friendship), remote input goes through the **same** validator as a browser's (a laxer second one is where the gap appears), and a dropped peer's players must be swept — they have no browser socket, so nothing else would ever notice they left. Invites go to **every** online device of a person (you invite a human, they pick a box); `GET /api/hassault/invitees` does the roster join backend-side so the pane never imports across a module boundary. **Weapons** are implemented (`weapons.py`): five of them, server-authoritative hitscan, and firing is a **flag on a movement command** — never its own message — so a shot carries the exact angles/seq of its frame, the rate limiter spends from the same time budget as movement, and the fabric carried weapons to remote matches with zero changes. Hit registration is **lag-compensated**: the client stamps each shot with `viewT` (`SnapshotBuffer.renderTime` — the server-clock instant it was rendering) and the server rewinds a 1s position history to match. That target is client-supplied, so **the clamp is the security boundary**, not tidiness: `PositionHistory.clamp` pins it to `[now-500ms, now]` — it's deliberately *not* range-checked in the wire parser, which doesn't know the time. Two rules do outsized work: a body is only a target if it's **nearer than the wall** (that comparison is the whole of cover), and a negative entry distance with a positive exit is **point blank, not a miss**. Fire rate/reloads run on the budgeted *simulated* clock (commands arrive batched, so a wall-clock gate silently halves a 700rpm rifle), while respawn timers use the wall clock (a dead player sends no commands). Health is public in the shared rows; **ammo is per-recipient** and hitmarkers drain when that envelope is built. Shots batch into the snapshot's `fx` — combat costs the tick rate, not the fire rate. Recoil is client-side (angles are client-owned anyway), the same concession as trusting `dt`. Weapon numbers are **served** (`GET /api/hassault/weapons`), never duplicated in TS — the `plane_order` precedent. **Bots** (`bots.py`) are not a second entity: a bot is a `MatchPlayer` whose input is produced here, enqueued through the same `enqueue`, so there's one simulation and a bot can't do what a player can't. No navmesh — it probes with the movement code's own `can_stand` and checks LOS with the same `raycast_world` a shot traces. Aim is wrong on purpose (rate-limited turn + wandering error), and the trigger fires when the barrel is where the bot *thinks* it's aiming — comparing against the true bearing instead yields a bot that never misses. Bots don't keep a room alive (the empty clock tracks humans), removal is newest-first by **insertion order** (Windows `monotonic` has ~16ms granularity), and they're host-only. **Movement is momentum-based and ported from AC's `physics.cpp`**, because the skill curve is the point: velocity with AC's friction constants (ground response ~0.12s vs air ~0.6s, so momentum and not the stick decides where a jump lands), the **chained-jump boost** (land and rejump within 250ms *while strafing* for 1.25× run speed — a clamp, not a compounding multiplier), **crouching** (eye to 3/4, speed to 0.4, silent, braced recoil, shrunken hitbox — and free of the speed penalty when begun mid-air, AC's `crouchedinair`), ramping gravity, and the **recoil push on the shooter** that makes AC's shoot-jumping work (`Weapon.kickback`, served like `interval` so the client predicts the identical impulse and never supplies one). Two deliberate deviations from AC, both because its exact behaviour would be a bug here: the velocity blend is `1-exp(-k·dt)` not `k·dt` (AC's is frame-rate dependent, and this server integrates client-reported `dt`), and the chain window is measured from **landing** rather than from the previous jump (AC's only fires on rising terrain, which makes it undiscoverable). One bug worth remembering: the "snap down off a lip" branch used to swallow genuine landings *and* a resting body dips below the floor every frame, so both branches now test `was_grounded` — "arrived on the ground" and "was already on the ground" are different events, and conflating them silently freed the chain timing and would have charged fall damage for standing still. **Fall damage** is the counterweight to shoot-jumping and goes through `_fall_damage`, not `_apply_damage`, because a death by map has no killer. **Noise** (`noise.py`) is a real mechanic and **server-resolved per recipient**: the wire carries only `{kind, volume, bearing, up}` — a bearing and a loudness, never an offset — because broadcasting footstep positions and letting clients judge audibility is a wall hack made of sound. Walls muffle rather than block, footsteps are paced by distance covered, and your own noises are never sent back (the client synthesizes them locally). Audio is **synthesized, never sampled** (`audio.ts`, band-passed noise bursts) — the same licensing rule as the maps — and the bearings are also *drawn* around the crosshair, so headphones aren't a competitive advantage. A **main menu** (`MainMenu.tsx`) replaced the bare Deploy button: map select, Train (alone, for learning the movement), Host with bots, the server browser incl. a LAN-discovery toggle, friends/invites, and settings; the Escape menu (`GameMenu.tsx`) shares the same panels from `menu-panels.tsx` and adds **Exit to menu**, so `deployed` is a flag the panel clears rather than a one-way latch. Prediction now rebases **velocity** too, via a private `you.move` block (`sinceLanded` is a duration, not a timestamp — the two simulated clocks are unrelated). Agent tools (`hassault.list_maps/list_matches/host/invite/status/surroundings/add_bot/remove_bot`) run the social side of a game and deliberately **stop short of playing** — 60 Hz input is a bot controller, not a tool; the agent fields bots rather than steering one. The **sniper scopes** (right mouse steps none → 2× → 4× → none): `zoom_levels` is **served** like `interval`, because the client divides both its FOV *and* its mouse sensitivity by the magnification and a hardcoded copy would be an aim wrong only while scoped. The mechanical half is a second cone — `hipfire_spread`, 27× the scoped one — so an unscoped sniper is a gamble rather than the best weapon at every range; the step rides on the *shot* as `scoped`, client-owned and **clamped against the weapon held** (`clamp_zoom`, not the wire parser, which cannot know which weapon the command lands on). **Train is no longer gunless**: `training.ts` plays the server's part locally (ammo, reloads, static dummies) and hands back the same `SelfState` a snapshot would have, so the trigger takes one code path in both modes — the shoot-jump can't be practised without a gun. That made shot geometry a third duplicate (`trace.ts`), pinned the same way movement is: `physics-vectors.json` now carries `traces`/`bodies` too. And a failed loadout fetch is **surfaced, not swallowed** — it used to leave you in a real match where the trigger silently did nothing. **Items** are implemented (`pickups.py`): six kinds off the map's own entities, server-authoritative, with **armour** as a real mechanic (it absorbs half of every hit and spends itself doing it) because `helmet`/`armour` entities would otherwise be inert. Three rules do the work: an item that **cannot help you is not consumed** (taking the armour at full armour and denying it to everyone else for forty seconds is the quiet unfairness this prevents); an item's `z` is the mapper's **eye**, so placements are resolved onto the floor by `physics._support` and **served** (`GET /maps/{name}` and the welcome) rather than re-derived in TS, the `plane_order` precedent; and the wire splits **the hole in the map (public `itemsOut`, the complement — a handful of ids, not sixty) from what it gave you (private `you.picked`, drained, carrying the amounts that actually applied)**. An absent `itemsOut` means "this server has no items", never "none are gone" — reading it the second way pops every taken item back once a tick. All three bundled maps carry item layouts (a bundled map without them would make the feature AssaultCube-owners-only, the exact asymmetry the licensing rule prevents), pinned by playability tests that also refuse an item **within pickup reach of a spawn** — which would make dying a resupply. **Water and ladders** are implemented across **all three** physics ports (`physics.py`, `player.ts`, `apps/native-fps/src/physics.rs`) with 13 new conformance cases binding them. Both are decisions, not AC ports — its constants are tuned against its own integrator. Water has **two states split at the eye, not the feet**: feet under is wading (slowed, still has a jump), eye under is swimming (jump becomes the swim control, crouch dives, and the screen tints at the same line so the moment you lose the jump is the moment it says so). It replaces the crouch penalty rather than stacking with it. The safe landing is mostly **drag, not a rule** — a landing while submerged is free and anything shallower is helped in proportion to its depth, because gating on the feet would make an inch of water a total fall-damage negator (the puddle-dive that refunds shoot-jumping). A **ladder is a volume you cannot fall out of**, its span resolved from the entity's height onto the cell floor (the mapper's-eye problem again; height 0 is **dropped**, never unbounded). Three ladder rules were each a bug first: the climb is `forward` **projected onto your facing** (so running past one does not launch you up it); while the input is climbing it is **not also walking** (without that grip, pressing back to descend walks you out of the volume); and at the last rung pressing up **lets go entirely** — releasing only the horizontal grip lets you walk *across* the ladder's centre, where the alignment flips sign and the input that was climbing up rides you back to the bottom. Two traps the fixture caught: **`eyeHeight` is absolute in TS and Rust but an offset in Python**, so two of three `submerged` ports double-counted `z`; and **the vector generator had lost its `hitboxSpecId` stamp** while both suites still checked it, so the first regeneration silently dropped two guards. hd_pit is flooded to its rim with two ladders out, pinned by tests that *climb* each bundled ladder (a ladder flush with the lip it serves is already stood on by the 2.2-cube body; one set too far back drops you before the ledge). **The native client draws all of it too**, each in the pass that suits it: items in the **opaque body pass** (placements from `MapInfo`, not the welcome — they are a property of the map, so one source serves a room and the range alike), water in the **translucent volume pass** as two quads with opposite winding (wound one way only it vanishes exactly when your head goes under), and ladders **inside the world mesh** so they upload once and shadow like any surface. `itemsOut` is an `Option` there for the same reason it is guarded in TS. `tests/browser_parity.rs` pins the item tints, bob/fade, water fallback and ladder dimensions against the browser's TypeScript **read at test time** — colour is the identifying signal, and a health pack red in one client and orange in the other looks deliberate from either one alone. Native Train fetches `GET /api/hassault/items` and resolves only the **ammunition** half locally (health/armour mean nothing where nothing shoots back); with no served table the range's items are **drawn but inert** rather than taken at a reach the client invented. Still missing: game modes beyond deathmatch. See docs/modules/hassault.mdx. A **mobile-android** companion app (`apps/mobile-android/`, Kotlin + Compose) rides that same fabric: it pairs by scanning a QR invite and then appears as an ordinary peer carrying a `mobile` capability — remote control of panes/media (`remote_command`, `backend/modules/network/remote_control.py`), streaming agent chat, and `mobile.*` agent tools pointing back at the phone (`mobile*tools.py`). Because it **reimplements the signed-envelope wire in Kotlin**, two contracts are byte-exact and fail silently (a closed socket, no error) when they drift: the node id is `base32(sha256(pubkey))[:16]`— \_not* base64url — and the signed canonical JSON must match Python's`json.dumps(sort_keys=True, separators=(",",":"))`exactly, which means recursively sorted keys,`ensure_ascii`, an always-present `re`(even as null), and Python's float`repr`(Java's`Double.toString`goes scientific at 1e7, Python at 1e16, and every envelope's`ts`sits in that gap).`backend/tests/test_network_mobile_conformance.py`pins those vectors. The invite QR embeds`trust.advertised_address()`, which auto-detects the **LAN IP** — `localhost`makes every invite undialable from a phone — and the backend must be bound with`pnpm dev:lan`. See docs/modules/mobile-android.mdx. An experimental Electron shell lives on the `electron-shell`branch. The deep-research pipeline runs`plan → [subagents → critique]\* → synthesis → verify → citations → export`: **gap-filling rounds** (the critique names what's missing and spawns a targeted wave; the round is derived from the DB so a restart resumes correctly), a **verification pass** grading claims by \_independent publisher\* — three citations to one domain count as one source — plus a contradiction check, and **steering** (park before subagents run to edit the plan, inject follow-ups mid-run, live per-subagent tool traces). Note `init_research_db` is `CREATE TABLE IF NOT EXISTS`, so new columns need `_ensure_column` or an upgraded install silently never gets them. The **training** module now carries a **typed recipe surface** on top of its notebook/venv machinery: `recipes.py` is a curated field catalog rendered as a form (`training.recipe` pane) and **materialized into `main.ipynb`** — cells, not a new runner, so it rides the same kernel and the same Kaggle/Colab push; a regenerate _replaces_ the previous block (`horrible_recipe` cell metadata) because two `SFTConfig` definitions means the second silently wins. Fields are **validated against the project venv** (`introspect()` reads `dataclasses.fields()` off the installed `SFTConfig`/`LoraConfig` in one cached subprocess) across four states, and the last two differ: `unsupported` = we asked and it said no → **not emitted**; `unvalidated` = we couldn't ask → emitted with a banner. `max_length`/`max_seq_length` **are** aliases; `warmup_ratio`/`warmup_steps` deliberately are **not** — transformers 5 dropped the first, but they carry different _units_, so aliasing would send `0.03` into a field meaning "3/100ths of a step" (no warmup, no error). The form states it covers N of the installed class's M knobs (112 on transformers 5.15) rather than implying it is the API. **`report_to` is additive**: every generated recipe installs `ht.callback()` (a `TrainerCallback` in the helper), so local metrics work offline and with `report_to=["none"]` — "none" means no third party, never no metrics. Credentials live in a **`trackers` connector** (W&B key + MLflow URI, both secret; a tracking URI embeds one) and reach the run through **`SessionConfig.env` at spawn**, never the notebook/`project.json`/an HTTP response; it is the one connector with **no agent tools**, so its id names no tool group. `convert.py` closes the loop: checkpoint → GGUF into llamacpp's **managed** dir, converter script fetched at the **installed build's tag** (recorded `verified: false` — GitHub publishes no digest for a raw file), LoRA told from a full checkpoint by `adapter_config.json` and sent to a different converter, deps installed via **`envs.install` (`uv pip install --python`) because a uv venv has no pip at all**. See docs/modules/training.mdx. A **hardware** module is the one capability probe every heavy surface now reads instead of guessing: `nvidia-smi` / `rocm-smi` / Apple-silicon Metal / `vulkaninfo` plus RAM, cached process-wide, spawned **synchronously** (asyncio subprocess spawning is broken under `uvicorn --reload` on Windows) and reached through `asyncio.to_thread`. It reports **three** states, not two — found it, looked and found nothing, and **could not ask** (`Profile.certain` plus a `note`) — because `nvidia-smi` missing from PATH yields the same empty list as a machine with no card and is not the same fact; rendering it as "no GPU detected" is the failure this module exists to prevent. From it come `llamaVariant` (the install route's `variant` was a flat `cpu`, now `auto`) — decided by the **card and the OS together**, because upstream publishes **CUDA for Windows only**, so NVIDIA-on-Linux resolves to `vulkan`; naming `cuda` there yields no install at all, a failure only reachable once the default became `auto` — `gpuLayers`, `threads` and the trace `tokenCap` — those request fields are nullable and resolved with `is None`, never falsiness, since an explicit `0` means pure CPU — each carrying a **reason string**, which is the only thing that explains a CPU build on a machine whose owner knows they have a card. Unified memory is reported `unified`/`exact: false` (calling it VRAM makes a 16 GB Mac look like a 16 GB card), a memory-less Vulkan device gets **no offload** rather than a guess, and there is no `metal` variant to download (upstream's macOS builds carry it). An override replaces the accelerator list and stamps `overridden`, so a user's assertion is never presented as a measurement. No pane — a settings section and three settings. See docs/modules/hardware.mdx. Alongside it, **remote updates**: `updater.rs` in the Tauri shell against a signed manifest, as custom commands rather than the plugin's JS API because the release **channel is a runtime setting** and only the Rust `UpdaterBuilder` can pick an endpoint at runtime. Three things are load-bearing. The **signature is the whole security model** (HTTPS only says the bytes came from GitHub; anyone who can publish a release can serve an installer), and there is no bypass. The manifest lives at a **fixed `updater` tag, not `/releases/latest/download/`** — GitHub resolves "latest" to the newest non-prerelease, so a beta manifest there is unreachable and a stable one gets shadowed the moment a beta is promoted — and `publish-manifest` copies it there only after **all four** platform builds finish, on a non-draft release (draft assets need an authenticated request, so a manifest pointing at them verifies then 404s). And **`$HORRIBLE_DATA_DIR` is never touched by an update**: llama.cpp builds are keyed by an upstream tag, GGUFs are tens of GB, traces are tied to a build. Until the signing key exists, `updater::is_configured()` (a compile-time read of the config source, because the answer decides whether the plugin is registered at all) is false, the plugin is skipped so the app still starts, and the check says it cannot verify an update rather than "up to date". Both commands need an ACL entry _and_ a `PERMISSION_FILES` line in the `acl_coverage` test. See docs/architecture/releases.mdx. Public-install hardening closed the standing leak in `GET /api/settings`: **secret-shaped keys are blanked on the way out** (`SECRET_KEY_SUFFIXES`) with a separate `secretKeys` list naming the ones that are set, matched on the key _shape_ rather than a declaration (declarations live on the frontend, so trusting them means asking the untrusted side which of its own values are sensitive), **blanked rather than omitted** (omitted is indistinguishable from unset, and a settings page that can't tell would overwrite a saved token with `""`), and redacted **on the way out only** — `get_value` still reads the real value. Such settings are write-only in the UI. It is a backstop, not a repeal: a credential still belongs in a connector. A **localtrack** module provides local experiment tracking inspired by W&B and MLflow (SQLite store with WAL mode under `$HORRIBLE_DATA_DIR/localtrack.db`, compound index on `(run_id, key, step)`, server-side LTTB downsampling, `LocalTrackHFCallback(TrainerCallback)`, template notebooks, `LocalTrackIcon`, and `localtrack.*` agent tools) — see docs/modules/localtrack.mdx. Remaining modules (editor, terminal, files, full chat cockpit) are unimplemented — see docs/ for their designs.

## Stack (decided, do not re-litigate)

- **Frontend:** React + TypeScript, Vite, pnpm workspaces
- **Desktop shell:** Tauri (Rust) — wraps the same frontend as the browser build
- **Backend:** Python 3.12 + FastAPI, managed with `uv`. The backend is the app's
  brain: agents, data, MCP integrations, websockets to the UI.
- **Extensibility:** built-in modules first. Every feature (chat, dashboard, notes,
  terminal, files) is an internal module registered through a central registry
  (commands, panels, keybindings). The public plugin API (`@horribledashboard/sdk` +
  marketplace) exposes the same contract to third-party frontend plugins, and
  `backend.sdk` exposes a server-side contract for backend plugins (routes, agent
  tools, `/ws` channels); both are trusted/unsandboxed in v1 — see
  docs/architecture/plugin-sdk.mdx and docs/architecture/backend-plugin-sdk.mdx.

## Commands

- `uv run pytest` — backend tests
- `uv run uvicorn backend.app:app --reload --reload-dir backend --reload-exclude "logs/*" --port 8000` — backend dev server (the `--reload-dir`/`--reload-exclude` scoping keeps `logs/backend.log` writes from triggering a reload loop)
- `uv run ruff format .` and `uv run ruff check --fix .` — Python format/lint
- `uv add <pkg>` / `uv add --dev <pkg>` — Python dependencies (never pip)
- `uv sync --extra games-native` — install the native ViZDoom engine (the `vizdoom_toy` / `vizdoom_duel` games). It's an **optional extra** (lazy-imported), so the core app installs on every OS without it; add it only to run a Doom table locally. Prebuilt wheels: Windows amd64, Linux x86_64/aarch64, Apple-Silicon macOS 14+ (Intel/old macOS builds from sdist — needs `brew install cmake boost sdl2 openal-soft`). The Fly game-server image already pulls it.
- `uv sync --extra clip` — install **CLIP visual search** for the library (index media by appearance, not just alt text). Another **optional extra** (lazy-imported, gated by the `library.clipEnabled` setting): ONNX Runtime rather than torch, so it's ~60 MB and installs everywhere; the ViT-B/32 weights (~350 MB) download once on first use. Existing media needs `POST /api/library/reindex-clip` to backfill.
- `uv sync --extra llamacpp` — install **activation tracing** (`llama-cpp-python`, CPU-only). Another **optional extra**, lazy-imported and pinned with `==` because `backend/modules/llamacpp/ggml_abi.py` mirrors ggml's internal tensor struct. PyPI ships an sdist rather than wheels, so this builds llama.cpp and needs cmake plus a C++ compiler; without it the `traces` section says so and the chat provider is unaffected (it runs a downloaded `llama-server` binary and needs none of this).
- `uv sync --extra voice` — install the **Clubhouse voice agent**'s speech: local Whisper STT (`/api/agent/stt`) and Edge TTS (`/api/agent/tts`). An **optional extra** because Whisper needs torch (~1–2 GB); both services are lazy-imported and the two routes answer **503 with an install hint** rather than 500 without it, so the rest of the app is unaffected. Decoding the browser's WebM/Opus chunks also needs `ffmpeg` on PATH.
- `uv sync --extra geoip` — install **DB-IP GeoIP lookup** so the browser's Route view can plot traceroute hops on a map. Optional and lazy-imported; the DB-IP Lite City database (CC-BY, freely redistributable — unlike MaxMind GeoLite2, which needs an account and a license key) is downloaded once to `$HORRIBLE_DATA_DIR/geoip/dbip-city.mmdb`. Without it hops still list, they just have no coordinates.
- `uv sync --extra browser-engine && uv run playwright install chromium` — install the real headless-Chromium engine for the **browser** module's "full mode" (server-rendered, agentic). Also an **optional extra** (lazy-imported); the `playwright install` step fetches the ~150 MB per-OS Chromium once. Gated at runtime by `HORRIBLE_ENABLE_SERVER_BROWSER=1` — without the extra or the flag, the browser stays in the light iframe mode.
- `pnpm dev` — browser layout, full stack: starts the backend, the Vite UI (port 5173,
  proxies /api and /ws to 8000), **and** the central game server (:9090) together via
  `scripts/dev.mjs`. `--no-gameserver` (or `HORRIBLE_DEV_NO_GAMESERVER=1`) skips the
  game server. Sign-in points at the **hosted** server by default, same as
  `pnpm dev:desktop` and a packaged node — the bundled local server ships with no OAuth
  client id or secret, so forcing the node at it (as this used to) killed GitHub/Google
  sign-in in the browser layout while desktop kept working. `--local-gameserver` (or
  `HORRIBLE_DEV_LOCAL_GAMESERVER=1`) points the node at the bundled one when you want a
  self-contained stack. `pnpm dev:web` is UI-only; `pnpm dev:lan` exposes both on 0.0.0.0
  (peer fabric).
- `pnpm dev:desktop` — desktop layout (Tauri; **spawns/supervises the backend
  itself** via `src-tauri/src/backend.rs` — reuses one already running on :8000).
  Unlike `pnpm dev`, this **defaults to `0.0.0.0`** (the desktop node is the one you
  pair a phone with and run the peer fabric from); `--host 127.0.0.1` opts out. The
  knob is `HORRIBLE_DEV_HOST`, set by `scripts/dev-desktop.mjs` and read by both
  `vite.config.ts` and `bind_host()` in `backend.rs`, whose fallback stays loopback
  so a packaged build is never LAN-exposed.
- `node scripts/build-backend-runtime.mjs` — build the **bundled backend runtime** a
  packaged desktop app ships: a relocatable CPython (python-build-standalone, the
  distribution `uv` manages) with every locked dependency in its own `site-packages`
  and the `backend/` tree beside it, written to
  `apps/desktop/src-tauri/backend-runtime/` where `bundle.resources` picks it up. ~1 GB
  and a few minutes; git-ignored, and only needed to _package_ — `pnpm dev:desktop`
  runs the checkout. A real interpreter rather than PyInstaller because the import
  graph isn't knowable at build time (backend plugins come from pip entry points), and
  freezing it breaks that silently. See docs/architecture/releases.mdx.
- `pnpm typecheck`, `pnpm lint` — whole workspace, from the root
- `cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml` — Rust check
- `pnpm build:hassault` / `pnpm build:hassault:debug` — build the **native
  hassault client** and hard-link the result into `apps/native-fps/bin/`, where
  the launcher looks. Use these rather than a bare `cargo build`: `pick_binary`
  starts the _newest_ of six candidate paths by mtime, so a sibling build (the
  other profile, or a stale `bin/` copy) can silently win and run a binary
  without the change you just made.
- **Android companion:** open `apps/mobile-android/` in Android Studio and run `app`.
  There's no committed Gradle wrapper yet, so there is no CLI build; `local.properties`
  is git-ignored (machine-local `sdk.dir`). The phone reaches the backend only when it's
  bound to the LAN (`pnpm dev:lan`) and the backend port is allowed through the firewall.

## Conventions

- TypeScript strict mode; no `any` without a comment explaining why.
- Pydantic models for every API boundary; the backend is the source of truth for
  shared types.
- **Never write `os.environ.get("HORRIBLE_DATA_DIR", ".data")`.** `backend/paths.py`
  is the one authority on where files live (`data_dir`, `config_dir`, `cache_dir`,
  `log_dir`). That inline default was relative to the **cwd**, which is set by
  whichever launcher started the backend, so the same code resolved to different
  directories under `pnpm dev`, the Tauri supervisor and a packaged build — a user's
  llama.cpp install simply vanishing. `paths` resolves from the source tree instead:
  env override → `<repo>/.data` in a checkout → the per-OS location. See
  docs/architecture/data-directories.mdx.
- New features go through the module registry — a module declares its commands,
  panels, and keybindings in one place; nothing reaches into another module's
  internals. See `.claude/skills/new-module/SKILL.md` before adding a feature.
- **Never install a `keydown` listener in a component.** `packages/core/src/keymap/`
  is the one keyboard authority: declare a `KeybindingDecl` (with a `when` clause
  over the closed context-key vocabulary if it should be pane-scoped). A pane that
  genuinely needs the keyboard — a game, a terminal, the server-rendered browser —
  takes **capture** (`useCapture`, or `capture` in its manifest) so the shell knows
  to suppress its own bindings, and Escape unwinds through one ordered ladder
  instead of every component racing for it. Bindings the host steals
  (`mod+1..9` is browser tab switching and never arrives) are declared in
  `keymap/reserved.ts` and split by `hosts`/`platforms`. See
  docs/architecture/keybindings.mdx.
- Browser and desktop layouts share one codebase; never fork a component per
  platform — branch on a platform capability check instead.
- Formatting/linting is automatic: a PostToolUse hook runs ruff (Python), prettier +
  eslint (TS/JS), and rustfmt (Rust) on every file you edit. Don't hand-format.
- **Clubhouse App Versioning:** The Clubhouse API requires a current Android app version header (e.g. `26.07.12`). If auth fails with `login did not pass token validation`, update `AppVersion` in `backend/modules/clubhouse/auth_helper/Program.cs` and `routes.py`, then delete `backend/modules/clubhouse/auth_helper/bin/ch-auth-helper.exe` so the backend forces a recompile.

## Documentation (docs/)

`docs/` documents the layout shell and every module — see
[docs/README.mdx](docs/README.mdx) for the index and the full sync policy. The short
version: adding or changing a module, panel, command, capability, backend route, or
layout-shell behavior must update the matching `docs/` page **in the same change**
(new module → new `docs/modules/<name>.mdx`). A Stop hook flags code changes under
`apps/`, `packages/`, or `backend/` that don't touch `docs/`; pure refactors are
exempt — just say so.

The docs are authored as **MDX with Mermaid diagrams** and published as a
[Docusaurus](https://docusaurus.io) site (`website/`, which reads this `docs/`
tree directly). `pnpm --filter @horrible/docs build` builds it locally; pushing to
`main` deploys to GitHub Pages via `.github/workflows/docs.yml`.

## UI and Design Standards

Apply a modern, developer-first Kombai aesthetic across the UI components:

- Elevation & Color:
  - Surface: Dark slate background (#16181D) with subtle 1px border (#262934) and inset top shadow.
  - Accentuate cards on hover with a crisp border highlight (#3B82F6 or #6366F1 at 40% opacity).
- Typography & Badging:
  - Use Geist/Inter for UI text and Geist Mono/JetBrains Mono for IDs, paths, and registry keys.
  - Replace raw badge borders with soft pill chips (e.g. green status dot + text on translucent green fill).
- Command Snippets:
  - Display commands (uvx, npx, http endpoints) inside recessed, rounded code containers with syntax-colored protocol prefixes.
- Compact Dev-Tool Form Controls:
  - Standardize all inputs, selectors, and action buttons to a sleek 30px height with 6px border-radius.
  - Group related inputs into inline segmented blocks.
  - Use high-contrast primary buttons paired with subtle ghost secondary buttons and clean micro-icons.
